# Chapter 1 - Anatomy of an Index

## Test

## 核心要点
1.  索引的叶子结点是双向链表，上面索引页是B+平衡树，B+数是有序的，搜索是用二分法可以快速定位。对数算法节省空间，百万级表三四层索引就够了
2.  索引页只存索引信息，最后一层包含表记录信息（主键）。
3.  慢索引Slow Index。查询慢不一定是索引坏掉了需要重建，如果索引不唯一，在匹配到多条记录时，要在链表中逐条匹配，这是一个串行操作，有时候比全表扫描还要慢，因为全表扫描可以并发读表。
4. 索引完整查询三步流程（后两个是索引变慢两大根本原因）
	1. B 树层级遍历，快速定位目标所属叶子节点（效率最高，有固定层级上限）
	2. 遍历叶子链表，顺着双向链表读取所有匹配数据，范围查询耗时取决于匹配数据量
	3. 回表查询：通过 ROWID/RID 读取原数据表完整行数据，当数据表数据无序散落时，IO 开销剧增，这是索引查询变慢的核心瓶颈。

## 扩展知识
#### 三大数据库索引对比（豆包）

##### 1. 核心定义

聚集索引：表数据本身就是按索引键 **物理有序排列**，一张表只能有 1 个。
非聚集索引：只存索引键 + 行地址，数据本身无序。
叶子节点就是整行数据

---

##### 2. SQL Server

- **主键默认就是聚集索引**
- 整张表**磁盘物理数据行完全按聚集索引字段排序存放**
- 无聚集索引 = 堆表，数据杂乱无序

---

##### 3. MySQL（InnoDB 引擎，主流）

1. **InnoDB 表一定有聚簇索引**，不存在纯堆表
2. 规则：    
    - 有主键 → **主键就是聚簇索引**
    - 无主键 → 选唯一非空键当聚簇索引
    - 都没有 → 自动生成隐藏 6 字节 ROWID 当聚簇索引
3. 特点：    
    - 表数据**逻辑上按聚簇索引有序存储**
    - 二级索引叶子只存**主键值**，回表靠主键查整行
4. 区别 SQL Server：    
    MySQL 是**逻辑有序**，磁盘物理不一定严格连续（依靠**B + 树叶子节点双向链表**，把所有行**逻辑串成有序队列**，物理存储散乱，但遍历链表就是按聚簇索引有序遍历。插入只改链表指针，**不用大规模移动磁盘数据**）

---

##### 4. PostgreSQL

**没有传统意义上的「聚集索引」**

1. PG 默认表 = **堆表**，原始数据行**完全无序存放**。主键 = 普通唯一索引 + NOT NULL
2. 普通 B 树索引 = 二级索引，存键 + 行号，**不组织表数据顺序**
3. PG 替代方案：    
    - `CLUSTER 表名 USING 索引名`：**临时把表数据物理重排**
    - 重排后有序，但**增删改会再次变乱**，不会自动维持顺序
4. 结论：
    **PG 无原生永久聚簇索引机制**，数据天生无序，全靠索引定位
5. 与MySQL区别：
    - MySQL的ROWID是一个逻辑ID，只要行不删就不变； PG是CTID，格式是页号+行号，在`UPDATE`、`VACUUM`、`CLUSTER`、页分裂、行移位时都会导致**CTID 改变**
    - MySQL在有主键时，二级索引叶子节点存的是主键值，回表通过主键走聚簇索引找行数据，无主键时二级索引叶子节点存的是隐藏的ROWID；PG无论有没有主键和唯一索引，所有普通 B 树索引叶子节点上统一只存CTID，永远不会存主键值当做回表地址
    - PG 靠什么机制抵消这个性能劣势？死元组 + VACUUM 延迟清理，不立刻修正索引，旧 CTID不会马上从索引里删掉，对新行新增索引条目，旧的CTID要等待VACUUM 批量回收清理时处理，不阻塞业务。在此之前索引扫描查到旧CTID，在访问堆表时发现是死元组直接跳过。可以调整fillfactor 预留空间，减少行迁移，提高VACUUM效率。VACUUM可以手动执行，也可以等后台自己判断时机自动调度
    - MySQL用逻辑主键统一收口，牺牲一点点回表效率，换取更新时二级索引零维护，写友好。MySQL有的B树分主键B树和二级索引B树，二级索引查到主键值后再去主键B树拿到实际数据。PostgreSQL直接存物理地址，查询回表更快（少一层主键映射），把代价转移到更新行移位后的索引清理，读偏友好，写靠配置优化兜底
6. Cluster：对PG来说，应对大量回表的方式就是
	```
	CLUSTER table_name USING idx_name;
	```

# Chapter 2 - The Where Clause
## 核心要点
1.  联合索引（Concatenated Indexes）。Select可以使用联合索引从左到右的子集，不能跳列，索引顺序的重要性。索引排序黄金规则：等值条件在前，范围条件在后
2. 维护多个索引需要额外资源和时间。创建联合索引而非多个独立索引。对多独立单列索引，数据库可通过索引合并整合结果，效率远低于精心设计的联合索引。
3.  函数索引：CREATE INDEX emp_up_name ON employees (UPPER(last_name));可以用那个自定义函数
4.  参数化查询（Parameterized Queries）使用占位符`?`/`:name`/`@name`传参，不直接拼接字面量，通过 API 单独赋值，占位符又称绑定变量。
	1. 利：防 SQL 注入，支持执行计划缓存。
	2. 弊：优化器无法获取参数真实值，无法借助字段直方图判断数据分布，默认按数据均匀分布估算行数，固定生成同一执行计划，出现参数倾斜时会选用低效计划。
	3. 慎用：参数值直接影响执行计划的场景（状态值分布悬殊、分区查询、前缀不确定的 LIKE 查询）
5. 访问谓词 VS 过滤谓词。
	1. 访问谓词：限定索引扫描起止范围，缩小扫描区间
	2. 过滤谓词：遍历索引叶子节点时再筛选，无法缩减扫描范围
6. LIKE 索引使用规则。
	1. 前缀匹配`LIKE 'ABC%'`：可用索引
	2. 中间 / 后缀匹配`LIKE '%ABC'`/`LIKE 'A%C'`：仅前缀部分做访问条件，其余仅过滤
7. 位图索引。多字段组合查询友好，写入性能极差，仅适用于数仓静态数据，OLTP 业务禁用。
8. 局部索引（Partial Index）。在建索引时加`WHERE`条件，仅索引符合条件的数据，体积更小、查询更快。
## SQL 索引失效反模式（重点避坑）

1. 字段侧嵌套函数。`TRUNC(日期列)`、`UPPER(字段)`、数值隐式转换，直接失效普通索引，仅能用函数索引
2. 日期错误写法。不要对日期字段做函数处理，改用区间范围查询适配原生索引
3. 符串与数值混用比对。文本存数字，用数字值比对触发隐式转换，索引失效
4. 字段拼接运算。列做加减乘除、字段拼接运算，直接阻断索引使用
5. 万能查询 SQL（最大坑）。字段=:val OR :val IS NULL`写法，绑定变量下优化器生成全表扫描通用计划，彻底废掉索引
6. 数学运算嵌套查询字段。查询条件对表字段做数学计算，无法走索引
## 通用最优实践

1. 日常业务**一律使用绑定变量**，优先保障安全
2. 条件区分优先级：等值字段放联合索引左侧，范围放右侧
3. 时间、区间查询统一写成**开闭区间**，放弃字段函数写法
4. 高频固定筛选条件，优先建立**局部索引**精简索引体积
5. 杜绝万能拼接 OR 空值查询，动态查询直接用动态 SQL 拼接，保留绑定变量传参
6. 首通配符全文检索，放弃 B 树索引，使用各库专属全文索引

---
## 扩展知识
- 使用索引必须是等值精准：status = 'active'。status IN ('active')`、`status <> 'inactive' 这类变体大概率识别失败。
- 覆盖索引（Covering Index）。使用Include关键字，减少回表，常和Where一起使用。避免滥用。
```sql
CREATE INDEX idx_attr_active_part ON attribute(model_key_name, object_name, attribute_name) INCLUDE (version) WHERE status = 'active';
```
- 覆盖索引实际上分两种情况，核心是杜绝回表。如果索引字段本身就能达到目的，也可以算是覆盖索引，如果不能，则使用Include关键字减少回表。覆盖索引实际上是索引覆盖不回表。

# Chapter 3 - Performance and Scalability
## 核心要点
1.  系统并发负载对性能的影响。
	1. 同等数据量下，并发请求越多，劣质索引性能衰减幅度远大于合理索引。
	2. 开发环境无压力负载，无法复现线上并发下的性能雪崩，仅靠简单基准测试不可靠。
	3. 能走索引≠最优索引，优化器只是选择比全表扫描快的方案，不代表是业务最优方案。
2. 响应时间与吞吐量核心认知
	1. 单核 CPU 性能已遇瓶颈，堆硬件、横向扩容只能提升整体吞吐量，无法优化单条 SQL 响应速度
	2. 生产环境架构更复杂，网络、防火墙、多层调用叠加延迟，往往比低配开发机更慢
	3. 合理索引设计是缩短单查询响应时间的根本，充分利用 B 树对数级扩容优势，远比堆砌硬件有效
	4. 数据库选型差异
		- 关系型数据库强一致性，牺牲部分写入性能，保障事务可靠
		- NoSQL 靠最终一致性实现高写入横向扩展，但无法替代 SQL 精准索引优化解决慢查询
3. 分布式相关补充
	1. CAP 定理、最终一致性：分布式场景下，强一致性会增加同步延迟、降低可用性；舍弃强一致可提升吞吐与可用，但易出现数据不一致问题。
	2. 分布式事务如 2PC，进一步拉高延迟、降低集群可用性，节点越多管控难度越大。
4. 存储硬件与缓存优化
	1. 机械硬盘 HDD：磁盘寻道延迟高，B 树层级遍历、多表联查极易触发大量随机 IO，拖慢查询。
	2. 固态硬盘 SSD：无机械结构，寻道速度远超 HDD，大幅削减磁盘 IO 耗时。
	3. 内存缓存：数据库自动缓存索引根节点、热点索引与数据，命中缓存可完全规避磁盘访问，是日常提速核心手段。    
5. 核心结论
	1. 索引字段顺序直接决定业务**数据量扩容、并发承压**两大场景下的可扩展性；
	2. 过滤谓词是线上隐形性能炸弹，业务增长后会彻底暴露性能缺陷；
	3. 解决慢查询优先优化索引结构与字段顺序，不要寄希望于升级硬件、集群扩容；
	4. 执行计划分析必须紧盯谓词信息，这是判断索引使用是否合理的核心依据。

## 扩展知识
### PostgreSQL

核心参数：`shared_buffers` 共享缓冲区（PG 核心数据 / 索引缓存区）
- 通用经验：服务器物理内存 **25% ~ 50%**
- 示例：64G 服务器 → 设置 `shared_buffers = 16GB`~`32GB`
- 行为：
        自动缓存 B + 树**根节点、分支节点、热点叶子页**，高频访问的表数据页也自动入缓存
        冷数据自动 LRU 淘汰，热点常驻内存，命中直接读内存，不走磁盘
- `work_mem` 仅用于排序、分组、去重、join、临时内存（ORDER BY / GROUP BY / DISTINCT / JOIN 用的临时内存）**不存索引与数据表**
	- 普通机器：**4MB~8MB**
	- 中型业务：**16MB**
	- 大内存机器：**32MB**
-  maintenance_work_mem（ vacuum、create index、alter table ）加速创建索引、清理数据
	- - **64MB ~ 256MB**
	- 64G 机器可以给 **512MB**
```plaintext
/var/lib/pgsql/14/data/postgresql.conf
```
64G内存：
```ini
shared_buffers = 16GB 
work_mem = 32MB 
maintenance_work_mem = 512MB 
effective_cache_size = 40GB
```

```bash
systemctl restart postgresql-14
```

```sql
show shared_buffers; 
show work_mem; 
show maintenance_work_mem;
```

# Chapter 4 - The Join Operation
## 核心要点
1.  连接基础认知
	1. **本质作用**：将范式化数据表数据，重组为非范式结构，适配业务查询与数据加工；多表关联极易产生磁盘随机 IO 延迟，**合理索引是提速核心**。
	2. **通用规则**：所有连接算法**一次仅处理两张表**，多表连接分步执行，先两表联查生成中间结果，再依次关联其余表。
	3. **连接顺序**：不改变最终查询结果，但严重影响执行性能；优化器会枚举所有连接顺序择优选择，表数量越多规划成本越高，**绑定变量是复杂 SQL 必备优化手段**，避免重复解析执行计划。
	4. **中间结果优化**：数据库采用**流水线推送**，无需落地存储完整中间集，逐行流转至下一轮连接，大幅降低内存占用。
2. 三大主流连接算法及适配场景之**嵌套循环连接 Nested Loops**
	1. **执行逻辑**：选定一张驱动表查出结果集，遍历每行数据去另一张匹配表精准查询对应数据，和 ORM 遍历查询逻辑一致。
	2. **优缺点**：驱动表结果集小时，查询效率极高，可利用索引精准定位数据；驱动表数据量大时，内层查询次数暴增，性能雪崩
	3. **索引设计原则**：驱动表按查询筛选条件建索引（含函数索引）； 匹配表按连接字段建立联合索引，实现快速索引范围扫描
	4. **实战痛点：N+1 查询问题**
		- 成因：ORM 默认懒加载，先查主表数据，再循环逐条查询关联子表数据，产生大量数据库交互
		- 核心危害：网络往返延迟远大于数据传输量延迟，是业务系统隐形性能瓶颈
		- 解决方案：开启**主动抓取 / 预加载**，直接在数据库层完成 JOIN 联查，规避多次循环查询
	5. **适用场景**：小结果集关联、等值匹配、左 / 右外连接高频场景。   
3.  三大主流连接算法及适配场景之**哈希连接 Hash Join**
	1. **执行逻辑**：选取数据量更小的一张表，基于连接字段构建内存哈希表；扫描另一张表，通过哈希匹配快速关联数据。
	2. **核心特性**    
	    - 无需为**连接字段**建立索引，索引仅作用于单表独立筛选条件
	    - 连接顺序不影响索引优化策略，优化逻辑对称
	    - 最优条件：整张哈希表可完整放入内存，避免磁盘溢写
    3. **性能优化手段**
	    - 建立单表过滤字段索引，提前过滤无效数据，缩减哈希表数据量
	    - SQL 仅查询业务必需字段，精简字段大幅压缩哈希表内存占用
	    - 增加业务筛选条件，进一步减少候选数据集    
	4. **数据库差异**：MySQL 原生不支持哈希连接，PG、Oracle、SQL Server 全面支持
	5. **适用场景**：大表与大表关联、结果集数据量大、无合适嵌套循环索引的批量查询。
4.  三大主流连接算法及适配场景之**排序合并连接 Sort Merge Join**
	1. **执行逻辑**：将两张表数据按连接字段排序，再以拉链式方式逐条匹配合并数据。
	2. **核心特点**    
	    - 完全对称：连接顺序不影响性能，是**全外连接**最优选择
	    - 索引规则和哈希连接一致，仅优化单表筛选字段
	    - 短板明显：无预排序时，全量排序开销极大，日常极少使用
	3. **优化关键**：利用索引天然有序性，直接读取有序数据，**省略手动排序步骤**，才能发挥性能优势
	4. **适用场景**：两张表数据已天然有序、大范围范围连接、全外连接查询。
5. ORM 连接开发实操要点
	1. **开发规范**：开发环境开启 SQL 日志，核查框架生成 SQL，提前规避 N+1 问题
	2. **抓取策略取舍**
        - 主动抓取 (Eager)：适合每次查询都必带关联数据的场景
	    - 懒加载 (Lazy)：适合按需获取关联数据，滥用极易触发 N+1    
	3. **精简查询方案**：通过 DTO 自定义返回字段、部分字段懒加载，避免查询全字段造成哈希表臃肿。
6. 核心选型 & 索引总规则
	1. 小结果集关联 → 嵌套循环连接 → 给**连接字段建联合索引**
	2. 大批量数据两表联查 → 哈希连接 → 仅给**单表过滤条件建索引**
	3. 有序数据 / 全外连接 → 排序合并连接 → 依托索引有序性免排序
	4. 通用铁律：优先在数据库层完成 JOIN，杜绝应用层循环拼接数据，减少网络交互次数。

## 扩展知识
PG 强制指定使用索引**planner hint**
```sql
-- 强制指定索引
SELECT * 
FROM table1 t1 INDEX (idx_table1_col1) 
JOIN table2 t2 INDEX (idx_table2_join_col) 
	ON t2.id = t1.t2_id 
JOIN table3 t3 INDEX (idx_table3_status) 
	ON t3.id = t2.t3_id
	
-- 强制不用索引
FROM table t INDEX () -- 空括号 = 强制不使用索引
```

PG 强制指定 JOIN 算法
1. 会话级临时开关，整个会话所有 JOIN 都强制用同一种算法
```sql
-- 只允许嵌套循环 
SET enable_nestloop = on; 
SET enable_hashjoin = off; 
SET enable_mergejoin = off;

-- 只禁止嵌套循环（三个值默认都是on的，关闭nestloop，数据库从剩下两个里面选） 
SET enable_nestloop = off; 
```
2. 精确控制每一次 JOIN 用什么算法，必须装pg_hint_plan插件
```sql
/*+ 
NestLoop(t1 t2) 
HashJoin( (t1 t2) t3 ) 👈 必须加括号，代表“前两张的结果” 
*/ 
SELECT * 
FROM t1 
JOIN t2 
	ON t1.id = t2.t1_id 
JOIN t3 
	ON t2.id = t3.t2_id;
```

不装插件如何调整让PG按自己的想法选择join算法
# 一、算法偏好

不用任何插件、不用 hint，靠**改写 SQL + 调整统计信息 + 调整会话开关 + 优化数据形态**，就能强制 PG 放弃 NestLoop，主动走 HashJoin/MergeJoin。

## 核心底层规则（PG 选 JOIN 算法的判定逻辑）

1. **NestLoop 偏好**
    - 外层驱动表结果集**行数极少**
    - 内表关联字段**索引极好**，单行查找成本极低
    - 优化器认为：外层行数 × 内层单行查找代价 总成本最低
2. **HashJoin 偏好**
    - 两边表**数据量都大**
    - 关联字段无高效单行索引，或走索引批量扫代价高
    - 优化器判定：构建哈希表 + 哈希匹配，比循环逐行查找更划算
3. **MergeJoin 偏好**
    - 两张表关联键**已经有序**（有有序索引，或者决定走sort merge后进行排序）
    - 数据量大且适合有序拉链合并

# 把 NestLoop 强行改成 HashJoin

## 方式 1：临时会话禁用 NestLoop

整条 SQL 执行前执行，仅当前会话生效，不影响全局
```sql
-- 禁止走嵌套循环，优先走哈希/归并
SET enable_nestloop = off;
-- 放行哈希连接
SET enable_hashjoin = on;
-- 可选：也关掉归并，只留哈希
SET enable_mergejoin = off;

-- 执行你的联表查询
SELECT ... FROM t1 JOIN t2 ...;

-- 用完恢复默认
RESET enable_nestloop;
RESET enable_mergejoin;
```

```java
String sql = """
    SET enable_nestloop = off;
    SET enable_mergejoin = off;
    SELECT * FROM 你的视图名;
    RESET enable_nestloop;
    RESET enable_mergejoin;
""";

// 然后正常执行这个 sql
List<Map<String, Object>> result = jdbcTemplate.queryForList(sql);
```

```java
transactionTemplate.execute(status -> { 
	// 1. 设置参数 
	jdbcTemplate.execute("SET enable_nestloop = off"); 
	jdbcTemplate.execute("SET enable_mergejoin = off"); 
	// 2. 查询视图 
	List<Map<String,Object>> list = jdbcTemplate.queryForList("SELECT * FROM 你的视图");
	// 3. 自动重置（事务结束会自动重置，或手动重置） 
	jdbcTemplate.execute("RESET enable_nestloop"); 
	jdbcTemplate.execute("RESET enable_mergejoin"); 
	return list; 
});
```

```xml
<select id="selectView" resultType="map"> 
	SET enable_nestloop = off; 
	SET enable_mergejoin = off; 
	SELECT * FROM 你的视图; 
	RESET enable_nestloop; 
	RESET enable_mergejoin; 
</select>
```
## 方式 2：更新ANALYZE 统计信息

统计信息陈旧，优化器误判行数，选错算法
```sql
ANALYZE t1,t2,t3;
```
让优化器拿到真实行数，大表场景自然倾向 HashJoin
## 方式 3：SQL结构微调，通过改写 SQL破坏 NestLoop 优选条件，更改执行预估体量

子查询包一层，固化结果集大小，让优化器判定为大结果集
```sql
select * from a join b on a.id = b.a_id where a.status = 'active';

-- where条件可选，有没有where，PG都会认为a_fixed是固定结果集从而放弃nestloop
select * from ( 
	select * from a where a.status = 'active' 
) as a_fixed 
join b on a_fixed.id = b.a_id;
```
包一层之后,PG 会把里面的 `a_fixed` 当成已经生成好的固定结果集，它不知道里面到底多少行，会默认为这个结果集比较大，既然驱动集可能很大，PG 就不敢用 NestLoop，从而自动选择 Hash Join，注意这时索引并没有被破坏
## 方式 4：临时救急，制造「数据量足够大」，破坏索引

PG 认为外层结果集大，循环遍历代价爆炸，自动切 HashJoin
1. 去掉驱动表精准过滤条件，扩大外层行数（外表）
2. 不让驱动表查出极小结果集（外表）
3. 对关联字段**删掉 / 屏蔽单行最优索引**（内表，临时禁止在关联字段上的索引）
    - 临时不让内表走关联键索引单行点查，NestLoop 优势消失，自动切 Hash

关联字段上做简单表达式运算，废掉索引单行查找能力（破坏索引）
```SQL
-- 原本走索引快速匹配，极易触发NestLoop
on a.id = b.a_id

-- 改写后索引失效，单行查找变慢，优化器放弃NestLoop
on a.id + 0 = b.a_id + 0
-- 或者包一层函数
on a.id = abs(b.a_id)
```
## 方式 5：调整成本参数，倾斜优化器决策（最糟糕，生产禁用）
修改 JOIN 成本计算偏向，让 NestLoop 成本估值变高
```sql
-- 调高嵌套循环估算成本，让优化器嫌它贵

-- 随机 IO（索引扫描、NestLoop 内部查找）的成本权重。走索引 = 随机跳着找数据 = 比较慢
SET random_page_cost = 4;
-- 顺序 IO（全表扫描、HashJoin、批量读）的成本权重。顺序扫表 = 连续读 = 很快
SET seq_page_cost = 1;
-- random 越高，索引、NestLoop 看起来越贵，seq 越低 → 全表、HashJoin 看起来越便宜
```

# 反向控制：怎么制造条件走 NestLoop 

1. 外层表加严格筛选，控制返回行数极少
2. 内表关联字段建立**高选择性联合索引**
3. 开启`enable_nestloop=on`，放开嵌套循环

## 一、分页优化（Pagination Optimization）

核心问题：**传统 LIMIT offset, size 分页，在大 offset 下性能会断崖式下跌**。

### 1. 为什么慢？

- 执行 `SELECT * FROM t WHERE ... LIMIT 100000, 10` 时，数据库会：
    
    1. 先扫描前 100010 条数据
    2. 再丢弃前 100000 条，只返回最后 10 条
    
- 偏移量越大，需要扫描的数据越多，耗时越长，还可能导致回表次数暴增。

### 2. 面试必问的优化方案

#### 方案 1：基于主键 / 索引的「游标分页」（推荐）

原理：利用索引有序性，用 `WHERE id > ? LIMIT ?` 替代 `LIMIT offset, size`

sql

```
-- 传统写法（慢）
SELECT * FROM t WHERE status=1 LIMIT 100000, 10;

-- 优化写法（快）
SELECT * FROM t WHERE status=1 AND id > 100000 LIMIT 10;
```

优点：索引直接定位，时间复杂度从 O (n) 降到 O (log n)，百万级数据也很快。

#### 方案 2：覆盖索引优化（减少回表）

- 如果业务允许，先通过覆盖索引拿到主键列表，再关联查询：

sql

```
SELECT * FROM t 
WHERE id IN (
    SELECT id FROM t WHERE status=1 ORDER BY id LIMIT 100000, 10
);
```

优点：内层子查询走覆盖索引，避免回表，外层再用主键快速获取数据。

#### 方案 3：业务层面的限制

- 不支持跳转到指定页码（比如 “第 1000 页”），只提供 “上一页 / 下一页”
- 限制最大页码，比如最多支持 100 页，避免极端 offset

## 二、大表优化（Large Table Optimization）

核心问题：**表数据量过大（通常千万级以上），导致索引维护、查询、备份、维护都变慢**。

### 1. 优化方向 1：表结构与索引优化

- **字段瘦身**：
    
    - 用合适的数据类型（比如 `INT` 代替 `BIGINT`，`VARCHAR(20)` 代替 `VARCHAR(255)`）
    - 避免大字段（TEXT/BLOB），单独拆分到副表
    
- **索引优化**：
    
    - 避免过多索引（增删改时索引维护成本高）
    - 优先使用覆盖索引，减少回表
    - 定期分析执行计划，清理失效索引
    

### 2. 优化方向 2：分区表（Partition Table）

- 按时间 / 范围 / 哈希分区，比如按 `create_time` 按月分区
- 查询时自动扫描对应分区，减少数据扫描范围
- 适合有明显时间维度的业务（订单、日志）

### 3. 优化方向 3：分库分表（Sharding）

- **垂直分库**：按业务拆分库（比如订单库、用户库），降低单库压力
- **垂直分表**：按字段拆分表（比如订单主表 + 订单详情表），减少单表字段数
- **水平分表**：按规则拆分数据（比如按用户 ID 哈希分表），把一张大表拆成多张小表
- 工具：Sharding-JDBC、MyCat 等

### 4. 优化方向 4：读写分离

- 主库负责写操作，从库负责读操作
- 分页查询、报表查询等重读操作走从库，降低主库压力

### 5. 优化方向 5：数据归档

- 定期把冷数据（比如超过 1 年的订单）归档到历史表或数据仓库
- 生产库只保留热数据，维持表的活跃数据量在可控范围

## 面试回答模板（直接背）

**分页优化**：

分页优化主要解决 `LIMIT offset, size` 在大偏移量下性能差的问题。核心思路是用**游标分页**（基于索引有序字段）替代传统偏移分页，利用索引的有序性快速定位数据，避免扫描大量无效数据。同时可以配合覆盖索引减少回表操作，或在业务层限制最大页码，避免极端场景。

**大表优化**：

大表优化的核心是「拆 + 减」：

1. **减**：通过字段瘦身、索引优化、覆盖索引减少单表数据量和 IO 操作；
2. **拆**：通过分区表、分库分表（垂直 / 水平）、读写分离分散压力；
3. **归档**：定期清理冷数据，维持活跃数据量。
    
    不同业务场景优先选择不同方案，比如时间序列数据优先用分区表，用户数据优先用水平分表。

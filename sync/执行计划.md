# 附录 A 执行计划

## PostgreSQL 相关说明

本节所讲方法适用于 **PostgreSQL 8.0 及以上版本**。

### 查看执行计划

在 SQL 语句前加上`EXPLAIN`命令，即可获取 PostgreSQL 执行计划。但存在一处重要限制：**带有绑定参数**（如`$1`、`$2`）的 SQL 无法直接用该方式解析，必须先预编译语句：

sql

```
PREPARE stmt(int) AS SELECT $1;
```

注：PostgreSQL 使用`$数字`作为绑定参数标识，数据库中间件通常会做封装，让你可以使用 SQL 标准的问号占位符。

执行预编译语句并查看执行计划写法：

sql

```
EXPLAIN EXECUTE stmt(1);
```

**版本差异**

1. PostgreSQL 9.1 及更早版本：预编译时就已生成执行计划，执行时传入的实际参数值无法影响计划；
2. PostgreSQL 9.2 及之后版本：执行计划推迟到语句真正运行时生成，能够结合绑定参数实际值优化。

**提示**

无绑定参数的语句可直接解析：

sql

```
EXPLAIN SELECT 1;
```

这类查询在生成计划时，优化器始终能识别字面常量值。若使用 9.1 及更早版本且业务中大量使用绑定参数，排查问题时也必须用带参数的预编译方式解析，才能拿到和线上一致的执行计划。

执行计划输出示例：

plaintext

```
QUERY PLAN
------------------------------------------
Result (cost=0.00..0.01 rows=1 width=0)
```

输出内容和本书中 Oracle 执行计划信息维度一致：包含操作名`Result`、执行成本、预估行数、单行数据宽度。

PostgreSQL 会展示两组成本数值：第一个是**启动成本**，第二个是**取出全部数据的总成本**；Oracle 执行计划仅展示后者。

`EXPLAIN`支持两个常用参数：

1. `VERBOSE`：输出完整表名等额外冗余信息，日常排查基本无用；
2. `ANALYZE`：使用频率极高，但**不建议养成随意使用的习惯**—— 该参数会**真实执行 SQL**。
    
    - 执行`SELECT`通常无风险；
    - 执行`INSERT/UPDATE/DELETE`会直接修改业务数据。
    

安全用法：包裹在事务内执行，查看完计划后回滚事务

sql

```
BEGIN;
EXPLAIN ANALYZE EXECUTE stmt(1);
ROLLBACK;
```

开启`ANALYZE`后，计划中会附带真实执行耗时、实际扫描行数，可用来精准排查**行数预估不准**的问题。

**警告**

`EXPLAIN ANALYZE`会实打实执行目标语句，包含增删改操作。

执行计划里只有**行数**同时展示预估值与实际值，可快速定位基数预估错误问题。

预编译语句使用完毕后务必释放：

sql

```
DEALLOCATE stmt;
```

### 执行计划常见操作

#### 索引与表访问方式

1. **Seq Scan 顺序扫描**
    
    遍历磁盘上存储的整张数据表，等价于 Oracle 的`全表扫描(TABLE ACCESS FULL)`。
    
2. **Index Scan 索引扫描**
    
    遍历 B 树索引叶子节点，匹配符合条件索引条目后回表取数，等价于 Oracle 中`索引范围扫描 + 通过ROWID回表查询`组合逻辑，详见第一章《索引底层结构》。
    
    索引过滤条件不合理，是索引扫描出现性能瓶颈的常见原因，下文会讲解区分方法。
    
3. **Index Only Scan 仅索引扫描（PostgreSQL9.2 起支持）**
    
    遍历 B 树索引即可拿到查询所需全部字段，**无需回表**；唯一例外：需要校验 MVCC 多版本可见性信息时仍需访问表数据，详见前文《仅索引扫描》章节。
    
4. **Bitmap Index Scan / Bitmap Heap Scan / Recheck Cond**
    
    引用 Tom Lane 官方释义：
    
    普通索引扫描是从索引取出一条行指针，立刻回表读取该行数据；
    
    位图扫描会一次性取出所有匹配行指针，在内存中通过位图结构排序，再按照数据物理存储顺序批量访问数据表行数据。
    

#### 关联查询操作

数据库多表关联默认**两两依次执行**：先关联两张表，再将中间结果集与下一张表继续关联；此处的 “表” 也可指代查询生成的中间结果集。

1. **Nested Loops 嵌套循环连接**
    
    以一张表结果为驱动表，逐行遍历去另一张表匹配数据，详见对应章节。
2. **Hash Join 哈希连接**
    
    将其中一张表匹配数据构建哈希表，另一张表数据逐行做哈希匹配查询。
3. **Merge Join 合并排序连接**
    
    要求两张关联数据源均已提前排序，像拉链合并有序数据一样完成关联。

#### 排序与分组操作

1. **Sort / Sort Key**
    
    根据指定字段完成结果集排序，需开辟内存存放中间数据，**非流水线执行**。
2. **GroupAggregate 有序分组聚合**
    
    依托已排序的数据完成分组统计，无需缓存全量数据，**流水线执行**。
3. **HashAggregate 哈希分组聚合**
    
    借助临时哈希表完成分组，无需数据提前排序，占用大量内存存储中间结果，**非流水线执行**，输出结果无序。

#### 前 N 行查询相关

1. **Limit**
    
    读取到指定行数后直接终止后续执行，依托底层执行模式决定整体效率；若底层是排序这类非流水线操作，即便加 Limit 依然性能较差。
2. **WindowAgg**
    
    标识语句使用窗口函数，**注意**：PostgreSQL 使用窗口函数时，无法实现流水线式前 N 行终止查询优化。

### 区分访问条件与索引过滤条件

PostgreSQL 将`WHERE`过滤条件分为三类：

1. **访问条件（Index Cond 索引检索条件）**
    
    用来划定索引叶子节点遍历的起止范围，缩小索引扫描区间。
2. **索引内过滤条件（Index Cond）**
    
    仅在索引遍历过程中做二次筛选，**无法缩小索引扫描范围**，不参与划定遍历起止边界。
3. **表级过滤条件（Filter）**
    
    过滤字段不在索引内，必须先回表读取整行数据之后，才能完成条件判断。

**重点**

PostgreSQL 执行计划不会主动区分访问条件和索引内过滤条件，二者统一标注为`Index Cond`，只能对照索引定义手动区分；

计划中标注为`Filter`的条件，**一律属于表级过滤**，哪怕出现在索引扫描流程中。

#### 实战示例

建表与基础索引：

sql

```
CREATE TABLE scale_data (
section NUMERIC NOT NULL,
id1 NUMERIC NOT NULL,
id2 NUMERIC NOT NULL
);
CREATE INDEX scale_data_key ON scale_data(section, id1);
```

查询语句：通过`section`走索引，同时过滤非索引字段`id2`

sql

```
PREPARE stmt(int) AS SELECT count(*)
FROM scale_data
WHERE section = 1
AND id2 = $1;

EXPLAIN EXECUTE stmt(1);
```

执行计划节选：

plaintext

```
Aggregate (cost=529346.31..529346.32 rows=1 width=0)
Output: count(*)
-> Index Scan using scale_data_key on scale_data
(cost=0.00..529338.83 rows=2989 width=0)
Index Cond: (scale_data.section = 1::numeric)
Filter: (scale_data.id2 = ($1)::numeric)
```

可以清晰看到：`id2`字段条件被标记为`Filter`表级过滤，因为该字段不在索引中；PostgreSQL 的索引扫描流程内置了回表逻辑，等同于把 Oracle 的`ROWID回表`步骤隐藏在了索引扫描操作内。

**核心结论**

PostgreSQL 执行计划里的`Filter`条件，无论搭配哪种索引扫描，都代表**表级别过滤**。

#### 调整索引后效果

新建包含`id2`的联合索引：

sql

```
CREATE INDEX scale_slow
ON scale_data (section, id1, id2);
```

再次执行相同查询，执行计划不再出现`Filter`，所有条件统一显示为`Index Cond`：

plaintext

```
Aggregate (cost=14215.98..14215.99 rows=1 width=0)
Output: count(*)
-> Index Scan using scale_slow on scale_data
(cost=0.00..14208.51 rows=2989 width=0)
Index Cond: (section = 1::numeric AND id2 = ($1)::numeric)
```

但此时`id2`依旧**无法缩小索引扫描范围**，因为索引字段顺序为`section,id1,id2`；数据库会先扫描所有`section=1`的整条索引区间，再在区间内逐行匹配`id2`条件。

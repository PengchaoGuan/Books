# 1. Introduction 
# 1.1 Data Organization
# 数据库（Databases）

PostgreSQL 是**数据库管理系统（database management systems）**类程序。该程序运行时，我们称其为**PostgreSQL 服务端（PostgreSQL server）**或**实例（instance）**。

由 PostgreSQL 管理的数据统一存放于**数据库（database）**中。单个 PostgreSQL 实例可同时管理多个数据库，这些数据库的集合统称为**数据库集群（database cluster）**。

使用数据库集群前，必须先完成**初始化（initialize）**操作以创建集群。存放集群所有相关文件的目录，通常依据指向该目录的环境变量命名为**数据目录（data directory）**。

通过预编译软件包安装部署时，各类工具所需参数会被显式配置，从而在原生 PostgreSQL 机制之上增设一层抽象逻辑。此种部署模式下，数据库服务会以操作系统服务形式运行，使用者几乎不会直接接触到数据目录环境变量，但该专业术语已形成通用行业叫法，本书后续将统一沿用。

集群初始化完成后，数据目录内会自动生成三个系统默认数据库：

1. **template0**：用于逻辑备份数据恢复、创建自定义字符集编码数据库等场景，**严禁人为修改**。
2. **template1**：作为集群内用户新建数据库的**模板数据库（template database）**。
3. **postgres**：通用默认业务数据库，可自由按需使用。

## 1.1 数据层级架构（Data Organization）

### 系统目录（System Catalog）

集群内所有对象（数据表、索引、数据类型、函数等）的**元数据（Metadata）**，均存储在归属于 ** 系统目录（system catalog）** 的数据表中。

每个独立数据库都拥有专属的系统目录表与视图，用于记录本库内部对象信息；同时存在部分**集群全局共享系统目录表**，这类表不属于任意单个业务数据库（技术层面依托 ID 为 0 的虚拟空数据库承载），所有数据库均可访问查询。

使用者可通过标准**SQL**语句查询系统目录，系统目录的所有数据修改操作均由**DDL**语句完成；`psql`客户端也内置专属命令，可快速查看系统目录内容。

所有系统目录表名均以`pg_`为前缀，例如`pg_database`；字段名通常使用数据表名对应的三位字符作为前缀，例如`datname`。

系统目录表中充当主键的字段统一命名为**oid（object identifier，对象标识符）**，字段类型同样为 oid，本质是**无符号整型**。

oid 对象标识符的实现逻辑与序列近似，但在 PostgreSQL 中出现更早。其核心特性为：全局唯一 oid 由统一计数器生成，可在系统目录内多张数据表中通用。当计数器数值达到最大值后会自动重置；为保障单表内 oid 唯一性，分配新 oid 时会通过唯一索引校验，若该数值已在当前表内存在，则自增重试直至获取空闲数值。

### 模式（Schemas）

**模式（schema）**是用于收纳数据库全部对象的**命名空间（namespace）**。除用户自定义模式外，PostgreSQL 预设多款内置模式：

- **public**：未手动指定模式时，用户业务对象默认存放的模式。
- **pg_catalog**：专门存放系统目录表。
- **information_schema**：遵循**SQL**标准定义，提供系统目录的标准化查询视图。
- **pg_toast**：用于存储大字段数据相关附属对象。
- **pg_temp**：存放临时数据表。不同用户创建的临时表会分属`pg_temp_数字`格式独立模式，但使用者统一通过`pg_temp`别名访问自身临时对象。

单个模式严格隶属于某一个数据库，所有数据库对象都必须归属指定模式。

访问数据库对象时若未显式指定模式名，PostgreSQL 会依据 ** 搜索路径（search path）** 参数配置，依次匹配路径内可用模式。搜索路径默认自动补齐`pg_catalog`与按需补齐`pg_temp`，因此不同模式下允许创建同名数据库对象。

### 表空间（Tablespaces）

数据库与模式定义的是数据库对象**逻辑分布结构**，而**表空间（tablespace）**用于定义数据**物理存储布局**。表空间本质就是文件系统内的实体目录。

使用者可借助表空间拆分存储层级：归档冷数据挂载低速磁盘存储，高频读写热数据挂载高速磁盘存储。

单个表空间可被多个数据库共用，单个数据库也能将数据分散存入多个不同表空间，由此实现**逻辑架构与物理存储相互解耦**。

每个数据库都配有**默认表空间**，未手动指定存储位置的数据库对象，都会默认创建至该表空间内，数据库专属系统目录对象也统一存放于此。

集群初始化时会自动创建两大核心表空间：

1. **pg_default**：存放于`数据目录/base`路径，若无手动指定，所有对象默认使用该表空间。
2. **pg_global**：存放于`数据目录/global`路径，专门存储集群全局共享的系统目录对象。

创建自定义表空间时可指定任意实体目录，PostgreSQL 会在`数据目录/pg_tblspc`路径下为其创建符号链接。PostgreSQL 内部所有文件路径均基于数据目录做相对寻址，因此停止服务后可直接迁移整个数据目录。

### 关系对象（Relations）

数据表、索引作为数据库核心对象，具备统一共性：二者均由 ** 数据行（row）** 构成。数据表由数据行组成易于理解，B 树索引节点同样遵循该结构，节点内存储索引值以及指向其他索引节点、数据表数据行的引用信息。

序列（可理解为单行数据表）、物化视图（可固化查询结果的特殊数据表）也遵循该结构；普通视图不存储实体数据，但逻辑定义与数据表高度相似。

在 PostgreSQL 体系中，上述所有同类对象被统一统称为**关系（relation）**。

该命名存在一定歧义，极易混淆数据库数据表与关系型理论中的标准关系定义，这一命名沿袭了项目学术设计理念，也是创始人迈克尔・斯通布雷克将一切数据结构抽象为关系的设计思路。其还曾提出**有序关系**概念，代指依靠索引划定数据行排序规则的数据表。

记录关系对象信息的系统目录表最初命名为`pg_relation`，后顺应面向对象设计理念更名为如今通用的`pg_class`，但其字段命名依旧保留原有前缀风格。

### 数据文件与分支文件（Files and Forks）

单个关系对象的所有数据信息，会拆分存储至多个 ** 分支文件（fork）** 中，不同分支文件承载不同类型数据。

分支文件初始以单个实体文件存在，文件名称由数值型 oid 构成，可搭配对应后缀区分分支类型。

当单个分支文件体积达到预设阈值后，系统会自动新建同类型分支文件（也称数据段文件 segment），并在文件名末尾追加段编号。该文件大小限制为历史兼容老旧文件系统所设定，可在编译 PostgreSQL 源码时通过编译参数自定义调整。

由此可知，一个逻辑关系对象会在磁盘上映射为多个物理文件；即便是无索引的简易数据表，也至少会包含三类必备分支文件。

除`pg_global`表空间外，其余所有表空间目录下，都会按数据库 ID 划分独立子目录；同一表空间、同一数据库下的所有对象文件，统一存放至对应子目录内。运维需注意：单目录下文件数量过多，会引发文件系统读写性能衰减。

#### 标准分支文件分类

1. **主分支（main fork）**
    
    存储实体核心数据，数据表存储数据行、索引存储索引行，除无实体数据的普通视图外，所有关系对象均配备主分支文件。
    
    主分支文件直接以 oid 命名，oid 数值存储于`pg_class`表的`relfilenode`字段中。
    
2. **初始化分支（initialization fork）**
    
    仅 ** 非日志表（unlogged table）** 及其索引拥有该分支。非日志表的各类数据操作不会写入预写日志，执行效率更高，但数据库故障重启恢复时，系统会清空该类对象所有分支文件，并以初始化分支覆盖主分支完成重置，无法保障故障后数据一致性。初始化分支文件命名规则为主分支名加`_init`后缀。
    
3. **空闲空间映射分支（free space map，FSM）**
    
    实时记录数据页内空闲存储空间，数据表执行清理（VACUUM）后空闲空间增多，写入新数据行后空闲空间减少。该分支核心作用是快速检索可容纳新数据的空闲数据页。
    
    空闲空间映射文件统一添加`_fsm`后缀，初始不会自动创建，执行数据表清理操作后生成。空闲空间映射采用树形结构组织，空表状态下也会占用最少三页存储空间。
    
    数据表与索引均配备空闲空间映射分支，但索引仅统计完全空闲、可复用的空数据页，无法随意向索引数据页内插入数据。
    
4. **可见性映射分支（visibility map，VM）**
    
    快速判定数据页是否需要执行清理或数据冻结操作，为每张数据表数据页配置两位状态标识位：
    

- 第一位：标记页面内所有数据行均为最新有效版本，清理进程可直接跳过该页面，同时支持走仅索引扫描优化查询。
- 第二位：标记页面内所有数据行均已完成数据冻结。
    
    可见性映射文件统一添加`_vm`后缀，体积通常为各类分支文件中最小，**仅数据表配备该分支，索引无可见性映射**。

### 数据页（Pages）

为适配磁盘读写 IO 操作，所有分支文件会被统一逻辑划分为**数据页（page/block）**，数据页是数据库最小读写数据单元，PostgreSQL 绝大多数底层算法均围绕数据页设计优化。

默认标准数据页大小为**8KB**，可在源码编译阶段自定义调整上限，服务编译部署完成后无法二次修改，同一实例内所有表空间必须沿用统一数据页尺寸。

数据库服务对所有分支文件的读写处理逻辑完全一致：数据页优先加载至 ** 缓冲区缓存（buffer cache）** 供进程读写编辑，后续再按需刷写回磁盘持久化。

### 超大字段存储机制（TOAST）

PostgreSQL 强制约束：**单行数据必须完整存放于单个数据页内，禁止跨页拆分存储**。为满足超长字段、超大字段的存储需求，数据库内置**超大属性存储技术（TOAST，The Oversized Attributes Storage Technique）**。

TOAST 提供三类核心处理策略：将超长字段拆分存入专属附属数据表、对超长字段执行数据压缩、压缩 + 拆分组合使用。

若数据表包含潜在超长字段类型（numeric、text、json 等），系统会自动为该表创建专属 TOAST 附属表，即便该字段实际从未存入超长数据也会默认创建。

索引仅支持借助 TOAST 完成字段压缩，不支持拆分存储超长索引键值，索引键长度上限受字段存储策略与操作符类约束。

字段默认 TOAST 存储策略由字段数据类型决定，可通过`psql`中`\d+`命令或查询系统目录查看，四类策略释义：

1. **plain**：不启用 TOAST 机制，适用于整型等固定短长度数据类型。
2. **main**：优先压缩字段数据，压缩后仍超限才拆分存入 TOAST 表。
3. **external**：不执行压缩，直接将超长原始数据拆分存入 TOAST 表。
4. **extended**：默认通用策略，支持压缩存储 + 拆分存入 TOAST 表双模式。

TOAST 执行核心规则：数据库优先保证单个数据页内至少存放四行完整数据；剔除数据页头部占用空间后，若单行数据体积超出单页四分之一容量，便触发 TOAST 机制优化存储，直至单行数据体积符合容量阈值。

执行优先级：优先处理 extended、external 策略超长字段→仍超限则批量迁移该类字段→再压缩 main 策略字段→最后迁移压缩失败的 main 策略字段。

可通过数据表存储参数`toast_tuple_target`自定义容量阈值。

业务场景可手动修改字段存储策略：例如存储不可压缩的图片二进制数据时，直接指定 external 策略，规避无效压缩损耗性能。

所有 TOAST 附属表统一存放于`pg_toast`内置模式，该模式默认不在搜索路径内，日常查询默认隐藏；临时数据表对应的 TOAST 表则存放于`pg_toast_数字`专属临时模式。

TOAST 附属表固定包含`chunk_id`（分片 ID）、`chunk_seq`（分片序号）、`chunk_data`（分片数据）三个字段，并自动建立联合主键索引用于快速检索分片数据；TOAST 分片数据统一使用 plain 策略，不做二次嵌套 TOAST 处理。

查询数据时，PostgreSQL 会自动拼接还原 TOAST 拆分的超长字段，对上层业务完全透明；若查询语句未涉及超长字段，数据库不会读取 TOAST 附属表数据，这也是生产环境禁止滥用`*`全字段查询的核心原因。

超长字段的压缩、拆分、数据还原均会消耗系统资源，因此非必要场景不建议在 PostgreSQL 中存储超大体积文件类数据；更优方案为文件存入本地文件系统，数据库仅记录文件路径，缺点是无法依托数据库保障文件数据事务一致性。

## 1.2 进程与内存（Processes and Memory）

完整 PostgreSQL 服务实例由多个协同工作的进程组成。

服务启动首个拉起的进程为`postgres`进程，行业内统称**主守护进程（postmaster）**。该进程通过类 Unix 系统`fork`系统调用创建所有子进程，并统一管控所有子进程状态；一旦子进程异常宕机，主守护进程会自动重启对应进程，若存在共享数据损坏风险，则直接重启整个数据库服务。

该多进程架构自项目初期沿用至今，业内长期存在替换为多线程架构的讨论。现有多进程架构存在明显短板：共享内存静态分配，无法在线调整缓冲区缓存等内存组件大小；并行运算算法实现难度大、执行效率偏低；会话与进程强绑定耦合。

多线程架构虽能解决上述问题，但存在隔离性适配、操作系统兼容、资源管控等诸多难题，且整体替换需要大规模重构底层源码、耗费数年开发周期，因此现阶段社区保持保守态度，短期内无架构替换计划。

数据库日常运行依赖各类**后台进程（background processes）**，核心常驻 / 功能后台进程如下：

- **startup**：数据库故障后执行数据恢复操作。
- **autovacuum**：自动清理数据表、索引内过期无效数据。
- **wal writer**：将预写日志持久化写入磁盘。
- **checkpointer**：执行数据库检查点操作。
- **writer**：将内存中脏数据页刷写至磁盘。
- **stats collector**：采集数据库实例全维度运行统计信息。
- **wal sender**：主库向从库同步传输预写日志。
- **wal receiver**：从库接收主库同步的预写日志。

部分后台进程完成指定任务后自动退出，部分进程长期后台常驻运行，还有部分进程支持手动关闭启停；所有进程运行状态均可通过对应配置参数精细化管控，熟练掌握底层运行逻辑才能完成服务最优初始化配置，后续再依托监控数据完成参数精细化调优。

主守护进程负责分配**共享内存（shared memory）**，集群内所有进程均可访问读写共享内存空间。

磁盘读写速度远低于内存读写速度，因此 PostgreSQL 全面启用缓存机制：共享内存划分专属空间缓存高频访问数据页，减少重复磁盘 IO 开销；修改后的数据页不会立即刷盘，延迟批量持久化写入磁盘。

**缓冲区缓存（buffer cache）**是共享内存最核心组成部分，共享内存内还包含各类加速磁盘访问的辅助缓存区域。同时操作系统自身也具备文件缓存机制，PostgreSQL 几乎不会绕过系统缓存执行直接 IO，最终形成**双层缓存**架构。

遭遇断电、系统崩溃等故障时，内存内所有缓存数据全部丢失，磁盘残留的数据页写入时间杂乱无序。为保障故障后数据可恢复一致性，PostgreSQL 全程写入**预写日志（WAL）**，故障恢复阶段可依托预写日志重放缺失操作，还原完整一致数据状态。

## 1.3 客户端与客户端服务端通信协议（Clients and the Client-Server Protocol）

监听客户端连接请求同样是主守护进程的核心职责。每当有新客户端发起连接，主守护进程都会单独创建专属**后端服务进程（backend process）**，客户端与该后端进程建立专属连接并开启会话，会话持续至客户端主动断开或连接异常中断。

一客户端对应一后端进程的架构存在明显性能瓶颈：

1. 每个后端进程都需要独立内存，用于缓存系统目录、预处理语句、查询中间结果等，并发连接数越高，内存资源占用量越大。
2. 短连接高频场景下，频繁创建销毁进程、初始化本地缓存的资源开销极高。
3. 进程数量越多，进程遍历管理耗时越长，高频遍历操作进一步拉低整体性能。

随着客户端并发量上升，数据库整体服务性能会持续衰减。

行业通用解决方案为**连接池（connection pooling）**，通过连接池限制后端进程最大创建数量。PostgreSQL 原生未内置连接池功能，需借助第三方组件实现，例如应用服务器内置连接池、独立中间件`PgBouncer`、`Odyssey`等。连接池模式下，单个后端进程可轮流处理多个不同客户端事务，该模式对业务开发存在约束：仅可使用事务级局部资源，不可依赖全局会话级资源。

客户端与服务端通信必须遵循统一**通信协议**，主流基于标准`libpq`库实现，同时也存在各类自定义协议实现版本。该通信协议核心作用是实现客户端连接鉴权、下发 SQL 查询语句、回传执行结果。

所有数据库连接都必须指定目标数据库与登录角色（用户）；即便单个集群管理多个数据库，应用程序访问不同数据库也必须建立独立连接。连接建立阶段同步完成身份认证，后端进程校验用户身份、连接权限、目标数据库访问权限。

客户端以文本字符串形式向后端进程传递**SQL**语句，后端进程依次完成语句语法解析、逻辑优化、执行计划生成、语句执行，最终将执行结果回传给客户端。

# 2. Isolation
# 2.1 一致性（Consistency）

关系型数据库的核心特性是能够保障**数据一致性（data consistency）**，也就是**数据正确性（data correctness）**。

众所周知，我们可以在数据库层面定义**完整性约束（integrity constraints）**，数据库系统会严格保证这类约束不会被违背，以此确保 ** 数据完整性（data integrity）** 不受破坏。

倘若所有业务所需的约束规则都能够在数据库层面完成定义，那么数据一致性自然就能得到保障。但现实中部分业务规则逻辑过于复杂，例如规则同时涉及多张数据表；即便某类约束可以用数据库语法定义，若出于某些原因未做定义，也不代表业务层面可以随意违背该规则。

由此可见，**数据一致性的约束标准要严于数据完整性**，但数据库系统本身无法感知业务层面定义的 “一致性” 具体内涵。一旦应用程序违背了业务一致性规则，却没有触犯数据库完整性约束，数据库完全无法察觉。因此，**数据一致性的判定标准必须由应用程序制定**，开发人员只能依托业务代码编写的正确性，来保障数据不出错。

既然业务代码执行的操作序列本身逻辑无误，那数据库系统又在其中起到什么作用？

首先，一套逻辑正确的操作序列，在执行过程中**临时打破数据一致性**是十分正常且合理的现象。

举一个经典易懂的例子：账户之间进行资金转账。

一条一致性规则可以定义为：资金转账操作前后，涉及转账的所有账户总余额必须保持不变。

这类规则很难通过数据库完整性约束直接实现，我们默认该规则由应用层管控，数据库对此无感知。

一次转账包含两步操作：第一步从转出账户扣除指定金额，第二步将同等金额转入目标账户。

第一步执行完成后，数据一致性被临时打破，第二步执行完毕后，数据一致性恢复正常。

若第一步执行成功、第二步因异常执行失败，数据一致性就会被永久性破坏。这类问题在应用层排查与处理成本极高，所幸无需在业务层兜底：只要告知数据库，这两步操作属于**不可分割的整体**，也就是**事务（transaction）**，数据库便可从底层彻底解决该问题。

除此之外，事务还存在更为隐蔽的问题：单条事务自身逻辑完全正确，但 ** 多事务并发执行（run in parallel）** 时，执行结果会出现异常。根源在于不同事务的操作指令会相互交错穿插执行。

如果数据库严格串行执行事务，即执行完一个事务所有操作后再执行下一个，自然不会出现此类问题，但串行执行的性能会极低。

真正意义上的事务并行执行，需要多核处理器、磁盘阵列等硬件设施支撑；而采用分时模式依次处理指令的服务器，同样会出现事务交错执行的问题。为便于统一归类，以上两种运行场景统称为**并发执行（concurrent execution）**。

逻辑无误的事务在并发运行时产生的异常结果，统称为**并发异常（concurrency anomalies）**。

举一个基础示例：应用程序读取数据库数据时，最低要求是**不能读取到其他事务未提交的修改数据**。一旦读取到这类数据，若源事务后续执行**回滚（rollback）**操作，程序就会读到数据库从未真实存在过的临时数据，该异常被称为**脏读（dirty read）**。除此之外还存在更多逻辑更复杂的并发异常。

事务并发运行时，数据库必须保证最终执行结果，等价于这些事务某一种合法串行执行顺序所产出的结果。简言之，数据库需要实现**事务隔离（isolate transactions）**，以此规避各类并发异常。

总而言之，**事务（transaction）**是一组数据库操作的集合：在满足**原子性（atomicity）**—— 整套操作完整执行、不可拆分，以及**隔离性（isolation）**—— 不受其他事务干扰的前提下，能将数据库从一种合法一致状态切换至另一种合法一致状态，这一定义涵盖了 ACID 特性中前三项核心要求。三者逻辑深度绑定，需要结合讲解。

除此之外，** 持久性（durability）** 也无法单独剥离讨论：数据库发生宕机故障后，系统内可能残留未提交事务产生的临时数据，必须通过机制清理恢复，才能重新保障数据一致性。

# 2.2 SQL 标准中的隔离级别与并发异常

数据库系统无法识别业务一致性规则，但可以依托事务边界，协助应用程序维护数据一致性。

但**完全事务隔离**实现难度极大，还会严重拖累数据库运行性能。因此绝大多数线上业务系统都会采用**宽松隔离级别（weaker isolation levels）**：仅拦截部分并发异常，无法规避全部异常。

这也就意味着，维护数据一致性的部分工作需要交由应用程序完成。这也充分说明，开发人员必须清晰掌握系统所用隔离级别、该级别具备的保障能力与存在的短板，以此编写适配对应隔离级别、逻辑严谨无误的业务代码。

## SQL 标准定义四大事务隔离级别

隔离级别的划分依据，是事务并发执行过程中允许出现、或禁止出现的并发异常类型，因此讲解隔离级别必须先明确各类并发异常。

需要注意：SQL 事务隔离标准属于理论规范，能够指导实际开发，但数据库落地实现和理论标准存在诸多差异，下文案例均为理论示例。本章所有银行账户事务案例仅用于原理讲解，和真实银行业务流程无关。

数据库理论体系的成型时间晚于 SQL 隔离标准落地时间，业界实际工程实践更是远超前于理论定义。

### 1. 丢失更新（Lost Update）

**异常定义**：两个事务先后读取同一数据表行数据，其中一个事务先行更新该行数据，后续另一事务再次更新该行数据时，完全忽略前一个事务已经完成的修改，最终造成数据变更结果被覆盖丢失。

**场景示例**：两个事务同时为同一个银行账户增加等额余额，两个事务读取到相同的初始余额，先后执行累加更新，最终仅生效一次累加操作，造成用户资金损失。

**标准约束**：SQL 标准规定，**所有隔离级别都禁止出现丢失更新异常**。

### 2. 脏读（Dirty Reads） & 读未提交（Read Uncommitted）

**脏读定义**：一个事务读取到其他事务**尚未提交**的数据修改结果。

**场景示例**：事务 A 向空账户转账，但未执行提交操作；事务 B 读取到这笔未提交的转账金额，并允许用户取款。若后续事务 A 中断执行并回滚修改，账户恢复为空，就会出现账面取款成功、实际无资金的逻辑漏洞。

**标准约束**：** 读未提交（Read Uncommitted）** 隔离级别允许脏读异常发生。

### 3. 不可重复读（Non-Repeatable Reads） & 读已提交（Read Committed）

**不可重复读定义**：同一事务内，**两次读取同一行数据**期间，其他事务完成该行数据的更新 / 删除操作并提交修改，导致当前事务两次读取结果不一致。

**场景示例**：业务规则禁止银行账户出现负余额。事务 A 准备扣除账户资金，首次查询余额判定扣款可行；在此期间其他事务清空该账户余额并提交，事务 A 再次校验余额时发现余额不足，但扣款逻辑已判定完成，最终引发账户透支问题。

**标准约束**：读未提交、读已提交两大隔离级别均允许出现不可重复读异常。

### 4. 幻读（Phantom Reads） & 可重复读（Repeatable Read）

**幻读定义**：同一事务内，先后执行两条**条件完全一致**的范围查询语句；两次查询间隙，其他事务新增满足查询条件的数据行并提交，导致当前事务两次查询返回的数据集合数量、内容不一致。

**场景示例**：业务规则限制单个用户最多开立三个银行账户。事务 A 准备新建账户，查询当前用户已有账户数量，判定可新建账户；在此期间其他事务为该用户新增账户并提交，事务 A 继续执行新建账户操作，最终超出账户数量限制。

**标准约束**：读未提交、读已提交、可重复读三大隔离级别均允许幻读异常。

### 5. 串行化（Serializable）：无任何并发异常

串行化是 SQL 标准中最高事务隔离级别，**禁止所有已知并发异常**。

该级别不仅拦截上述四类基础异常，还能规避更多未被标准定义的隐性并发异常。

业务开发人员使用串行化级别时，无需手动处理事务隔离带来的数据一致性问题：只要单个事务独立运行时代码逻辑无误，并发运行时也不会破坏数据一致性。

|隔离级别|丢失更新|脏读|不可重复读|幻读|其他隐性异常|
|---|---|---|---|---|---|
|读未提交|禁止|允许|允许|允许|允许|
|读已提交|禁止|禁止|允许|允许|允许|

### 隔离级别设计初衷溯源

SQL 标准仅定义上述几类基础并发异常的原因暂无权威定论，主流观点认为：标准制定初期数据库并发理论尚未完善，大量隐性异常未被发掘。

早期事务隔离机制均基于 ** 锁机制（lock）**设计，经典的**两段锁协议（Two-Phase Locking, 2PL）** 要求事务执行过程中锁定操作数据，事务结束后统一释放锁。

简单来说，事务持有锁的数量越多，和其他事务之间的隔离性越强，但数据库整体并发性能越差 —— 事务会因争抢数据锁陷入阻塞排队，无法并行执行。

业界普遍认为，SQL 标准四大隔离级别的划分，本质是实现该级别所需加锁数量的差异：

1. 仅对更新数据加写锁、不加读锁 → 读未提交，允许读取未提交临时数据；
2. 对更新数据同时加读锁与写锁 → 读已提交，禁止读取未提交数据，允许同事务内数据发生变更；
3. 对读写涉及的所有数据行加锁 → 可重复读，保障同事务重复读取结果一致；
4. 普通行锁存在天然短板：无法锁定尚未存在的数据行，因此无法彻底杜绝幻读。想要实现完全隔离，必须放弃行锁，改用 ** 谓词锁（predicate locks）** 锁定查询条件。
    
    谓词锁早在 System R 数据库研发阶段就被提出，但仅适用于逻辑简单的查询条件，至今没有主流数据库完整落地原生谓词锁机制。

# 2.3 PostgreSQL 数据库中的事务隔离级别

随着技术迭代，基于锁的传统事务管理协议，逐步被**快照隔离（Snapshot Isolation, SI）**协议取代。

快照隔离核心原理：每个事务运行时，都会获取某一固定时间点的**数据一致性快照（consistent snapshot）**，快照内仅包含快照生成前已成功提交的所有数据修改。

快照隔离最大限度减少锁资源占用：仅多事务同时修改同一行数据时才会触发行锁冲突；其余场景读写完全互不阻塞，**写操作不阻塞读操作，读操作不占用任何锁资源**。

PostgreSQL 采用 ** 多版本并发控制（Multiversion Concurrency Control, MVCC）** 实现快照隔离：数据库会为同一行数据保留多个历史版本，事务直接读取匹配自身快照时间点的数据版本，无需为规避脏数据主动终止事务。

## PostgreSQL 隔离级别特性（与 SQL 标准差异）

1. 底层机制天然禁止脏读，即便手动指定 ** 读未提交（Read Uncommitted）** 级别，实际运行逻辑和读已提交完全一致，日常开发无需使用读未提交；
2. PostgreSQL 可重复读级别，不仅禁止不可重复读，同时彻底杜绝幻读，但依旧无法实现理论层面的全事务隔离；
3. 读已提交级别依旧存在数据变更丢失类隐性并发异常。

表格

|隔离级别|丢失更新|脏读|不可重复读|幻读|其他隐性异常|
|---|---|---|---|---|---|
|读已提交|禁止|禁止|允许|允许|允许|
|可重复读|禁止|禁止|禁止|禁止|允许|

下文基于账户表完成实操演示，初始化 SQL 语句：

sql

```
CREATE TABLE accounts(
id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
client text,
amount numeric
);
INSERT INTO accounts VALUES
(1, 'alice', 1000.00), (2, 'bob', 100.00), (3, 'bob', 900.00);
```

## 一、读已提交（Read Committed）

PostgreSQL**默认事务隔离级别**。

1. **禁止脏读**：事务仅能读取已提交的正式数据，无法读取其他事务未提交的临时修改，事务仅能实时查看自身做出的未提交修改。
2. **允许不可重复读**：同一事务多次执行相同查询时，若间隙内其他事务提交数据修改，本次查询会直接读取最新已提交数据，前后查询结果不一致。

### 业务代码经典反面案例

在事务内先查询余额判定操作可行性，再执行金额修改：

sql

```
IF (SELECT amount FROM accounts WHERE id = 1) >= 1000 THEN
UPDATE accounts SET amount = amount- 1000 WHERE id = 1;
END IF;
```

判定逻辑和更新逻辑之间存在时间间隙，其他事务可随意修改账户数据，导致判定条件失效，属于典型开发反模式。

此类异常复现难度极高，线上故障排查难度极大。

### 规范优化方案

1. **声明式 SQL 替代过程式判断**：依托数据库 ** 检查约束（CHECK）** 兜底数据规则；

sql

```
ALTER TABLE accounts ADD CHECK amount >= 0;
```

2. **合并为单条 SQL 语句**：消除多条操作之间的时间空隙，杜绝数据中途变更；
3. **手动添加显式锁**：作为兜底方案，可添加**行排他锁**或**表锁**，但会彻底丧失 MVCC 并发读写的性能优势。

### 读倾斜（Read skew）隐性异常

读已提交级别下存在 SQL 标准未定义的**读倾斜**异常：同一事务批量查询多条关联数据时，不同数据行读取到不同时间节点的快照数据，最终汇总得出错误统计结果。

即便单条长耗时查询，整体会依托执行起始时间点生成统一快照，不会出现读倾斜；但事务内嵌套 ** 易变函数（VOLATILE）** 执行子查询时，依旧会触发读倾斜异常。

### 读已提交下的更新机制特性

多个事务并发修改同一行数据时，等待中的事务获取行锁后，会**重新读取最新行数据**再执行更新操作，该机制可以规避部分异常，但会诱发读倾斜；

若业务基于事务外部缓存的旧数据执行更新操作，依旧会触发**丢失更新**异常，数据库无法拦截此类业务层逻辑漏洞。

## 二、可重复读（Repeatable Read）

1. **核心特性**：彻底禁止不可重复读与幻读，同一事务全程依托事务启动时的统一数据快照执行查询，全程无法感知其他事务提交的新增、修改数据；
2. **冲突处理机制**：不再通过重读数据规避冲突，并发数据修改冲突会直接抛出 ** 序列化失败（serialization failure）** 异常并终止事务；
3. **适用场景**：多语句批量统计报表、批量数据查询等只读事务场景，体验极佳。

### 可重复读允许的两类核心隐性异常

1. **写倾斜（Write skew）**
    
    两条独立事务基于同一时间点的全局数据状态做出合法判定，分别修改不同分片数据，最终合并结果打破全局一致性规则。
    
    示例：允许单账户负余额、用户总余额非负，两个事务分别扣除同一用户不同账户资金，最终导致用户总余额为负数。
    
2. **只读事务异常（read-only transaction anomaly）**
    
    多事务交错提交执行时，只读事务观察到的数据状态排序错乱，和真实事务提交时序不符。
    

## 三、串行化（Serializable）

1. 最高隔离级别，彻底拦截所有已知、未知并发异常，包含可重复读无法规避的写倾斜、只读事务异常；
2. 底层依托快照隔离增强实现，通过读写依赖关系判定冲突，一旦检测到会触发序列化失败异常终止事务；
3. 支持**只读可延迟事务（READ ONLY DEFERRABLE）**：自动阻塞只读事务，直至运行环境无并发冲突后再执行，减少事务重试次数；
4. 存在短板：
    
    - 大量事务因冲突终止重试，大幅降低数据库整体吞吐量；
    - 存在误判终止安全事务的**假阳性冲突判定**，运行行为不可精准预判；
    - 不支持数据库只读副本执行串行化事务；
    - 必须全局统一使用该级别，混用其他隔离级别会自动降级为可重复读。

# 2.4 隔离级别选型原则

1. **读已提交（默认首选）**
    
    绝大多数线上业务通用选型，优势是不会主动终止任何事务，无需开发编写事务重试逻辑；
    
    缺点是并发异常种类多，要求开发人员熟知各类异常场景，尽量使用单条 SQL 完成业务逻辑，复杂场景必须手动加锁兜底，一致性相关故障排查难度大。
    
2. **可重复读**
    
    消除大部分主流并发数据异常，只读统计类业务适配性极强；
    
    读写混合业务使用时，必须编写事务重试逻辑处理序列化失败异常，增加业务代码开发复杂度。
    
3. **串行化**
    
    最大限度简化业务代码编写，无需考量任何并发数据异常；
    
    代价是事务终止重试开销大、系统吞吐量下降，存在诸多使用限制，仅适用于对数据一致性要求极高、并发量偏低的核心金融核心交易场景。

# 3. Pages and Tuples

## 3.1 数据页结构

每一个数据页都具备固定的内部布局，通常由以下几部分构成：

- 页头
- 项指针数组
- 空闲空间
- 数据项（行版本）
- 特殊空间

### 页头

页头处于最低地址位置，拥有固定大小。它存储着该页面的各类信息，例如页面校验和，以及页面内其余各个组成部分的尺寸大小。

借助`pageinspect`扩展工具，能够轻松查看这些尺寸信息。我们来看一张数据表的首个页面（页面编号从零开始）：

sql

```
CREATE EXTENSION pageinspect;
SELECT lower, upper, special, pagesize
FROM page_header(get_raw_page('accounts',0));
```

### 特殊空间

特殊空间位于数据页的另一端，占据页面最高地址区域。

部分索引会使用这片空间存放辅助信息，其余索引以及数据表页面的特殊空间大小均为零。

整体而言，索引页面的布局形式十分多样，其存储内容很大程度上取决于具体的索引类型。即便是同一种索引，也会包含不同类型的页面：例如 B 树索引中，存在结构特殊的元数据页面（0 号页面），还有结构与数据表页面高度相近的普通页面。

### 元组

数据行中存放着数据库内的实际存储数据，同时还附带一些附加信息，这些数据行就存放在特殊空间的前方位置。

对于数据表而言，我们实际处理的是行版本而非单纯的数据行，原因在于多版本并发控制机制会为同一行数据生成多个不同版本。索引并不会采用这种多版本机制，索引需要引用该行数据所有已存在的版本，并依靠可见性规则筛选出符合条件的有效版本。

数据表的行版本与索引条目，常常统一被称作元组。这一术语借鉴自关系理论，也是 PostgreSQL 承袭学术设计理念的又一处体现。

### 项指针

指向元组的指针数组，相当于数据页的内容目录，它紧邻页头之后进行存放。

索引条目需要以特定方式关联到具体的堆元组，PostgreSQL 为此采用六字节长度的元组标识符。每一个元组标识符由主分支的页面编号，以及该页面内对应某一行版本的引用标识共同组成。

从理论层面来讲，我们也可以依靠元组相对于页面起始位置的偏移量来定位元组。但这种方式一旦将页面内的元组进行位置挪动，所有相关引用都会失效，进而引发页面碎片等一系列问题。

正因如此，PostgreSQL 采用间接寻址方式：元组标识符对应着对应的指针序号，而指针记录着元组当前的偏移位置。即便元组在页面内部发生位置移动，它的元组标识符也不会发生改变，仅需修改同页面内对应的指针信息即可。

每一个指针固定占用四个字节，其中包含以下信息：

- 元组距离页面起始位置的偏移量
- 元组自身长度
- 用于标识元组状态的若干位标识信息

### 空闲空间

指针区域与元组区域之间会留存一部分空闲空间，这一状态信息会同步记录在空闲空间映射表当中。PostgreSQL 的数据页不会产生存储空间碎片，页面内所有可用的空闲空间始终整合为一整块连续空间。

## 3.2 行版本布局

每一个行版本都由头部信息和实际数据两部分组成。行头部包含多个字段，其中主要字段如下：

xmin 与 xmax 代表事务编号，用于区分同一行数据的不同版本；

信息掩码由一组信息位构成，用来定义行版本的各项属性；

ctid 是指向同一行数据下一个更新版本的指针；

空值位图是一组位数组，用来标记字段中可以存放空值的列。

由此可见，行头部占用的存储空间并不小，每一个元组的头部至少需要占用固定字节，而受空值位图以及为实现数据对齐而设置的必要填充位影响，实际占用空间往往会超出这个数值。在字段数量较少的精简数据表中，各类元数据占用的空间大小，甚至会超过实际业务数据占用的空间。

数据在磁盘上的存储布局，与内存中的数据存储形式完全一致。数据页以及页内的元组会原封不动地读取至缓冲区缓存中，不会进行任何格式转换。这也是不同操作系统平台之间，数据库数据文件无法直接兼容的原因。

造成数据文件不兼容的原因之一是字节序差异。例如 x86 架构采用小端字节序，z/Architecture 架构采用大端字节序，ARM 架构的字节序则可自主配置。

另一项原因是多数硬件架构要求数据按照机器字边界完成对齐存储。举个例子，在 64 位 x86 系统中，整型数据占用四个字节，需按照四字节字边界对齐存储，双精度浮点型数据占用八个字节，同样遵循该对齐规则；而在 32 位系统环境中，双精度浮点型数据则需要按照八字节字边界完成对齐。

数据对齐这一特性，使得元组占用空间大小会受数据表内字段排列顺序影响。多数场景下该影响可以忽略不计，但部分场景中，字段排序不合理会造成存储空间占用量大幅增加。

示例如下：

sql

```
CREATE TABLE padding(
b1 boolean,
i1 integer,
b2 boolean,
i2 integer
);
INSERT INTO padding VALUES (true,1,false,2);
SELECT lp_len FROM heap_page_items(get_raw_page('padding', 0));
```

上述语句中，我使用`pageinspect`扩展提供的`heap_page_items`函数，查看指针与元组的详细信息。

在 PostgreSQL 体系中，数据表常常被称作堆。这一晦涩的叫法，源于元组的空间分配方式与动态内存分配存在相似之处。二者虽有共通逻辑，但数据表的实际管理算法和内存管理算法截然不同。我们可以通俗理解这一命名：数据表的数据杂乱堆砌存放，和有序排列的索引形成鲜明对比。

上述示例中行数据占用固定字节空间，其中行头部占用指定字节，整型字段各占用四字节，布尔型字段各占用一字节，基础数据合计占用对应字节，剩余多余空间，均是为整型字段实现四字节对齐而产生的冗余填充空间。

重新调整数据表字段顺序后，存储空间的利用效率会得到显著提升：

sql

```
DROP TABLE padding;
CREATE TABLE padding(
i1 integer,
i2 integer,
b1 boolean,
b2 boolean
);
INSERT INTO padding VALUES (1,2,true,false);
SELECT lp_len FROM heap_page_items(get_raw_page('padding', 0));
```

还有一种实用的细微优化方式：将不可为空的定长字段放置在数据表字段列表的最前端。这类字段的页内偏移位置能够被系统缓存，进而提升数据访问效率。

## 3.3 元组相关操作

为区分同一行数据的不同版本，PostgreSQL 会为每一个行版本标注两个数值：xmin 与 xmax。这两个数值界定了每个行版本的有效存续时段，它们不依托实际时间，而是依靠持续递增的事务编号来实现判定。

当新增一行数据时，该行版本的 xmin 数值会被赋值为执行插入命令的事务编号。

当删除一行数据时，该行当前有效版本的 xmax 数值，会被赋值为执行删除命令的事务编号。

从抽象层面来看，更新命令可以拆解为两项独立操作：先删除原有数据，再插入全新数据。执行流程为：首先将当前行版本的 xmax 字段设置为执行更新操作的事务编号，随后生成该行数据的全新版本，新版本的 xmin 数值与旧版本的 xmax 数值保持一致。

接下来我们细致讲解各类元组操作的底层细节。

为完成下述实验，我们先创建一张包含两个字段的数据表，并在其中一个字段上建立索引：

sql

```
CREATE TABLE t(
id integer GENERATED ALWAYS AS IDENTITY,
s text
);
CREATE INDEX ON t(s);
```

### 插入操作

开启事务并插入一行数据：

sql

```
BEGIN;
INSERT INTO t(s) VALUES ('FOO');
-- 查询当前事务编号
SELECT pg_current_xact_id();
```

在 PostgreSQL 中，事务常用简写标识在 SQL 函数名与源代码中频繁出现，因此事务编号也存在多种简写叫法，后文会频繁接触到这类简写形式。

我们可以查看页面内部存储内容，`heap_page_items`函数能够获取全部所需信息，该函数会原样输出原始数据，因此展示格式不易阅读。

我们精简筛选信息，优化字段展示形式：

sql

```
SELECT '(0,'||lp||')' AS ctid,
CASE lp_flags
WHEN 0 THEN 'unused'
WHEN 1 THEN 'normal'
WHEN 2 THEN 'redirect to '||lp_off
WHEN 3 THEN 'dead'
END AS state,
t_xmin as xmin,
t_xmax as xmax,
(t_infomask & 256) > 0 AS xmin_committed,
(t_infomask & 512) > 0 AS xmin_aborted,
(t_infomask & 1024) > 0 AS xmax_committed,
(t_infomask & 2048) > 0 AS xmax_aborted
FROM heap_page_items(get_raw_page('t',0)) \gx
```

上述查询完成了几项处理：

1. 将 lp 指针格式转换为标准的元组标识符格式：(页面编号，指针序号)
2. 对 lp_flags 状态标识进行文字释义，此处状态为正常，代表该指针真实指向有效元组
3. 从众多信息位中筛选出两组核心标识位：xmin 已提交标识、xmin 已中止标识，用于判定 xmin 对应事务的最终状态；xmax 已提交标识、xmax 已中止标识，用于判定 xmax 对应事务的最终状态。

`pageinspect`扩展还提供`heap_tuple_infomask_flags`函数，可完整解析所有信息位含义，本文仅按需提取当前所需标识位，采用更简洁的形式展示。

回到本次实验中，插入命令已经在堆页面内新增一条指针，该指针指向目前页面内唯一的一条元组。

这条元组的 xmin 字段已赋值为当前执行事务的编号，由于该事务尚未结束提交，因此 xmin 对应的已提交、已中止标识位均未启用。

xmax 字段此时数值为 0，这是一个占位数值，代表当前这条元组未被执行删除操作，是该行数据的有效最新版本。所有事务都会忽略这个占位数值，原因是 xmax 已中止标识位处于启用状态。

尚未发生的事务却默认启用事务中止标识位，看似不合逻辑，但从事务隔离机制的角度而言二者并无区别：已中止的事务不会留存任何数据变更记录，等同于从未执行过。

后续我们会反复使用这类查询语句，因此将其封装为自定义函数，同时精简输出内容，整合事务编号与事务状态展示形式：

sql

```
CREATE FUNCTION heap_page(relname text, pageno integer)
RETURNS TABLE(ctid tid, state text, xmin text, xmax text)
AS $$
SELECT (pageno,lp)::text::tid AS ctid,
CASE lp_flags
WHEN 0 THEN 'unused'
WHEN 1 THEN 'normal'
WHEN 2 THEN 'redirect to '||lp_off
WHEN 3 THEN 'dead'
END AS state,
t_xmin || CASE
WHEN (t_infomask & 256) > 0 THEN ' c'
WHEN (t_infomask & 512) > 0 THEN ' a'
ELSE ''
END AS xmin,
t_xmax || CASE
WHEN (t_infomask & 1024) > 0 THEN ' c'
WHEN (t_infomask & 2048) > 0 THEN ' a'
ELSE ''
END AS xmax
FROM heap_page_items(get_raw_page(relname,pageno))
ORDER BY lp;
$$ LANGUAGE sql;
```

借助封装后的函数，能够清晰直观查看元组头部信息：

sql

```
SELECT * FROM heap_page('t',0);
```

我们也可以直接查询数据表，借助 xmin、xmax 伪列获取同类信息，只是展示内容相对简略：

sql

```
SELECT xmin, xmax, * FROM t;
```

### 事务提交

事务成功执行完毕后，系统需要固化该事务的最终执行状态，也就是标记该事务已完成提交。PostgreSQL 依靠提交日志这一专用结构实现该功能。

提交日志以独立文件形式存放于数据目录下的 pg_xact 文件夹中，并非以系统目录数据表的形式存储。

在旧版本数据库中，这类文件原本存放于 pg_clog 目录下，后续版本完成了目录更名调整。做出这一调整的原因是，不少不熟悉 PostgreSQL 运维逻辑的管理员，会误以为日志类文件属于无用文件，擅自删除该目录文件释放磁盘空间，进而引发数据库故障。

提交日志仅为了方便管理拆分为多个独立文件，系统通过共享内存缓冲区，以页面为单位读取调用这些日志文件。

和元组头部结构一致，提交日志中会为每一条事务记录分配两位状态标识位，分别对应事务已提交状态、事务已中止状态。

事务完成提交后，提交日志内会为该事务标记已提交标识位。当其他事务访问堆数据页面时，必须完成一项判定：该元组对应的 xmin 事务是否已经执行完毕。

1. 若事务仍处于运行状态：当前元组对其他事务不可见
    
    为判定事务是否处于活跃状态，PostgreSQL 会调用实例共享内存内的另一项结构 —— 进程数组。该结构记录着所有正在运行的后台进程，以及每个进程当前正在执行的活跃事务信息。
    
2. 若事务已执行完毕，再判定该事务最终状态为提交还是中止：若为中止状态，当前元组同样对其他事务不可见。
    

上述状态判定操作，都需要调取提交日志完成校验。即便近期访问频繁的提交日志页面会缓存至内存缓冲区，频繁执行这类校验依旧会产生不小的性能开销。

一旦事务最终状态完成判定，该状态信息会直接写入元组头部，具体写入 xmin 已提交标识位与 xmin 已中止标识位，这两类标识位也被统称为提示位。只要任意一类提示位完成赋值，就代表该事务状态已明确确定，后续访问该元组的事务，无需再次调取提交日志与进程数组进行重复校验。

为何执行数据插入的事务，不会在执行阶段直接完成提示位的赋值？核心原因在于事务执行阶段，无法预判自身最终会提交还是中止。

而当事务完成提交操作时，系统也无法精准定位该事务修改过的所有元组与数据页面。倘若该事务修改了大量数据页面，逐一检索页面并更新提示位，会产生极高的性能消耗。除此之外，部分被修改的页面可能已经移出内存缓存，为了单纯更新提示位重新读取磁盘页面，会严重拖慢事务整体提交效率。

依靠提示位减少状态校验开销，随之带来的附带影响是：任意事务，即便是仅执行查询语句的只读事务，都有可能触发提示位的更新操作，进而在缓冲区缓存中产生大量被修改的脏数据页面。

最后我们提交此前执行插入操作的事务：

sql

```
COMMIT;
```

提交操作完成后，数据页面内的直观数据信息并未发生任何变化，但事务提交状态已经同步写入提交日志当中。

此时以常规方式访问该数据表（不借助页面查看扩展工具）的首个事务，会自动判定 xmin 对应的事务状态，并完成提示位的更新赋值：

sql

```
SELECT * FROM t;
SELECT * FROM heap_page('t',0);
```

### 数据删除

执行数据删除操作时，该行当前有效版本的 xmax 字段，会被赋值为执行删除操作的事务编号，同时清空 xmax 已中止标识位。

在该删除事务尚未提交结束期间，xmax 字段对应的事务编号会起到行级锁的作用。其他事务若尝试修改或删除该行数据，必须等待该删除事务执行完毕。

我们执行数据删除操作：

sql

```
BEGIN;
DELETE FROM t;
SELECT pg_current_xact_id();
```

此时事务编号已经写入元组的 xmax 字段，但对应的状态标识位尚未完成赋值：

sql

```
SELECT * FROM heap_page('t',0);
```

### 事务回滚

事务回滚的执行逻辑与事务提交相近，执行效率同样高效，二者唯一区别是回滚操作会在提交日志内标记事务中止标识位。

即便执行了事务回滚命令，数据库也不会对数据页面内已做出的修改进行物理回滚复原，事务执行期间在数据页面内产生的所有变更内容，都会原样保留。

sql

```
ROLLBACK;
SELECT * FROM heap_page('t',0);
```

后续再次访问该数据页面时，系统会自动校验对应事务的最终状态，并为元组补充设置 xmax 已中止提示位。xmax 字段内留存的事务编号不会被清空，但后续所有事务都会直接忽略该数值，不再以此作为判定依据。

sql

```
SELECT * FROM t;
SELECT * FROM heap_page('t',0);
```

### 数据更新

数据更新操作的执行逻辑，等同于先删除原有元组，再插入一条全新元组：

sql

```
BEGIN;
UPDATE t SET s = 'BAR';
SELECT pg_current_xact_id();
```

执行查询语句能够正常读取到该行数据更新后的全新版本数据。

但打开数据页面查看可以发现，页面内会同时留存该行数据的新旧两个版本元组。

原有旧版本元组的 xmax 字段，被赋值为当前执行更新操作的事务编号。由于此前对应事务已经执行回滚操作，原有 xmax 字段内的数值会被直接覆盖。同时当前事务最终状态尚未确定，因此不会设置任何相关中止标识位。

完成本次实验，提交当前事务即可：

sql

```
COMMIT;
```

## 3.4 索引

无论采用何种索引类型，索引结构内部都不会启用行版本管理机制，数据表内的每一行数据，在索引中仅对应唯一一条索引元组。简单来说，索引元组的头部结构中，不存在 xmin 与 xmax 这两个字段。

索引条目会指向数据表内该行数据存在的所有行版本。事务想要判定哪一个行版本处于可见状态，必须访问数据表本体完成校验，仅当对应数据页面的可见性映射表命中时，才可跳过数据表访问流程。

为方便实操演示，我们创建简易自定义函数，依托`pageinspect`扩展查看索引页面内所有索引条目内容，B 树索引页面内的索引条目以平铺列表形式存储：

sql

```
CREATE FUNCTION index_page(relname text, pageno integer)
RETURNS TABLE(itemoffset smallint, htid tid)
AS $$
SELECT itemoffset,
htid
FROM bt_page_items(relname,pageno);
$$ LANGUAGE sql;
```

该索引页面内的索引条目，会同时指向堆表内该行数据的当前最新版本元组与历史旧版本元组。

依据事务编号大小排序规则，对应较早元组的索引条目会排列在列表靠前位置。

## 3.5 TOAST 表

TOAST 表本质上属于普通的数据表，拥有独立完整的行版本管理体系，其版本管理逻辑不会依附于主数据表的行版本。

但 TOAST 表内的数据行具备特殊处理规则：系统不会对已存在的 TOAST 行数据执行更新操作，仅支持新增 TOAST 行数据与删除原有 TOAST 行数据，因此 TOAST 表的版本管理机制属于人为设定的伪版本机制。

对主数据表执行数据修改操作时，系统一定会在主数据表内生成全新的行版本元组。

倘若本次数据修改操作，并未改动存储在 TOAST 结构中的超长字段数据，那么主数据表内的全新元组，会直接引用已经存在的 TOAST 存储数据。

只有当超长字段本身发生数据修改时，PostgreSQL 才会同步在主数据表内创建新元组，同时生成全新的 TOAST 分片存储数据。

## 3.6 虚拟事务

为合理管控事务编号资源，避免事务编号快速耗尽，PostgreSQL 设计了一项专属优化机制。

仅执行查询操作的只读事务，不会对任何数据行的可见性造成影响。基于这一特性，这类事务在初始化阶段，只会被分配虚拟事务编号。

虚拟事务编号由后台进程编号与顺序序列号组合而成，虚拟事务编号的分配流程无需多个进程之间进行同步协调，分配速度极快。处于该阶段的事务，尚未获取正式的实体事务编号。

数据库系统运行期间，内存中会留存大量已经分配使用过的虚拟事务编号，这属于正常现象。虚拟事务编号仅在事务运行期间存在于内存当中，不会写入任何数据页面，也不会持久化存储至磁盘文件。

一旦原本的只读事务开始执行数据修改类操作，系统会立即为该事务分配唯一有效的实体事务编号。

sql

```
BEGIN;
SELECT pg_current_xact_id_if_assigned();

UPDATE accounts
SET amount = amount- 1.00;
SELECT pg_current_xact_id_if_assigned();
COMMIT;
```

## 3.7 子事务

### 保存点

标准 SQL 语法支持保存点功能，借助保存点，我们可以撤销同一个事务内部的部分操作，而无需直接终止整个事务。

但这一执行逻辑，和前文讲解的事务整体状态判定规则相互冲突：事务的最终状态作用于事务内所有执行操作，且事务回滚不会执行物理层面的数据还原操作。

为实现保存点功能，包含保存点的完整事务，会被系统拆分为多个独立的子事务，各个子事务的执行状态能够单独管控。

子事务拥有专属的事务编号，且子事务编号数值大于所属主事务的编号。子事务的执行状态，同样按照常规方式写入提交日志当中；已经执行完成的子事务，会同时标记已提交标识位与已中止标识位。

子事务的最终生效状态，完全由所属主事务决定：倘若主事务最终执行回滚操作，那么其内部所有子事务都会统一判定为执行中止。

所有子事务的相关记录信息，统一存放于数据目录下的 pg_subtrans 文件夹内。子事务相关文件的调用方式，和提交日志一致，均依托实例共享内存内的缓冲区完成读取，缓冲区的内部结构也与提交日志缓冲区完全相同。

务必区分子事务与自治事务：二者不存在任何关联逻辑。原生 PostgreSQL 数据库并不支持自治事务，这一设计反而具备合理性。自治事务适用场景极少，但其余多款数据库中自治事务的滥用行为，往往会引发各类难以排查的业务故障。

清空测试数据表，开启全新事务并插入第一条数据：

sql

```
TRUNCATE TABLE t;
BEGIN;
INSERT INTO t(s) VALUES ('FOO');
SELECT pg_current_xact_id();
```

创建事务保存点，继续插入第二条数据：

sql

```
SAVEPOINT sp;
INSERT INTO t(s) VALUES ('XYZ');
SELECT pg_current_xact_id();
```

可以发现，查询事务编号的函数，返回的始终是外层主事务的编号，不会展示内层子事务编号。

关联查询页面元组信息与数据表实际数据：

sql

```
SELECT *
FROM heap_page('t',0) p
LEFT JOIN t ON p.ctid = t.ctid;
```

执行回滚操作，撤销保存点之后执行的所有操作，随后插入第三条数据：

sql

```
ROLLBACK TO sp;
INSERT INTO t(s) VALUES ('BAR');
SELECT *
FROM heap_page('t',0) p
LEFT JOIN t ON p.ctid = t.ctid;
```

此时数据页面内，依旧保留着被回滚子事务插入的数据行元组。

提交整个外层主事务：

sql

```
COMMIT;
SELECT * FROM t;
SELECT * FROM heap_page('t',0);
```

此时能够清晰直观看到，事务内每一个子事务，都拥有各自独立的执行状态标识。

PostgreSQL 不允许用户手动直接启用子事务，无法在当前事务未结束的前提下，直接开启全新独立事务。

子事务均由数据库系统隐式创建调用，主要用于实现保存点功能、存储过程与函数内部的异常捕获处理，以及其余各类小众特殊业务场景。

### 程序异常与事务原子性

SQL 语句执行过程中若出现程序异常，事务会进入何种状态？

sql

```
BEGIN;
SELECT * FROM t;
UPDATE t SET s = repeat('X', 1/(id-4));
```

语句执行报错后，整个事务会被统一标记为中止状态，事务内部无法再执行任何新的数据库操作。

即便手动执行事务提交命令，数据库也会自动判定执行事务回滚操作。

数据库严格禁止异常出现后继续执行事务操作，核心原因是事务执行期间已经完成的数据修改不会被物理撤销。倘若允许异常后继续执行操作，业务程序会读取到异常出现之前完成的部分数据变更，彻底打破 SQL 语句以及整体事务具备的原子性约束。

补充说明：psql 客户端内置专属运行模式，开启该模式后，可实现语句报错后继续执行事务，效果等同于单独回滚出错语句。

sql

```
\set ON_ERROR_ROLLBACK on
BEGIN;
UPDATE t SET s = repeat('X', 1/(id-4));
SELECT * FROM t;
COMMIT;
```

该模式的底层实现原理十分简单：开启模式后，psql 会在执行每一条 SQL 语句之前，自动创建隐式保存点，一旦语句执行报错，自动回滚至前置保存点位置。该模式不会作为默认运行模式，原因是频繁创建事务保存点，会产生极大的性能资源开销。


# 第四章 快照

## 4.1 什么是快照

一个数据页中可以存放同一行数据的多个版本，但任意事务最多只能看到其中一个版本。所有不同数据行中可见的数据版本组合在一起，就构成了**快照**。快照仅包含其生成时刻已提交的最新数据，能够提供该时间点下具备一致性语义的数据视图。

为保障事务隔离性，每个事务都会使用专属快照。这意味着不同事务可依据不同时间点生成各自的快照，且每份快照的数据状态均保持一致。

在**读已提交**隔离级别下，每条 SQL 语句执行之初都会生成一份新快照，且该快照仅在当前语句执行期间生效。

在**可重复读**与**串行化**隔离级别下，事务内第一条语句执行时生成快照，该快照会一直生效，直至整个事务执行完毕。

## 4.2 行版本可见性

快照并非所需所有数据元组的物理副本，而是由一组数值定义而成，元组是否可见由既定规则判定。

元组的可见性由元组头部的**事务 ID 最小值**与**事务 ID 最大值**字段（即执行插入、删除操作的事务编号）以及对应的提示位共同决定。由于事务 ID 最小值与最大值对应的时间区间互不重叠，任意一行数据在同一份快照中仅会呈现其中一个数据版本。

行可见性判定规则十分繁杂，需要兼顾各类业务场景与边界情况。简单概括规则如下：若一份快照纳入了某元组插入事务的变更，同时排除了其删除事务的变更，则该元组在这份快照中可见，也就是该数据已创建且尚未被删除。

进一步来说，若创建快照前事务已完成提交，那么该事务产生的数据变更就能在快照中被查询到。存在特殊例外情况：事务能够查询到自身未提交的数据变更；若事务最终回滚撤销操作，其所有数据变更在任何快照中都无法被查看。

举个简单示例，下图线段代表事务的执行周期，从事务启动到事务提交结束：

1 号事务在快照生成前完成提交，其数据变更可见；

2 号事务在快照生成时处于运行状态，其数据变更不可见；

3 号事务在快照生成之后才启动，无论该事务是否执行完毕，其数据变更均不可见。

## 4.3 快照结构

实际上数据库内核并非按照上述直观逻辑判定快照状态。系统无法直接获取事务的提交时间，仅能记录事务的启动编号，事务完成时间不会做统一登记。

开启`track_commit_timestamp`参数后可记录事务提交时间，但该参数不会参与数据可见性校验，仅可用于外部数据同步等其他业务场景。

此外数据库会在日志中记录事务提交与回滚时间，该类信息仅用于时间点数据恢复。

系统仅能实时获取事务当前运行状态，相关信息存储在服务端共享内存中，进程数组结构会记录所有活跃会话及对应事务。一旦事务执行完毕，系统便无法回溯判定该事务在快照生成时刻是否处于运行状态。

因此生成快照时，除记录生成时间外，还必须采集当下所有事务的运行状态，否则后续无法界定哪些元组可见、哪些元组需要屏蔽。

受此机制限制，即便数据页中留存着完整历史数据版本，PostgreSQL 也无法生成任意历史时间点的一致性数据快照，也就无法实现回溯查询（也称时间点查询、闪回查询）。

该功能最初曾是 PostgreSQL 的设计目标且完成过开发，项目交由社区维护后该功能被移除。

一份完整快照由生成时刻记录的三类核心数值构成：

1. **xmin（快照下界）**：取值为快照生成时最早活跃事务的编号。所有编号小于该值的事务，要么已提交（变更纳入快照），要么已回滚（变更直接忽略）。
2. **xmax（快照上界）**：取值为当前最新已提交事务编号加一，用于界定快照生成的时间节点。所有编号大于等于该值的事务，要么仍在运行，要么尚未创建，其数据变更均不可见。
3. **xip_list（活跃事务列表）**：存储所有处于运行状态的事务编号，虚拟事务不影响可见性判定，不会纳入该列表。

快照还包含其他辅助参数，本章暂不展开说明。

### 实操示例

sql

```
-- 清空测试表
TRUNCATE TABLE accounts;
```

**事务 1：插入数据，事务保持开启不提交**

sql

```
BEGIN;
INSERT INTO accounts VALUES (1, 'alice', 1000.00);
SELECT pg_current_xact_id();
-- 输出事务编号 790
```

**事务 2：插入数据并立即提交**

sql

```
BEGIN;
INSERT INTO accounts VALUES (2, 'bob', 100.00);
SELECT pg_current_xact_id();
-- 输出事务编号 791
COMMIT;
```

**新建会话，开启可重复读事务并获取当前快照**

sql

```
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT pg_current_snapshot();
-- 输出格式：xmin:xmax:xip_list  结果：790:792:790
```

获取快照后，提交事务 1

sql

```
COMMIT;
```

**事务 3：快照生成后启动，修改已有数据**

sql

```
BEGIN;
UPDATE accounts SET amount = amount + 100 WHERE id = 2;
SELECT pg_current_xact_id();
-- 输出事务编号 792
COMMIT;
```

**在持有快照的事务中查询数据**

仅能查询到旧版本数据

sql

```
SELECT ctid, * FROM accounts;
```

查看数据页内所有存储的元组版本，可发现表内实际存在三条数据版本。

### 可见性判定实战规则

1. 事务编号小于 xmin：数据变更无条件可见；
2. 事务编号介于 xmin 与 xmax 之间：仅当该事务编号不在活跃事务列表内时，变更才可见；
3. 事务 1 插入的数据因事务编号存在于活跃列表中，即便处于快照区间内也无法查看；
4. 事务 3 生成的最新数据版本，事务编号超出快照上界，无法查看；
5. 事务 2 创建的旧版本数据符合判定条件，正常可见。

## 4.4 事务自身变更的可见性

事务查看自身产生的数据变更时，判定规则更为复杂，部分场景下仅能看到部分变更。例如在指定时间点开启的游标，无论采用何种隔离级别，都无法读取游标创建之后事务新增的数据。

为适配这类场景，元组头部设有专属字段，通过`cmin`与`cmax`伪列展示事务内部操作序号，`cmin`标记插入操作序号，`cmax`标记删除操作序号。

为节省存储空间，两个序号共用同一个存储字段。业务场景中同一事务内极少出现同一行数据先插入再删除的情况；若出现该特殊场景，数据库会写入组合标识，单独存放真实的`cmin`与`cmax`数值。

### 游标实操演示

sql

```
BEGIN;
INSERT INTO accounts VALUES (3, 'charlie', 100.00);
SELECT pg_current_xact_id();
-- 输出事务编号793
-- 声明游标统计数据行数
DECLARE c CURSOR FOR SELECT count(*) FROM accounts;
-- 游标创建后再次插入数据
INSERT INTO accounts VALUES (4, 'charlie', 200.00);
-- 查看事务内操作序号
SELECT xmin, CASE WHEN xmin = 793 THEN cmin END cmin, * FROM accounts;
-- 从游标获取查询结果
FETCH c;
```

最终游标仅统计出 3 条数据，游标创建后新增的数据无法被读取，该操作序号相关信息同样会存入快照，无直接查询查看的系统函数。

## 4.5 事务视界

前文提到快照下界`xmin`代表快照生成时最早活跃事务编号，该数值定义了使用当前快照事务的**事务视界**。

无生效快照的事务（例如读已提交级别下两条语句执行间隙），直接以自身事务编号作为视界边界。

所有早于视界边界完成的事务，均可确定为已提交状态，事务仅能读取视界之外数据的最新稳定版本。该概念借鉴物理学中的事件视界定义。

数据库内核会实时记录所有进程的事务视界，可通过系统视图查看当前事务视界编号。

虚拟事务无实体事务编号，同样正常使用快照与事务视界；唯一特例是无生效快照的虚拟事务，视界概念对其无效，在快照与数据可见性逻辑中处于完全透明状态。

以此类推可定义**数据库全局视界**：汇总数据库内所有事务的视界，选取数值最小、时间最早的`xmin`作为全局视界。

处于全局视界之外的老旧元组，不会被库内任何事务查询到，这类无用数据可被 VACUUM 机制安全清理，这也是事务视界具备实际运维价值的核心原因。

### 运维核心结论

1. 可重复读、串行化级别下的长事务，会锁定数据库全局视界，直接延迟垃圾数据清理操作；
2. 读已提交级别普通事务，即便处于事务空闲未执行语句状态，同样会锁定全局视界；
3. 读已提交级别虚拟事务，仅在执行 SQL 语句期间占用全局视界；
4. 整库仅有唯一全局视界，一旦被事务锁定，视界范围内所有数据都无法执行垃圾回收，无关数据也无法清理。

系统目录全局表拥有独立视界，会统筹所有数据库的事务状态；临时表仅受当前进程事务影响，不受全局视界约束。

仅当锁定视界的长事务提交结束后，数据库全局视界才会向后推进，老旧无效数据才能正常执行清理。

**运维建议**：业务开发中尽量避免长事务搭配高频数据更新场景，此类组合会快速产生大量历史数据版本，引发数据表与索引膨胀问题。

## 4.6 系统目录快照

系统目录表虽和普通数据表存储形式一致，但无法沿用普通事务快照进行查询访问。读取系统目录必须使用最新快照，确保能获取最新的表结构、字段属性、数据约束等元数据，避免读取到过期元数据信息。

### 示例演示

在可重复读事务内生成普通快照后，执行表结构修改新增非空约束，后续插入违规数据时，依旧会触发约束报错。

该现象看似违背隔离级别特性，实际底层逻辑为：若插入操作先锁定数据表，表结构修改语句会被阻塞等待事务结束。

数据库内核在查询系统目录时，会自动生成独立的专属快照；为兼顾查询性能，不会无限制频繁新建快照，同时还会结合系统目录缓存机制优化执行效率。

## 4.7 快照导出

部分业务场景中，多个并发事务必须读取完全一致的数据视图，例如并行模式下执行`pg_dump`数据备份，所有备份进程需要统一的数据状态，以此生成一致性完整备份文件。

仅依靠同时启动事务无法保证快照一致，必须借助**快照导出**机制实现统一视图。

`pg_export_snapshot`函数可导出快照唯一标识字符串，该标识可跨会话、跨程序传递使用。

### 完整使用流程

1. 开启可重复读事务，查询业务数据后导出快照标识；
2. 新会话清空表内所有数据；
3. 新会话开启可重复读事务，通过`SET TRANSACTION SNAPSHOT`命令导入指定快照；
4. 导入快照后的事务，依旧能读取快照导出时刻的原始数据，无视后续的数据删除操作。

快照导出后，两个事务仅共享导出时刻的数据视图，快照导出之后双方各自执行的数据变更，依旧遵循原生可见性规则互不互通。

导出快照的有效生命周期，与导出该快照的事务生命周期保持一致。


# 第五章 页面修剪与 HOT 更新

## 5.1 页面修剪

在读取或是更新一个堆页面的过程中，PostgreSQL 能够执行一些快速的页面清理操作，也就是页面修剪。

该操作会在以下情形中发生：

- 上一次更新操作未能在同一个页面中找到足够空间来存放新元组。该情况会在页面头部留下记录标识。
- 该堆页面存储的数据量超出了填充因子这一存储参数所限定的范围。

只有当页面的填充占比低于填充因子设定百分比时，插入操作才能够向该页面写入新行数据。页面中其余剩余空间会预留出来专供更新操作使用（默认状态下不会预留这类空间）。

页面修剪会清除所有已经无法在任意快照中被查询到的元组，也就是所有处于数据库视界之外的元组。该操作的执行范围始终不会超出单个堆页面，相应地执行速度也十分迅速。

指向已修剪元组的指针会继续保留在原有位置，原因是这类指针有可能被索引所引用，而索引本身存储在其他独立页面当中。

出于同样的原因，可见性映射与空闲空间映射也不会进行刷新处理，也就是说清理回收出来的空间仅分配给更新操作使用，不会用于数据插入操作。

由于页面修剪可以在数据读取的过程中被触发执行，因此任意查询语句都有可能造成页面数据发生修改。这也是除了延迟设置信息标识位之外，又一种会出现此类情况的场景。

接下来我们实操演示页面修剪的实际运行逻辑。我们先创建一张包含两列字段的数据表，并且为两列字段分别建立索引：

sql

```
CREATE TABLE hot(id integer, s char(2000)) WITH (fillfactor = 75);
CREATE INDEX hot_id ON hot(id);
CREATE INDEX hot_s ON hot(s);
```

若 s 列仅填写拉丁字母，那么每一个堆元组都会拥有固定长度的存储空间，再加上元组头部占用的固定字节。填充因子存储参数被设置为百分之七十五。这代表该页面的空闲空间理论上足以存放四条元组，但实际仅允许插入三条元组。

我们先插入一行新数据，再对其执行多次更新操作：

sql

```
INSERT INTO hot VALUES (1, 'A');
UPDATE hot SET s = 'B';
UPDATE hot SET s = 'C';
UPDATE hot SET s = 'D';
```

此时该页面内部已经存有四条元组：

sql

```
SELECT * FROM heap_page('hot',0);
```

不出所料，此时数据存储量已经突破了填充因子的限制。我们可以通过页面大小与页面高位地址数值的差值判断这一点，该差值已经超出页面总大小的百分之七十五。

sql

```
SELECT upper, pagesize FROM page_header(get_raw_page('hot',0));
```

下一次访问该页面时，就会触发页面修剪机制，清除所有过期无效元组，随后将新的元组写入到清理出来的空闲空间当中：

sql

```
UPDATE hot SET s = 'E';
SELECT * FROM heap_page('hot',0);
```

页面内剩余的有效堆元组会向高地址位置进行物理移动，让所有空闲空间整合为一整块连续空间，元组对应的指针也会同步完成调整。最终实现消除页面内部空间碎片的效果。

指向已修剪元组的指针暂时还无法删除，因为这类指针依旧被索引引用。PostgreSQL 只会将这类指针的状态从正常状态修改为失效状态。我们查看 hot_s 索引的首个页面（编号 0 页面用于存放元数据）：

sql

```
SELECT * FROM index_page('hot_s',1);
```

另一张索引表中也能看到完全一致的情况：

sql

```
SELECT * FROM index_page('hot_id',1);
```

索引扫描操作能够读取到这类元组标识，数据库服务端会尝试读取对应的堆元组，却发现该指针已经处于失效状态，这就代表该元组实际已经不存在，应当直接忽略。与此同时，服务端还会同步修改索引页面内该指针的状态，避免后续重复读取堆页面造成资源消耗。

我们修改索引页面查询函数，让其能够同步显示指针是否处于失效状态：

sql

```
DROP FUNCTION index_page(text, integer);
CREATE FUNCTION index_page(relname text, pageno integer)
RETURNS TABLE(itemoffset smallint, htid tid, dead boolean)
AS $$
SELECT itemoffset,
htid,
dead
FROM bt_page_items(relname,pageno);
$$ LANGUAGE sql;
```

sql

```
SELECT * FROM index_page('hot_id',1);
```

目前索引页面内所有指针都还处于有效状态，一旦执行首次索引扫描操作，这些指针的状态就会发生变更：

sql

```
EXPLAIN (analyze, costs off, timing off, summary off)
SELECT * FROM hot WHERE id = 1;
SELECT * FROM index_page('hot_id',1);
```

第四条指针所指向的堆元组虽然还未被修剪，状态也显示正常，但该元组已经处于数据库视界之外，这也是这条指针同样被标记为索引内失效状态的原因。

## 5.2 HOT 更新

在索引当中持续保存所有堆元组的引用关系，这种运行方式效率十分低下。

首先，任意一行数据发生修改，都会触发该数据表上所有索引的更新动作。只要生成一条新的堆元组，每一个索引都必须新增一条指向该元组的引用记录，即便被修改的字段本身并没有建立索引。

除此之外，索引会不断累积大量历史堆元组的引用信息，最终这类引用信息也需要和历史元组一同完成清理工作。数据表创建的索引数量越多，这类问题带来的负面影响就会越发严重。

但如果被更新的字段不属于任何索引的组成字段，那么完全没有必要为相同的索引键值重复创建索引条目。为了规避这类冗余操作，PostgreSQL 推出了一项名为仅堆元组更新的优化机制。

执行这类更新操作后，每一行数据在索引页面当中只会保留唯一一条索引条目。该条目固定指向该行数据最早生成的版本，同一页面内后续生成的所有数据版本，都会依靠元组头部的 ctid 指针相互串联形成一条数据链。

没有被任何索引引用的数据行版本，会被标记上仅堆元组标识。已经纳入更新数据链当中的数据版本，则会被标记上堆热更新标识。

当索引扫描访问堆页面，读取到带有堆热更新标识的数据行版本时，代表扫描流程需要继续向后执行，沿着更新数据链依次向后遍历。显而易见，所有读取获取到的数据行版本，都需要完成可见性校验之后，才能够将最终结果返回给客户端。

接下来我们删除其中一张索引表，清空数据表数据，实操演示 HOT 更新的执行流程：

sql

```
DROP INDEX hot_s;
TRUNCATE TABLE hot;
```

为了方便查看数据，我们重新定义堆页面查询函数，在输出结果中新增三个字段：ctid 以及两个和 HOT 更新相关的标识位：

sql

```
DROP FUNCTION heap_page(text,integer);
CREATE FUNCTION heap_page(relname text, pageno integer)
RETURNS TABLE(
ctid tid, state text,
xmin text, xmax text,
hhu text, hot text, t_ctid tid
) AS $$
SELECT (pageno,lp)::text::tid AS ctid,
CASE lp_flags
WHEN 0 THEN 'unused'
WHEN 1 THEN 'normal'
WHEN 2 THEN 'redirect to '||lp_off
WHEN 3 THEN 'dead'
END AS state,
t_xmin || CASE
WHEN (t_infomask & 256) > 0 THEN ' c'
WHEN (t_infomask & 512) > 0 THEN ' a'
ELSE ''
END AS xmin,
t_xmax || CASE
WHEN (t_infomask & 1024) > 0 THEN ' c'
WHEN (t_infomask & 2048) > 0 THEN ' a'
ELSE ''
END AS xmax,
CASE WHEN (t_infomask2 & 16384) > 0 THEN 't' END AS hhu,
CASE WHEN (t_infomask2 & 32768) > 0 THEN 't' END AS hot,
t_ctid
FROM heap_page_items(get_raw_page(relname,pageno))
ORDER BY lp;
$$ LANGUAGE sql;
```

我们再次执行数据插入与数据更新操作：

sql

```
INSERT INTO hot VALUES (1, 'A');
UPDATE hot SET s = 'B';
```

此时该页面内部已经形成一条完整的 HOT 更新数据链：

堆热更新标识代表执行引擎需要顺着事务指针链条继续向后查找；仅堆元组标识代表该元组没有被任何索引引用。

sql

```
SELECT * FROM heap_page('hot',0);
```

持续执行更新操作，这条数据链的长度会不断增加，但其扩展范围始终被限制在当前页面之内：

sql

```
UPDATE hot SET s = 'C';
UPDATE hot SET s = 'D';
SELECT * FROM heap_page('hot',0);
```

索引表当中依旧仅保留唯一一条引用记录，该记录指向整条数据链的起始位置：

sql

```
SELECT * FROM index_page('hot_id',1);
```

只有当被修改的字段不属于任意索引字段时，才能够触发 HOT 更新机制。如若不满足该条件，部分索引就会生成指向数据链中间版本的引用条目，和这项优化机制的设计初衷相互违背。由于 HOT 数据链仅能在单个页面内部延伸扩展，遍历整条数据链的过程无需访问其他页面，因此不会对数据库运行性能造成负面影响。

## 5.3 适配 HOT 更新的页面修剪

有一种十分特殊却又至关重要的页面修剪场景，那就是针对 HOT 更新数据链执行修剪操作。

在上文的示例当中，数据存储量已经超出填充因子限定范围，因此下一次更新操作必然会触发页面修剪。而此时的页面内存放着一条 HOT 更新数据链。

整条数据链的起始位置绝对不能变动，原因是该位置被索引直接引用，除此之外其余所有指针都可以被释放清理，这类指针确定不存在任何外部引用关系。

为了避免移动数据链头部位置，PostgreSQL 采用双重寻址的设计方案。被索引直接引用的指针会被设置为重定向状态，该指针会直接指向当下整条数据链实际的起始元组位置。

sql

```
UPDATE hot SET s = 'E';
SELECT * FROM heap_page('hot',0);
```

部分历史元组已经完成修剪清理，用于重定向的头部指针保留不动，其余无引用的指针则被标记为未使用状态。新生成的元组会写入到清理出来的空闲空间当中。

我们继续执行多次数据更新操作：

sql

```
UPDATE hot SET s = 'F';
UPDATE hot SET s = 'G';
SELECT * FROM heap_page('hot',0);
```

再次执行更新操作就会触发新一轮的页面修剪动作：

sql

```
UPDATE hot SET s = 'H';
SELECT * FROM heap_page('hot',0);
```

本轮操作再次清理掉部分历史元组，同时同步调整指向数据链头部的指针位置。

如果业务场景中需要频繁修改未建立索引的字段，适当调低填充因子的数值是合理的选择，以此在页面当中预留出更多可供更新操作使用的空间。显而易见，填充因子的数值设置得越低，页面内部预留的空闲空间就越多，对应的数据表整体物理存储体积也会随之变大。

## 5.4 HOT 数据链拆分

当当前页面已经没有剩余空间用来存放新生成的元组时，原本连贯的 HOT 数据链就会发生拆分断裂。此时 PostgreSQL 只能新增一条独立的索引条目，用来存放在其他页面当中的元组。

我们开启一个并发事务并创建快照，以此阻塞页面修剪机制的执行，复现该场景：

sql

```
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT 1;
```

在首个会话当中连续执行多次更新操作：

sql

```
UPDATE hot SET s = 'I';
UPDATE hot SET s = 'J';
UPDATE hot SET s = 'K';
SELECT * FROM heap_page('hot',0);
```

执行下一次更新操作时，当前页面已经无法容纳新元组，同时页面修剪机制也无法释放出可用空间：

sql

```
UPDATE hot SET s = 'L';
COMMIT;
SELECT * FROM heap_page('hot',0);
```

该元组当中写入了指向新页面的引用地址：

sql

```
SELECT * FROM heap_page('hot',1);
```

这条新的引用地址不会纳入原有 HOT 数据链当中，对应的元组也不会标记堆热更新标识。而新页面当中的元组可以被索引直接访问，此时索引表内部会生成两条独立索引条目，每一条条目分别指向各自所属 HOT 数据链的头部位置。

sql

```
SELECT * FROM index_page('hot_id',1);
```

## 5.5 索引层面的页面修剪

前文提到的页面修剪操作，执行范围仅限定在堆页面当中，不会对索引造成任何影响。但索引自身也配备了专属的修剪清理机制，该机制同样仅针对单个索引页面执行清理工作。

当向 B 树索引执行数据插入，即将触发页面分裂动作、原有页面空间不足时，索引修剪机制就会被触发。存在的问题是，即便后续部分索引条目对应的数据被删除，已经拆分完成的两个索引页面也不会自动合并复原。这种情况最终会造成索引体积膨胀，并且索引一旦出现膨胀问题，即便数据表内大量数据被删除，索引体积也无法自动收缩。而索引修剪机制能够清理部分无效元组，以此延后索引页面分裂的触发时机。

一共有两类元组能够从索引结构当中被修剪清除：

第一类是 PostgreSQL 会优先清理所有已经被标记为失效状态的索引元组。正如前文所说，在索引扫描过程中，一旦检测到某条索引条目指向的元组无法被任意快照识别、或是该元组已经彻底不存在时，数据库就会为这条索引条目打上失效标记。

如果检索不到任何已经标记失效的索引元组，PostgreSQL 就会开始检查那些指向同一张数据表内同一行数据不同版本的索引条目。由于更新操作会批量生成大量数据行版本，这类版本当中的绝大部分很快就会处于数据库视界之外。HOT 更新机制能够缓解这类问题，但该机制无法适配所有业务场景。一旦被更新的字段属于索引字段，对应的索引引用关系就会同步同步至所有索引当中。

在触发索引页面分裂之前，检索并清理这类尚未标记失效、但已经满足清理条件的数据行具备实际意义。想要完成这项操作，PostgreSQL 必须校验对应堆元组的可见性状态。这类校验动作需要访问数据表本体，因此数据库只会针对具备清理潜力的索引元组执行校验，也就是那些为实现更新功能而复制生成的索引条目。执行这类可见性校验的资源开销，要远低于触发额外索引页面分裂产生的资源开销。


# 第六章 清理与自动清理

## 6.1 清理

页面清理的执行速度非常快，但它仅能回收一部分潜在可释放的空间。

页面清理仅在单个堆页面内操作，不会触及索引（反之亦然，索引页面的清理不会影响数据表）。

常规清理是主要的清理流程，由`VACUUM`命令执行。它会处理整个数据表，清除过期的堆元组以及所有对应的索引项。

清理操作与数据库系统中的其他进程并行执行。在清理期间，数据表和索引可以照常使用，支持读写操作（但不允许并发执行`TRUNCATE`、`ALTER TABLE`等部分命令）。

为避免扫描额外的页面，PostgreSQL 使用可见性映射表。该映射表中记录的页面会被跳过，因为这些页面确定只包含当前有效元组，因此只有未出现在该映射表中的页面才会被清理。

如果清理后页面中剩余的所有元组都超出了数据库视界，可见性映射表会被更新以纳入该页面。

空闲空间映射表也会被更新，以反映已清理出的空间。

我们创建一张带索引的数据表：

plaintext

```
=> CREATE TABLE vac(
id integer,
s char(100)
)
WITH (autovacuum_enabled = off);
=> CREATE INDEX vac_s ON vac(s);
```

`autovacuum_enabled`存储参数会关闭自动清理；我们这样做仅用于实验，以便精确控制清理的启动时间。

我们插入一行数据并执行几次更新：

plaintext

```
=> INSERT INTO vac(id,s) VALUES (1,'A');
=> UPDATE vac SET s = 'B';
=> UPDATE vac SET s = 'C';
```

现在数据表中包含三个元组：

plaintext

```
=> SELECT * FROM heap_page('vac',0);

−−−−−−−+−−−−−−−−+−−−−−−−+−−−−−−−+−−−−−+−−−−−+−−−−−−−−
```

每个元组都被索引引用：


## 6.2 重温数据库视界

## 6.3 清理阶段

清理机制看似十分简单，但这种印象具有误导性。毕竟，数据表和索引都必须并发处理，且不能阻塞其他进程。为实现这种操作方式，每张表的清理会分多个阶段执行。

整个流程从扫描数据表查找失效元组开始；如果找到，会先从索引中移除，再从数据表本身移除。如果一次需要清理大量失效元组，该过程会重复执行。最终，可能会执行堆截断操作。

### 堆扫描

第一阶段执行堆扫描。扫描过程会考虑可见性映射表：该映射表中记录的所有页面都会被跳过，因为这些页面确定不包含过期元组。如果一个元组超出视界且不再被需要，它的`tid`会被添加到一个专用的`tid`数组中。这类元组暂时无法移除，因为它们可能仍被索引引用。

`tid`数组存储在`VACUUM`进程的本地内存中；分配的内存块大小由`maintenance_work_mem`参数定义。整个 64MB 内存块会一次性分配，而非按需分配。不过，分配的内存永远不会超过最坏场景所需的容量，因此如果数据表很小，清理操作使用的内存可能低于该参数指定的值。

### 索引清理

第一阶段有两种结果：要么完整扫描数据表，要么在操作完成前`tid`数组的分配内存已占满。无论哪种情况，都会开始索引清理阶段。在此阶段，会完整扫描表上创建的每个索引，查找所有引用`tid`数组中记录的元组的条目。这些条目会从索引页面中移除。

索引可以帮助你通过索引键快速定位堆元组，但无法通过对应的元组`tid`快速找到索引项。该功能目前正在为 B 树开发，但尚未完成。

如果存在多个大于`min_parallel_index_scan_size`值的索引，可由后台工作进程并行执行清理。除非`parallel N`子句显式定义并行度，否则`VACUUM`会为每个合适的索引启动一个工作进程（在后台工作进程数量的总体限制内）。一个索引无法由多个工作进程处理。

在索引清理阶段，PostgreSQL 会更新空闲空间映射表并计算清理统计信息。不过，如果仅执行插入操作（无删除或更新），该阶段会被跳过，因为此时数据表不包含失效元组。届时，仅会在最后作为独立的索引清理阶段强制执行一次索引扫描。

索引清理阶段会确保索引中不存在指向过期堆元组的引用，但元组本身仍保留在数据表中。这完全正常：索引扫描无法找到任何失效元组，而数据表的顺序扫描会依靠可见性规则过滤它们。

### 堆清理

随后进入堆清理阶段。再次扫描数据表，移除`tid`数组中记录的元组并释放对应的指针。此时所有相关的索引引用已被移除，可以安全执行该操作。

`VACUUM`回收的空间会反映在空闲空间映射表中，而现在仅包含所有快照均可见的当前元组的页面，会在可见性映射表中被标记。

如果堆扫描阶段未完整读取数据表，`tid`数组会被清空，并从上次中断的位置恢复堆扫描。

### 堆截断

清理后的堆页面会包含部分空闲空间；偶尔可以清空整个页面。如果文件末尾出现多个空页面，清理操作可以 “截断” 这部分尾部空间，并将回收的空间返还给操作系统。该操作在堆截断阶段执行，这是清理的最后阶段。

堆截断需要对数据表施加短暂的排他锁。为避免长时间阻塞其他进程，获取锁的尝试不会超过 5 秒。

由于必须锁定数据表，仅当空页面尾部至少占数据表的 1/16 或长度达到 1000 个页面时，才会执行截断操作。这些阈值是硬编码的，无法配置。

如果尽管采取了所有预防措施，数据表锁仍引发问题，可以使用`vacuum_truncate`和`toast.vacuum_truncate`存储参数完全禁用截断功能。

## 6.4 分析

谈及清理操作，我们必须提及另一项与其密切相关的任务，尽管二者之间没有正式关联。这就是分析，即为查询规划器收集统计信息。收集的统计信息包括关系中的行数（`pg_class.reltuples`）和页面数（`pg_class.relpages`）、列内的数据分布以及其他一些信息。

你可以使用`ANALYZE`命令手动执行分析，或通过调用`VACUUM ANALYZE`将其与清理结合执行。不过，这两项任务仍按顺序执行，因此性能方面没有差异。

在历史上，`VACUUM ANALYZE`最早出现在 7.1 版本，而独立的`ANALYZE`命令直到 8.0 版本才实现。在早期版本中，统计信息由`vacuumdb`脚本收集。

自动清理和分析的配置方式相似，因此适合放在一起讨论。

## 6.5 自动清理与分析

除非数据库视界被长时间阻塞，否则常规清理操作能够完成其工作。但我们需要多久调用一次`VACUUM`命令？

如果频繁更新的数据表清理过于频繁，服务器会忙于维护工作而非执行有效业务。

此外，典型的工作负载可能随时间变化，因此固定的清理计划毫无用处：表更新越频繁，清理就需要越频繁。

该问题由自动清理解决，它会根据表更新的强度启动清理和分析进程。

### 自动清理机制

启用自动清理（`autovacuum`配置参数为`on`）时，自动清理启动器进程会始终在系统中运行。该进程定义自动清理计划，并根据使用统计信息维护 “活跃” 数据库列表。如果启用`track_counts`参数，就会收集此类统计信息。不要关闭这些参数，否则自动清理将无法工作。

每隔`autovacuum_naptime`时间，自动清理启动器会为列表中的每个活跃数据库启动一个自动清理工作进程（这些工作进程照常由`postmaster`派生）。因此，如果集群中有 N 个活跃数据库，会在`autovacuum_naptime`间隔内派生 N 个工作进程。但并行运行的自动清理工作进程总数不能超过`autovacuum_max_workers`参数定义的阈值。

自动清理工作进程与常规后台工作进程非常相似，但它们比这种通用任务管理机制出现得早得多。最终决定保留自动清理的实现不变，因此自动清理工作进程不占用`max_worker_processes`插槽。

启动后，后台工作进程连接到指定数据库并构建两个列表：

- 所有需要清理的数据表、物化视图和 TOAST 表的列表
- 所有需要分析的数据表和物化视图的列表（TOAST 表不分析，因为它们始终通过索引访问）

随后逐个处理选定的对象（执行清理、分析或两者都执行），任务完成后，工作进程终止。

自动清理的工作方式与`VACUUM`命令发起的手动清理类似，但存在一些细微差别：

- 执行手动清理时，元组`tid`会累积在`maintenance_work_mem`大小的内存块中。对自动清理使用相同限制并不理想，因为这可能导致内存消耗过高：可能有多个自动清理工作进程并行运行，每个进程都会一次性获取`maintenance_work_mem`大小的内存。相反，PostgreSQL 为自动清理进程提供了独立的内存限制，由`autovacuum_work_mem`参数定义。

默认情况下，`autovacuum_work_mem`参数回退到常规限制`-1`（即使用`maintenance_work_mem`），因此如果`autovacuum_max_workers`值较高，可能需要相应调整`autovacuum_work_mem`的值。

- 手动清理可以并发处理一张表上创建的多个索引；使用自动清理执行此操作会导致大量并行进程，因此不允许。

如果工作进程无法在`autovacuum_naptime`间隔内完成所有计划任务，自动清理启动器会派生另一个工作进程在该数据库中并行运行。第二个工作进程会构建自己的待清理和分析对象列表并开始处理。表级别不存在并行性；仅可并发处理不同的表。

### 哪些表需要清理？

你可以在表级别禁用自动清理 —— 尽管很难想象有这样做的必要。为此提供了两个存储参数，一个用于常规表，另一个用于 TOAST 表：

- `autovacuum_enabled`
- `toast.autovacuum_enabled`

通常情况下，自动清理由失效元组累积或新行插入触发。

**失效元组累积**。失效元组由统计收集器持续计数；它们的当前数量显示在系统目录表`pg_stat_all_tables`中。

如果失效元组超过以下两个参数定义的阈值，则认为需要执行清理：

- `autovacuum_vacuum_threshold`，指定失效元组数量（绝对值）
- `autovacuum_vacuum_scale_factor`，设置失效元组在表中的占比

满足以下条件时需要执行清理：

plaintext

```
pg_stat_all_tables.n_dead_tup >
autovacuum_vacuum_threshold +
autovacuum_vacuum_scale_factor × pg_class.reltuples
```

这里的主要参数当然是`autovacuum_vacuum_scale_factor`：它的值对大表很重要（而大表很可能引发大部分问题）。默认值 20% 似乎过高，可能需要大幅降低。

不同表的最佳参数值可能不同：它们很大程度上取决于表大小和工作负载类型。建议设置大致合适的初始值，然后使用存储参数为特定表覆盖这些值：

- `autovacuum_vacuum_threshold` 和 `toast.autovacuum_vacuum_threshold`
- `autovacuum_vacuum_scale_factor` 和 `toast.autovacuum_vacuum_scale_factor`

**行插入**。如果仅执行插入操作，无删除或更新，表中不包含失效元组。但此类表也需要清理，以提前冻结堆元组并更新可见性映射表（从而支持仅索引扫描）。

如果自上次清理以来插入的行数超过另一组类似参数定义的阈值，表将被清理：

- `autovacuum_vacuum_insert_threshold`
- `autovacuum_vacuum_insert_scale_factor`

计算公式如下：

plaintext

```
pg_stat_all_tables.n_ins_since_vacuum >
autovacuum_vacuum_insert_threshold +
autovacuum_vacuum_insert_scale_factor × pg_class.reltuples
```

与上一个示例相同，你可以使用存储参数在表级别覆盖这些值：

- `autovacuum_vacuum_insert_threshold` 及其 TOAST 对应参数
- `autovacuum_vacuum_insert_scale_factor` 及其 TOAST 对应参数

### 哪些表需要分析？

自动分析仅需要处理修改过的行，因此计算比自动清理稍简单。

如果自上次分析以来修改的行数超过以下两个配置参数定义的阈值，则认为需要分析表：

- `autovacuum_analyze_threshold`
- `autovacuum_analyze_scale_factor`

满足以下条件时触发自动分析：

plaintext

```
pg_stat_all_tables.n_mod_since_analyze >
autovacuum_analyze_threshold +
autovacuum_analyze_scale_factor × pg_class.reltuples
```

要为特定表覆盖自动分析设置，可以使用同名存储参数：

- `autovacuum_analyze_threshold`
- `autovacuum_analyze_scale_factor`

由于 TOAST 表不分析，因此没有对应的参数。

### 自动清理实战

为将本节所述内容规范化，我们创建两个视图，显示当前哪些表需要清理和分析。这些视图中使用的函数会返回传入参数的当前值，并考虑该值可在表级别重新定义：

plaintext

```
=> CREATE FUNCTION p(param text, c pg_class) RETURNS float
AS $$
SELECT coalesce(
(SELECT option_value
FROM pg_options_to_table(c.reloptions)
WHERE option_name = CASE
WHEN c.relkind = 't' THEN 'toast.' ELSE ''
END || param
),
current_setting(param)
)::float;
$$ LANGUAGE sql;
```

与清理相关的视图如下：

plaintext

```
=> CREATE VIEW need_vacuum AS
WITH c AS (
SELECT c.oid,
greatest(c.reltuples, 0) reltuples,
p('autovacuum_vacuum_threshold', c) threshold,
p('autovacuum_vacuum_scale_factor', c) scale_factor,
p('autovacuum_vacuum_insert_threshold', c) ins_threshold,
p('autovacuum_vacuum_insert_scale_factor', c) ins_scale_factor
FROM pg_class c
WHERE c.relkind IN ('r','m','t')
)
SELECT st.schemaname || '.' || st.relname AS tablename,
st.n_dead_tup AS dead_tup,
c.threshold + c.scale_factor * c.reltuples AS max_dead_tup,
st.n_ins_since_vacuum AS ins_tup,
c.ins_threshold + c.ins_scale_factor * c.reltuples AS max_ins_tup,
st.last_autovacuum
FROM pg_stat_all_tables st
JOIN c ON c.oid = st.relid;
```

`max_dead_tup`列显示触发自动清理的失效元组数量，而`max_ins_tup`列显示与插入相关的阈值。

以下是用于分析的类似视图：

plaintext

```
=> CREATE VIEW need_analyze AS
WITH c AS (
SELECT c.oid,
greatest(c.reltuples, 0) reltuples,
p('autovacuum_analyze_threshold', c) threshold,
p('autovacuum_analyze_scale_factor', c) scale_factor
FROM pg_class c
WHERE c.relkind IN ('r','m')
)
SELECT st.schemaname || '.' || st.relname AS tablename,
st.n_mod_since_analyze AS mod_tup,
c.threshold + c.scale_factor * c.reltuples AS max_mod_tup,
st.last_autoanalyze
FROM pg_stat_all_tables st
JOIN c ON c.oid = st.relid;
```

`max_mod_tup`列显示自动分析的阈值。

为加速实验，我们将自动清理的启动间隔设为每秒：

plaintext

```

```

我们清空`vac`表，然后插入 1000 行。注意，该表的自动清理已关闭。

plaintext

```

SELECT id, 'A' FROM generate_series(1,1000) id;
```


我们回到自动清理：

## 6.6 负载管理

清理操作在页面级别执行，不会阻塞其他进程；但尽管如此，它会增加系统负载，并对性能产生显著影响。

### 清理限流

为控制清理强度，PostgreSQL 会在表处理过程中定期暂停。完成约`vacuum_cost_limit`个工作单元后，进程会休眠，并保持空闲`vacuum_cost_delay`时间间隔。

`vacuum_cost_delay`的默认零值意味着常规清理实际上从不休眠，因此`vacuum_cost_limit`的具体值无关紧要。假设管理员必须执行手动清理，他们可能希望尽快完成。

如果设置了休眠时间，进程每次在缓冲区缓存中处理页面消耗`vacuum_cost_limit`个工作单元后都会暂停。如果页面在缓冲区缓存中命中，每次页面读取操作的成本估算为`vacuum_cost_page_hit`个单位；否则为`vacuum_cost_page_miss`个单位。如果清理操作将干净页面弄脏，会额外增加`vacuum_cost_page_dirty`个单位。

如果保持`vacuum_cost_limit`参数的默认值，`VACUUM`在最佳场景下每个周期最多可处理 200 个页面（如果所有页面都已缓存，且`VACUUM`未弄脏任何页面），最坏情况下仅能处理 9 个页面（如果所有页面都从磁盘读取并变为脏页）。

### 自动清理限流

自动清理的限流与`VACUUM`限流非常相似。不过，自动清理可以以不同强度运行，因为它有自己的一组参数：

- `autovacuum_vacuum_cost_limit`
- `autovacuum_vacuum_cost_delay`

如果这些参数中的任何一个设置为`-1`，会回退到常规`VACUUM`的对应参数。这意味着`autovacuum_vacuum_cost_limit`参数默认依赖`vacuum_cost_limit`的值。

在版本 12 之前，`autovacuum_vacuum_cost_delay`的默认值为 20ms，这在现代硬件上导致性能非常差。

自动清理工作单元每个周期限制为`autovacuum_vacuum_cost_limit`，并且由于它们在所有工作进程之间共享，无论工作进程数量如何，对系统的总体影响大致保持不变。因此，如果需要加速自动清理，`autovacuum_max_workers`和`autovacuum_vacuum_cost_limit`的值应按比例增加。

如果需要，你可以通过设置以下存储参数为特定表覆盖这些设置：

- `autovacuum_vacuum_cost_delay` 和 `toast.autovacuum_vacuum_cost_delay`
- `autovacuum_vacuum_cost_limit` 和 `toast.autovacuum_vacuum_cost_limit`

## 6.7 监控

通过监控清理操作，可以检测到失效元组无法一次性移除的情况，因为指向它们的引用无法装入`maintenance_work_mem`内存块。在这种情况下，所有索引都必须完整扫描多次。对于大表，这可能花费大量时间，从而对系统造成显著负载。

即使查询不会被阻塞，额外的 I/O 操作也会严重限制系统吞吐量。

此类问题可以通过更频繁地清理表（使每次运行清理更少的元组）或分配更多内存来解决。

### 监控清理

使用`VERBOSE`子句运行时，`VACUUM`命令会执行清理并显示状态报告，而`pg_stat_progress_vacuum`视图会显示已启动进程的当前状态。

分析也有类似的视图（`pg_stat_progress_analyze`），尽管分析通常执行得非常快，不太可能引发任何问题。

我们向表中插入更多行并全部更新，使`VACUUM`必须运行一段明显的时间：

plaintext

```

SELECT id, 'A' FROM generate_series(1,500000) id;
```

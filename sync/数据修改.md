# 第八章 数据修改

到目前为止，我们只讨论了查询性能，但 SQL 并不只有查询。它同样支持数据操作。对应的命令 ——**INSERT、DELETE、UPDATE**—— 构成了所谓的**数据操作语言（DML）**，这是 SQL 标准的一部分。这些命令的性能**绝大多数情况下都会受到索引的负面影响**。

索引本质是**纯粹的冗余**。它只存储表中已有的数据。在写操作期间，数据库必须保持这些冗余数据的一致性。具体来说，INSERT、DELETE、UPDATE 不仅会影响表本身，还会影响所有存储了受影响数据副本的索引。

---

## INSERT（插入）

表上的索引数量是影响插入性能**最主要**的因素。索引越多，插入越慢。INSERT 语句是**唯一无法直接从索引受益**的操作，因为它没有 WHERE 子句。

向表中添加新行涉及多个步骤：

1. 数据库必须找到存储该行的位置。对于普通堆表（没有特定行顺序），数据库可以使用任何有足够空闲空间的数据块。这是一个非常简单快速的过程，主要在内存中执行。
2. 数据库只需要将新行写入对应数据块即可。

如果表上有索引，数据库必须确保新行也能通过这些索引找到。因此，它**必须向表上的每一个索引都添加一条新的索引条目**。

**索引的数量相当于插入成本的倍数。**

此外，向索引中添加条目比向堆结构插入昂贵得多，因为数据库必须**保持索引有序和树的平衡**。

这意味着新条目不能写入任意数据块 —— 它必须属于**特定的叶子节点**。

尽管数据库使用索引树本身查找正确的叶子节点，但遍历树仍然需要读取若干索引块。

找到正确的叶子节点后，数据库会检查节点是否有足够空间。

如果没有，数据库会**分裂叶子节点**，将条目分配到旧节点和新节点中。

这个过程还会影响对应的分支节点 —— 分支节点也可能需要分裂。

最坏情况下，数据库必须一直分裂到根节点。这是索引树增加高度、变深的唯一情况。

**索引维护是插入操作中最昂贵的部分。**

图 8.1 “按索引数量划分的插入性能” 清晰地展示了这一点：

- 无索引时，执行时间几乎可以忽略不计
- **添加第一个索引就会让执行时间增加上百倍**
- 每多一个索引，速度就会进一步下降

**注意**

**第一个索引带来的性能影响最大。**

要优化插入性能，**保持索引数量尽可能少**至关重要。

**提示**

谨慎、精简地使用索引，避免冗余索引。这对 DELETE 和 UPDATE 同样有益。

只考虑插入的话，**完全去掉索引**是最好的选择 —— 能获得极致插入性能。

但在实际应用中，无索引的表几乎不现实。你通常需要检索数据，因此需要索引加速查询。

即使是只写日志表，通常也有主键和对应的索引。

尽管如此，无索引的性能如此优秀，以至于在**批量加载大量数据时临时删除所有索引**非常有意义 —— 前提是这段时间内没有其他 SQL 需要这些索引。

这会带来巨大的性能提升，这也是**数据仓库的常用实践**。

## DELETE（删除）

与 INSERT 不同，DELETE 语句**有 WHERE 子句**，可以直接从索引受益 —— 使用第二章 “WHERE 子句” 中描述的所有方法。

事实上，DELETE 就像一次查询，再加上一步删除找到的行。

真正删除行的过程与插入类似 —— 尤其是**从索引中移除引用**以及**维护索引树平衡**的操作。

因此，图 8.2 所示的性能图表与 INSERT 非常相似。

理论上，我们会期望**无索引表**拥有最佳删除性能 —— 就像插入一样。

但问题是：**如果没有索引，数据库必须全表扫描才能找到要删除的行**。

这意味着 “删除行” 很快，但 “找到行” 极慢。因此图 8.2 没有展示这种情况。

尽管如此，当删除语句会返回表中大部分数据时，**不用索引执行 DELETE** 也是合理的 —— 就像不用索引执行查询一样。

**提示**

即使是 DELETE 和 UPDATE 语句，也有执行计划。

**无 WHERE 子句的 DELETE**

这是数据库显然无法使用索引的典型例子。

但这是一个特殊情况，SQL 有专门命令：**TRUNCATE TABLE**。

它与无 WHERE 的 DELETE 效果相同，但**一次性删除所有行**，速度极快。

但有两个重要副作用：

1. 会**隐式提交事务**（例外：PostgreSQL）
2. **不触发触发器**

---

### MVCC 的副作用

多版本并发控制（MVCC）是数据库实现**非阻塞并发访问**和**一致性事务视图**的机制。

但不同数据库的实现差异很大，对性能影响也很显著。

例如 PostgreSQL：

- 只在**表级别**保留版本信息（可见性信息）
- 删除一行**只是在表块中标记 “已删除”**
- 因此 PostgreSQL 的删除性能**不依赖表上索引的数量**
- 物理删除行和索引维护只在 **VACUUM** 过程中执行

## UPDATE（更新）

UPDATE 语句必须**重新定位被修改的索引条目**以保持索引有序。

为此，数据库必须：

1. **删除旧条目**
2. **在新位置添加新条目**

响应时间基本等于**对应的 DELETE + INSERT** 之和。

更新性能与插入、删除一样，取决于表上的索引数量。

**唯一区别是：UPDATE 不一定修改所有列，通常只改少数几列。**

因此，UPDATE **不一定影响所有索引，只影响包含被修改列的索引**。

图 8.3 展示了两种更新的响应时间：

1. **修改所有列** → 影响所有索引
2. **只修改一列** → 只影响一个索引

- 修改所有列：每增加一个索引，耗时明显上升
- 只修改一列：耗时增长很小，因为大部分索引未被触及

**优化更新性能的关键：只更新真正改变的列。**

手动写 SQL 时这显而易见。

但 ORM 工具可能生成**每次都更新所有列**的语句。

例如 Hibernate，在禁用 `dynamic-update` 时会这样做。

从 4.0 版本开始，该模式**默认启用**。

使用 ORM 工具时，建议在开发环境**偶尔开启 SQL 日志**，检查生成的语句是否合理。

# 第八章 核心要点（简洁版，你要我再展开）

1. **索引对写操作几乎都是负面影响**，因为每次写入都要维护所有相关索引。
2. **INSERT**
    
    - 性能取决于**索引数量**，第一个索引影响最大
    - 索引维护（分裂、平衡）是主要开销
    - 批量导入时可**临时删索引**极大提速
    
3. **DELETE**
    
    - 可以用索引快速找到行
    - 但删除时仍需维护所有索引
    - 无索引会导致全表扫描，反而更慢
    
4. **UPDATE**
    
    - 等于 DELETE + INSERT
    - **只影响包含被修改列的索引**
    - 优化关键：**只改需要改的列**
    
5. **通用原则**
    - 索引越少，写入越快
    - 避免冗余索引
    - ORM 工具注意避免全字段更新

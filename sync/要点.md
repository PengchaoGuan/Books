你不能想当然认为，仅仅设计出优秀的**逻辑数据模型**，就能写出高效的 SQL 语句。你必须确保你的设计以合理的方式完成物理落地，否则你会发现，借助 SQL 从数据中高效提取有效信息的能力将会受到制约。

保障 SQL 查询语句高效执行的核心要点之一，就是为数据表建立规范索引。本章内容能够帮你理清，在落地已设计完备的数据模型时，那些常常被忽视的设计要点。虽然数据表与索引的创建工作大多交由数据库管理员（DBA）负责，但事实上，索引设计工作交由开发人员来完成往往更为合适。数据库管理员精通存储系统配置与硬件架构部署，可合理索引的创建，需要清楚业务系统会对数据表执行哪些查询语句。这类业务查询信息，数据库管理员与外部顾问通常很难全面掌握，却是应用开发人员理应熟知的内容。本章内容将带你理解索引的重要性，以及如何保障索引完成规范部署。

如同第一章《数据模型设计》中所说，如果你拥有数据库落地实施的管控权限，你可以对照本章各项要点复核数据模型，排查并修正发现的所有问题。如果你无权主导整体设计，也可以借助本章所学内容向数据库管理员提供参考依据，协助他们高效搭建数据库。

## 要点 10：创建索引时充分考量空值

在关系型数据库中，**NULL**是一种特殊值，用于表示字段数据**未知**或字段无数据存储。空值永远无法与任意值判定相等或不等，即便是两个空值之间也不存在等值关系。想要判断字段是否存在空值，必须使用专用的`IS NULL`判定条件。

我们通常会为查询条件中频繁用到的单列或多列组合创建索引，以此提升这类查询语句的执行性能。为字段建立索引前，你需要确认该字段是否存储空值，并清楚你所使用的数据库系统如何处理索引中的空值。

如果一张数据表内，某索引字段的绝大多数数据行都存储为空值，那么该索引基本没有实用价值，除非你的业务查询只检索非空数据。这类索引还会占用大量不合理的存储空间，除非你的数据库系统支持从索引中剔除空值数据。部分数据库系统会将空字符串视作空值（系统会自动把写入字段的空字符串转换为 NULL），这也进一步增加了你判断是否为该字段建立索引的难度。

各大数据库系统处理索引内空值的方式各不相同，但所有主流数据库都遵循一条通用规则：**主键内的任意字段都不允许存储空值**。这是 ISO SQL 标准明确规定的硬性要求，也是统一规范。下文将分别讲解各类数据库对应的相关问题，以及它们对索引内空值、零长度字符串的处理逻辑。

### IBM DB2

除主键索引外，DB2 所有索引都会收录空值。

你在创建唯一索引时，可通过指定`EXCLUDE NULL KEYS`选项，主动将空值排除在唯一索引之外，示例见代码清单 2.1。

**代码清单 2.1 在 DB2 唯一索引中排除空值**

sql

```
CREATE UNIQUE INDEX ProductUPC_IDX
ON Products (ProductUPC ASC)
EXCLUDE NULL KEYS;
```

在索引判定逻辑中，DB2 将所有空值视为彼此相等。因此，若你没有为唯一索引添加非空限定条件，当你尝试向索引字段插入多条空值数据时，系统会抛出重复值错误。第二条写入的空值数据会被判定为与已有索引条目重复，而唯一索引不允许存在重复数据。

在 DB2 的非唯一索引中，你同样可以添加`EXCLUDE NULL KEYS`选项，禁止索引收录空值。当你明确该字段大部分数据均为空值时，该用法尤为实用 —— 这类使用`IS NULL`条件的查询，大多会直接走全表扫描，不会调用索引。剔除索引内的空值，还能有效缩减索引占用的数据库存储空间，具体用法见代码清单 2.2。

**代码清单 2.2 在 DB2 普通索引中排除空值**

sql

```
CREATE INDEX CustPhone_IDX
ON Customers(CustPhoneNumber)
EXCLUDE NULL KEYS;
```

DB2 不会将`VARCHAR`与`CHAR`类型字段内的空字符串视作空值。但如果在 Linux、UNIX、Windows 环境的 DB2 中开启甲骨文兼容模式，向`VARCHAR`字段存入空字符串时，该值会自动转为 NULL。更多细节可参考后文 Oracle 部分内容。

### Microsoft Access

Microsoft Access 会将空值纳入索引范围。由于主键字段禁止存储空值，因此你无法向主键字段写入 NULL。

你可以通过设置索引的**忽略空值**属性，让 Access 不在索引中存储空值，在可视化索引配置界面中即可完成该设置，该界面同时支持配置索引唯一属性与主键属性。

你也可以直接执行建索引 SQL 语句，通过`WITH IGNORE NULL`设置忽略空值属性，具体语法见代码清单 2.3。

**代码清单 2.3 在 Access 中通过 SQL 创建忽略空值的索引**

sql

```
CREATE INDEX CustPhoneIndex
ON Customers (CustPhoneNumber)
WITH IGNORE NULL;
```

你还可以使用`WITH DISALLOW NULL`语法禁止索引字段存入空值，该功能也可通过将字段必填属性设为开启来实现。

Access 判定所有空值互不相等，因此在建立唯一索引的字段中，允许存储多条带空值的数据行。Access 存在一处特殊规则：所有文本类型（等同于 VARCHAR）字段，都会自动剔除字段末尾的所有空格；通过可视化界面向字段存入空字符串时，系统会自动将其转为 NULL。

如果你尝试向主键字段或已开启必填属性的字段存入空字符串，系统会直接报错。你可以通过开启字段的**允许零长度字符**属性规避该问题。开启该属性后，Access 不会将空白内容、空字符串转为 NULL，但你需要在 SQL 语句或可视化界面中，用一对双引号明确写入空字符串。向已开启该属性的字段存入空字符串时，该字段值的长度即为 0。

### Microsoft SQL Server

SQL Server 与 DB2 规则相近，会收录索引内的空值，且判定所有空值彼此相等。主键的所有字段都不允许存入 NULL，建立唯一索引的字段中，仅允许存储一行带空值的数据。

想要在 SQL Server 中让索引剔除空值，必须创建**筛选索引**，示例见代码清单 2.4。

**代码清单 2.4 在 SQL Server 筛选索引中排除空值**

sql

```
CREATE INDEX CustPhone_IDX
ON Customers(CustPhoneNumber)
WHERE CustPhoneNumber IS NOT NULL;
```

需要注意：若查询语句中针对该字段使用`IS NULL`查询条件，SQL Server 不会调用该筛选索引执行检索。SQL Server 不会将`VARCHAR`类型的空字符串转换为 NULL，在上述筛选索引中，存储空字符串的数据行会正常被纳入索引范围。

### MySQL

MySQL 禁止主键字段存储空值。在索引规则中，MySQL 判定所有空值互不相等，因此建立唯一索引的字段中，允许存入多条带有空值的数据行。

MySQL 会默认将空值录入索引，且没有任何语法可以将空值从索引中剔除。针对`IS NULL`与`IS NOT NULL`查询条件，MySQL 都会正常调用可用索引。

MySQL 不会将空字符串转换为 NULL，NULL 无长度属性，而空字符串的长度固定为 0。

### Oracle

Oracle 默认不会为空值建立索引，同时主键字段也禁止存储空值。对于多列复合索引，只要索引内至少有一个字段为非空值，该行数据就会被录入索引。

你可以通过两种方式强制 Oracle 为空值建立索引：第一种是构建组合索引，将固定常量作为索引列之一；第二种是使用可处理空值的函数索引。

**代码清单 2.5 借助常量组合索引让 Oracle 收录空值**

sql

```
CREATE INDEX CustPhone_IDX
ON Customers (CustPhoneNumber ASC, 1);
```

你也可以使用`NVL()`函数转换空值，以此建立索引，用法见代码清单 2.6。

**代码清单 2.6 通过函数转换为空值建立索引**

sql

```
CREATE INDEX CustPhone_IDX
ON Customers (NVL(CustPhoneNumber, 'unknown'));
```

使用`NVL()`函数建立索引存在明显弊端：后续想要查询空值数据时，查询条件中也必须同步使用该函数，例如`WHERE NVL(CustPhoneNumber, 'unknown') = 'unknown'`。

Oracle 与 Microsoft Access 规则一致，认为`VARCHAR`类型的零长度空字符串等同于 NULL；但向`CHAR`类型字段存入空字符串时，只会填充空格，不会判定为空值。Oracle 没有类似 Access 的配置项，无法让`VARCHAR`字段独立存储空字符串。同时 Oracle 判定所有空值互不相等。

### PostgreSQL

PostgreSQL 禁止主键内存储空值。它与 MySQL、Microsoft Access 规则相同，判定所有空值互不相等，因此你可以为字段建立唯一索引，同时向该字段批量存入空值数据。

PostgreSQL 默认会将空值纳入索引，你可以通过添加`WHERE`筛选条件创建局部索引，以此剔除索引内的空值，示例见代码清单 2.7。

**代码清单 2.7 在 PostgreSQL 索引中排除空值**

sql

```
CREATE INDEX CustPhone_IDX
ON Customers(CustPhoneNumber)
WHERE CustPhoneNumber IS NOT NULL;
```

PostgreSQL 与 SQL Server 逻辑一致，不会将零长度字符串与空值互相转换，二者属于完全不同的数据形式。

### 牢记要点

1. 规划索引字段时，提前判断该字段是否会存储空值；
2. 若业务需要查询字段内的空值数据，但该字段大部分数据均为空值，尽量不要为该字段建立索引，该情况也说明数据表结构存在优化重构的必要；
3. 若需要快速查询字段内的非空数据，且所用数据库支持筛选索引 / 局部索引，可创建剔除空值的精简索引；
4. 不同数据库系统对索引内空值的处理逻辑差异极大，在为含空值的字段建索引前，务必熟知当前数据库的相关配置与使用规则。

## 要点 11：合理规划索引创建，减少索引扫描与数据全表扫描

依靠升级硬件资源优化性能固然可行，但通过优化查询语句，往往能以更低成本获得更显著的性能提升。数据库运行中十分常见的问题就是索引缺失或索引设计不合理，这会迫使数据库引擎处理更多数据，才能筛选出符合查询条件的数据行，这类低效检索行为就是索引扫描与全表扫描。

索引扫描与全表扫描，指数据库引擎需要遍历索引页或数据表数据页来匹配目标数据；与之相对的是索引精准定位检索，直接依托索引锁定满足查询条件的数据。数据表存储的数据量越大，扫描类检索方式消耗的执行时间就越长。

参考下方数据表创建语句：

sql

```
CREATE TABLE Customers (
CustomerID int PRIMARY KEY NOT NULL,
CustFirstName varchar(25) NULL,
CustLastName varchar(25) NULL,
CustStreetAddress varchar(50) NULL,
CustCity varchar(30) NULL,
CustState varchar(2) NULL,
CustZipCode varchar(10) NULL,
CustAreaCode smallint NULL,
CustPhoneNumber varchar(8) NULL
);
CREATE INDEX CustState ON Customers(CustState);
```

上述语句为数据表创建了两个索引：`CustomerID`被设为主键，系统会自动为该字段生成主键索引，额外执行的建索引语句则为`CustState`字段创建了普通索引。

执行`SELECT * FROM Customers WHERE CustomerID = 1`这类查询时，数据库会通过主键索引完成精准定位检索，再通过索引回表读取整行数据。

若执行`SELECT CustomerID FROM Customers WHERE CustomerID = 25`，由于查询所需字段全部包含在主键索引内，无需执行回表操作，仅依靠索引精准检索即可完成查询。

再看查询语句`SELECT * FROM Customers WHERE CustState = 'TX'`，虽然我们已经为`CustState`建立索引，但该索引并非唯一索引，数据库需要遍历整条索引匹配所有符合条件的数据，也就是索引扫描；同时由于查询字段未全部存在于索引中，还需要回表读取原始数据表数据。

最后，执行`SELECT CustomerID FROM Customers WHERE CustAreaCode = '905'`时，该字段无任何索引，数据库只能执行全表扫描，逐行遍历整张数据表匹配查询条件。

多数场景下，全表扫描与索引扫描的直观差距并不大，二者都需要遍历数据条目匹配目标值。但索引的数据体量更小，且结构专为遍历检索设计，当你只需要查询数据表内少量数据行时，索引扫描效率更高；若查询数据量占数据表总量三成左右，索引将不再具备提速优势。该比例并非固定标准，不同数据库引擎的扫描效率临界值各不相同。

事实上，部分场景下全表扫描的查询性能反而更优，这主要取决于查询结果集占整张数据表数据量的比例。但绝大多数业务场景中，都需要为数据表配置合理索引。想要深入了解相关内容，可参考本书第 46 条技巧：读懂执行计划运行原理。

切记不要认为索引可以解决所有数据检索问题。大量冗余索引不仅无法提升查询速度，还会拖慢数据更新操作的执行效率。每当你修改索引关联字段的数据时，系统都需要同步更新对应索引结构，产生大量磁盘读写操作；且索引的存储结构更为规整，索引更新的资源开销通常高于数据表原生数据更新。

面向高频增删改查的业务数据表，每一条索引的创建都必须具备实际业务价值；而面向几乎无数据变更的数据分析型数据库，可放心搭建各类索引优化查询效率，这类数据库也十分适合采用反范式设计，具体可参考第 9 条技巧。但单纯堆砌索引也并非万能解决方案。

目前绝大多数数据库管理系统最常用的索引结构为 B 树索引。部分数据库还支持哈希索引、空间索引等专用索引结构，而 B 树索引通用性最强，应用范围也最广。本书不再深度讲解 B 树底层结构，仅做简要概述：B 树索引由根节点、多级中间节点、叶子节点依次构成，最终由叶子节点指向数据表实际存储的数据。

B 树索引对查询性能的提升效果，由索引类型决定，主要分为聚集索引与非聚集索引两大类。聚集索引会按照索引定义的字段顺序，调整数据表数据的物理存储顺序。由于数据表数据仅能按照一种顺序物理排序，因此**单张数据表仅能创建一个聚集索引**。

至少在 SQL Server 中，聚集索引的叶子节点会直接存储完整数据表数据。非聚集索引的整体结构与聚集索引一致，主要存在两处核心区别：

1. 非聚集索引的排序规则，可以和数据表物理数据排序互不相同；
2. 非聚集索引的叶子节点仅存储索引键与数据行定位标识，不会直接存储完整业务数据。

**补充说明**

在 Oracle 中，数据表数据不会依据索引字段完成物理排序。数据库优化器会通过聚集因子统计索引与数据表数据排序的契合程度，以此作为选择执行计划的重要依据。

非聚集索引检索性能是否优于全表扫描，取决于数据表体量、数据存储分布、单行数据长度以及查询结果集占比。行业通用经验：当查询结果数据量达到数据表总量的 10% 及以上时，全表扫描的执行效率通常会超越非聚集索引检索；而聚集索引即便检索大批量数据，性能依旧优于全表扫描。

另一项重要设计原则是贴合日常业务的数据访问形式。若某个字段几乎不会出现在查询条件中，为其建立索引毫无意义。如同上文举例，字段数据重复率高、字段区分度低时，索引也无法发挥提速作用。如果使用索引后，数据库引擎需要读取的数据量没有缩减到最低标准比例，数据库就会放弃调用该索引。

除此之外，数据表体量过小也无需建立索引。主流数据库会直接将小型数据表加载至内存中，数据存入内存后，无论是否建立索引，检索速度都很快。数据表大小的判定标准，由数据总行数、单行数据大小、数据页存储规格以及数据库服务器可用内存共同决定。

联合索引的字段组合顺序同样至关重要。如果多数业务查询都会同时用到多个固定字段，就需要创建包含这些字段的联合索引；单独为每个字段建立单列索引，未必能生成高效的查询执行计划。创建多字段联合索引时，字段的排列顺序尤为关键。

例如部分查询仅单独检索姓氏字段，另一部分查询同时检索姓名与姓氏字段，联合索引就需要将姓氏字段放在前面、名字字段放在后面，顺序颠倒会直接导致索引失效。

**合理联合索引创建语句**

sql

```
CREATE INDEX CustName
ON Customers(CustLastName, CustFirstName);
```

**不合理联合索引创建语句**

sql

```
CREATE INDEX CustName
ON Customers(CustFirstName, CustLastName);
```

### 牢记要点

1. 梳理业务数据访问特征，按需创建能够优化查询性能的合理索引；
2. 定期核查已创建索引，确保索引能够在实际业务查询中被正常调用。

## 要点 12：索引的用途不止于数据筛选

数据库索引是独立存在于数据库中的专用数据结构，每一个索引都会占用独立的磁盘存储空间，且索引内存储了数据表索引字段的数据副本，属于典型的数据冗余。但这类冗余具备实用价值：索引能够快速定位目标数据，无需逐行遍历整张数据表，以此大幅提升数据表的数据检索效率。除此之外，索引还具备诸多其他实用作用。

`WHERE`子句用于定义 SQL 语句的查询筛选条件，这也是索引最核心的用途 —— 快速匹配筛选数据。编写不合理的`WHERE`筛选条件，是造成查询语句运行缓慢的首要原因。

字段是否建立索引，会直接影响多表关联查询的执行效率。本质上，关联查询能够将范式化数据模型中的分散数据，整合为适配业务处理的非范式化数据形态。多表关联操作需要读取分布在不同数据页内的数据，磁盘寻址延迟对其影响极大，合理设计索引能够大幅缩短关联查询的响应耗时。

数据库查询常用的三种关联算法分别为：嵌套循环关联、哈希关联、排序合并关联，三类算法有一个共同特点：单次仅能完成两张数据表的关联匹配。涉及多张数据表的 SQL 查询，需要分步执行：先将两张数据表关联生成临时结果集，再将该结果集与下一张数据表继续关联，依次循环执行。

嵌套循环关联是最基础的关联查询算法，可理解为两层嵌套查询逻辑：外层驱动查询从一张数据表中读取数据，内层查询再依据外层每一行数据，从另一张数据表中匹配对应数据。因此，关联字段建立索引，能够最大化发挥嵌套循环关联的性能优势。当外层驱动查询的结果集数据量较小时，嵌套循环关联执行效率极佳；若结果集体量过大，数据库优化器通常会自动切换为其他关联算法。

哈希关联会先将其中一张关联表的候选数据载入哈希表，再逐行遍历另一张数据表，快速匹配哈希表内的数据。优化哈希关联的索引设计思路，与嵌套循环关联完全不同。由于哈希关联依靠哈希表完成数据匹配，无需为关联字段单独建立索引；能够优化哈希关联性能的索引，仅为`WHERE`筛选条件字段索引与关联条件字段筛选索引，这也是哈希关联唯一会调用索引的场景。实际应用中，优化哈希关联性能最有效的方式，是从横向缩减数据行数、纵向精简查询字段，以此缩小哈希表的存储体量。

排序合并关联要求两张关联数据表的数据，都按照关联条件完成排序，之后再像拉链拼接一样合并两组有序数据集。排序合并关联在诸多特性上与哈希关联较为相似：仅为关联字段建立索引无法优化性能，需要为独立筛选条件建立索引，一次性读取所有候选数据。排序合并关联有一处独有特性：关联表的先后顺序不会对执行逻辑与运行性能造成任何影响，而其余两类关联算法会受左右外连接方向限制，固定关联执行顺序。排序合并关联甚至可同时实现左右双向外连接，也就是全外连接。

在数据源完成排序的前提下，排序合并关联性能表现优异，但对两组数据同时进行排序操作会消耗大量系统资源，因此该算法日常使用率较低。但如果存在与排序规则匹配的索引，就能直接省略排序步骤，充分发挥排序合并关联的性能优势。反观哈希关联仅需预处理其中一张数据表的数据，在多数场景下实用性更强。

上文针对关联算法的讲解存在一定理论性。虽然在 SQL Server 与 Oracle 中，可通过查询提示强制指定关联算法，但最优做法依旧是交由数据库优化器，根据当前实际数据分布自动匹配最合适的算法，同时搭配规范合理的索引设计。

**补充说明**

MySQL 数据库暂不支持哈希关联与排序合并关联两种算法。

索引还可依托数据聚集特性优化查询。数据聚集指将业务中连续访问的数据物理存储至相邻位置，以此减少数据访问时的 I/O 操作次数。参考下方查询语句：

sql

```
SELECT EmployeeID, EmpFirstName, EmpLastName
FROM Employees
WHERE EmpState = 'WA'
AND EmpCity LIKE '%ELLE%';
```

查询条件中，`EmpCity`字段使用前缀通配符模糊匹配，这类写法无法调用索引，只能执行全表扫描；但`EmpState`字段的筛选条件十分适配索引优化。如果满足筛选条件的数据集中存储在少数几个数据块内，数据表访问带来的性能损耗可以忽略不计；反之，若目标数据零散分布在大量不同数据块中，多次读取数据块会严重拖慢查询效率。简单来说，查询性能直接取决于目标数据的物理存储分布状态。

调整数据表内数据行的排列顺序，使其匹配索引排序规则，能够优化查询性能，但该方案适用场景极少 —— 数据表数据仅能按照一种物理顺序存储，也就意味着该方式仅能针对单一索引做定向优化。

创建如下结构的索引，将等值筛选字段放在索引首位，能够有效匹配这类业务查询：

sql

```
CREATE INDEX EmpStateName
ON Employees (EmpState, EmpCity);
```

如果能让查询语句无需访问原始数据表，仅依靠索引就能获取全部所需数据，查询性能还能进一步提升。参考下述业务数据表：

sql

```
CREATE TABLE Orders (
OrderNumber int IDENTITY (1, 1) NOT NULL,
OrderDate date NULL,
ShipDate date NULL,
CustomerID int NULL,
EmployeeID int NULL,
OrderTotal decimal NULL
);
```

若业务需要统计每位客户的订单总金额，执行如下查询：

sql

```
SELECT CustomerID, Sum(OrderTotal) AS SumOrderTotal
FROM Orders
GROUP BY CustomerID;
```

创建下方覆盖索引后，查询所需全部字段都包含在索引内，执行过程中无需访问原始数据表：

sql

```
CREATE INDEX CustOrder
ON Orders (CustomerID, OrderTotal);
```

**补充说明**

部分数据库中，当数据表数据量极小时，数据库依旧会优先选择全表扫描，而非调用上述覆盖索引。

需要注意：即便查询结果集数据量更少，只要查询字段超出索引包含范围，数据库依旧大概率执行全表扫描，示例如下：

sql

```
SELECT CustomerID, Sum(OrderTotal) AS SumOrderTotal
FROM Orders
WHERE OrderDate > '2015-12-01'
GROUP BY CustomerID;
```

索引同样会直接影响`ORDER BY`排序子句的执行效率。数据排序属于高资源消耗操作，不仅会占用大量 CPU 资源，还需要数据库临时缓存所有查询结果，必须读取完全部数据源后，才能输出第一条排序结果。

索引本身会按照固定规则有序存储索引数据，借助这一特性，可直接利用索引完成排序，省略查询语句中额外的排序操作。

关联查询可通过数据流推送机制，将临时结果实时传递至下一级关联逻辑，无需完整存储全部临时结果集，以此节省内存资源；但排序操作必须完整处理完所有数据源，才能输出排序结果。

以 B 树索引为代表的有序索引，提前将数据完成排序存储，能够直接适配`ORDER BY`排序需求，省去实时排序的资源开销，还能边读取索引数据边输出结果，实现数据流推送式查询。想要实现该效果，用于筛选数据的索引，必须同时覆盖排序子句中用到的所有字段。

数据库支持正向、反向双向读取索引，即便索引排序方向与`ORDER BY`指定排序方向完全相反，依旧可以实现流式排序输出，且不会影响索引在筛选条件中的正常使用。但在多字段联合索引中，字段的排序方向会对索引使用效果产生明显影响。

**补充说明**

MySQL 在索引定义语句中，会忽略`ASC`与`DESC`排序修饰符。

### 牢记要点

1. `WHERE`筛选条件中的字段是否建立索引，直接决定查询语句的执行性能；
2. `SELECT`查询字段是否被索引覆盖，同样会影响整体查询效率；
3. 字段索引状态，会改变多表关联查询的执行效率；
4. 索引能够优化`ORDER BY`排序语句的执行效率；
5. 数据表创建过多索引，会直接拖慢数据写入、修改类操作的运行速度。

## 要点 13：切勿过度使用触发器

绝大多数关系型数据库管理系统，都支持在数据表执行新增、删除、修改操作时，自动触发执行存储过程类触发器程序。虽然很多开发人员习惯借助触发器清理孤立冗余数据，但第 6 条技巧中提到的外键引用完整性约束，实现方式更为简便，执行效率也更高。触发器也可用于自动更新计算类字段数据，但第 5 条技巧已经说明，存储计算类字段本身就存在诸多弊端，也存在更优质的替代实现方案。

引用完整性约束依靠各类约束规则实现，由数据库引擎自动强制执行数据表的数据完整性，明确限定字段允许存储的数据格式与范围，是保障数据完整性的标准实现方式。相较于数据操作语言触发器、自定义规则、字段默认值，优先使用约束规则是行业通用最优方案。数据库查询优化器还会依托各类约束定义，生成高性能的查询执行计划。

为数据表新增数据配置引用完整性约束后，向从表新增数据时，数据库会自动校验主表中是否存在对应关联主键，无匹配主键则直接禁止新增操作。同时还可为数据修改、数据删除操作配置级联约束行为：级联同步、禁止操作、设为空值、设为默认值。

下方 SQL 借助引用完整性约束，实现删除主表数据时同步清理从表孤立数据：

sql

```
ALTER TABLE Order_Details
ADD CONSTRAINT fkOrder FOREIGN KEY (OrderNumber)
REFERENCES Orders (OrderNumber) ON DELETE CASCADE;
```

而借助触发器实现完全相同业务逻辑的写法如下：

sql

```
CREATE TRIGGER DelCascadeTrig
ON Orders
FOR DELETE
AS
DELETE Order_Details
FROM Order_Details, deleted
WHERE Order_Details.OrderNumber = deleted.OrderNumber;
```

正如上文所述，依靠约束实现引用完整性，运行效率与资源消耗都远优于触发器方案。

如第 5 条技巧所言，触发器也常被用于自动计算更新字段数据，下方 SQL 为 SQL Server 专用触发器，可在订单明细表数据发生变动时，自动更新订单表内的订单总金额字段。

sql

```
CREATE TRIGGER updateOrdersOrderTotals
ON Orders
AFTER INSERT, DELETE, UPDATE
AS
BEGIN UPDATE Orders
SET OrderTotal = (
SELECT SUM(QuantityOrdered * QuotedPrice)
FROM Order_Details OD
WHERE OD.OrderNumber = Orders.OrderNumber
)
WHERE Orders.OrderNumber IN(
SELECT OrderNumber FROM deleted
UNION
SELECT OrderNumber FROM inserted
);
END;
```

对比触发器复杂的编写逻辑，直接为数据表定义计算字段的方式更加简洁，且运行性能也更具优势。

数据库设计中，实现同一业务需求往往存在多种技术方案，触发器虽是维护数据一致性的方案之一，但绝非最优解。当然部分特定场景下，触发器依旧是不可替代的选择：

1. 维护冗余数据、衍生同步数据：非范式化数据库存在大量数据冗余，可依靠触发器完成多表数据实时同步；
2. 复杂字段约束校验：当字段约束规则需要关联本表其他数据行、或是关联其他数据表数据时，触发器是最适配的实现方式；
3. 自定义复杂字段默认值：依托其他字段、其他数据表的数据，动态生成字段默认值；
4. 跨数据库引用完整性管控：关联数据表分布在两个不同数据库时，依靠触发器保障跨库数据引用关系合法有效。

**补充建议**

必须使用触发器时，建议将触发器绑定在视图而非原生数据表上。该方式能够灵活控制触发时机，避免大批量数据导入导出时误触发触发器，仅保留业务正常操作时的触发逻辑。

**补充说明**

不同数据库管理系统对约束、默认值的功能限制各不相同，例如部分数据库不支持在检查约束中嵌套子查询，这类场景只能改用触发器实现。开发前务必查阅对应数据库官方文档，优先选用非触发器方案实现业务需求。

### 从 Microsoft Access 数据库升级迁移

很多开发者都会疑惑：从 Access 数据库升级迁移时，该选用引用完整性约束还是触发器维护数据表关联关系。

迁移至 SQL Server 数据库时，升级向导的数据表属性导出界面，提供了两种引用完整性实现方案，具体选择需要依据原始 Access 数据表的关联配置决定。

选用引用完整性约束方案时，SQL Server 会依据 Access 中原有的数据表关联关系重建数据表与关联规则，但 SQL Server 的引用完整性约束，不支持级联更新、级联删除功能，迁移后会直接丢失 Access 中原有的级联联动逻辑。

在 Access 中打开数据表关联设置界面，双击数据表之间的关联连线，即可查看三项核心配置：启用引用完整性、级联更新关联字段、级联删除关联数据。

仅开启启用引用完整性时，可直接选用升级向导的约束方案；只要开启了任意一项级联联动配置，迁移时就必须选用触发器方案。

Access 支持数据表自关联场景下的级联更新与级联删除，但 SQL Server 并不支持该功能。因此下方在 Access 中可正常运行的自关联约束语句，在 SQL Server 中执行会直接报错：

sql

```
CREATE TABLE OrgChart (
employeeID INTEGER NOT NULL PRIMARY KEY,
manager_employeeID INTEGER
CONSTRAINT SelfReference FOREIGN KEY (manager_employeeID)
REFERENCES OrgChart (employeeID)
ON DELETE SET NULL
ON UPDATE CASCADE
);
```

**补充说明**

自 2010 版本起，Access 新增数据宏功能，作用等同于 SQL Server 中的触发器。如果原有 Access 数据库大量使用数据宏，迁移至 SQL Server 时，最优方案就是转换为 SQL Server 触发器。

### 牢记要点

1. 依托约束规则实现引用完整性、依托数据库原生功能实现计算字段，运行性能更优，建议作为项目开发默认首选方案；
2. 触发器跨数据库兼容性极差，为某一款数据库编写的触发器，几乎无法不经修改直接在其他数据库中运行；
3. 仅在无替代方案的刚需场景下使用触发器，同时尽量保证触发器具备幂等性。

## 要点 14：合理使用筛选索引，定向收录或排除指定范围数据

业务查询几乎很少需要读取数据表内所有数据行，因此开发者都会添加`WHERE`筛选条件缩减结果集。但缩减查询结果集，并不代表能够有效减少数据查询产生的 I/O 开销。

筛选索引（SQL Server）、局部索引（PostgreSQL）属于非聚集索引，仅收录数据表内部分指定数据行。相较于传统全覆盖非聚集索引，这类索引数据体量更小，传统索引的数据行数与数据表行数基本保持一比一对应关系。

借助筛选索引能够同时优化查询性能、节省磁盘存储空间，索引内数据行数更少，查询所需的 I/O 操作也随之减少。在数据库支持的前提下，数据表分区功能也能实现与筛选索引相近的效果。

**版本限制说明**

2016 及更早版本的 Access、5.6 及更早版本的 MySQL，均不支持筛选索引功能；Oracle 与 DB2 无原生筛选索引语法，但可通过其他语法模拟实现同等效果。

筛选索引的创建方式，就是在常规建索引语句后追加`WHERE`筛选条件。如果某个字段值频繁出现在查询筛选条件中，且该字段值仅占数据表总数据量的极小比例，创建筛选索引能够带来极为明显的性能提升。

你可以通过筛选条件，让索引仅收录非空数据或者仅收录空值数据，具体空值相关设计思路可参考第 10 条技巧。筛选索引的`WHERE`条件内，仅能使用确定性函数，且不支持`OR`逻辑运算符。

**SQL Server 额外限制**

筛选条件不能引用计算字段、自定义数据类型字段、空间数据类型字段、层级标识字段，同时禁止使用`BETWEEN`、`NOT IN`、`CASE`语法。

筛选条件内用到的字段，无需必须加入索引字段列表。

例如商品数据表包含库存数量字段，想要专门优化低库存商品查询，可创建如下筛选索引：

sql

```
CREATE NONCLUSTERED INDEX LowProducts
ON Products (ProductNumber)
WHERE QuantityOnHand < 10;
```

文档管理系统也是筛选索引的常用业务场景，依据文档状态字段定向创建索引，优化指定状态文档查询：

sql

```
CREATE NONCLUSTERED INDEX PendingDocuments
ON DocumentStatus (DocumentNumber, Status)
WHERE Status IN ('Pending publication', 'Pending expiration');
```

你也可以针对同一个字段，创建多条不同筛选规则的筛选索引：

sql

```
CREATE NONCLUSTERED INDEX PendPubDocuments
ON DocumentStatus (DocumentNumber, Status)
WHERE Status = 'Pending publication';
CREATE NONCLUSTERED INDEX PendExpDocuments
ON DocumentStatus (DocumentNumber, Status)
WHERE Status = 'Pending expiration';
```

第 12 条技巧提到，索引可以省略`ORDER BY`子句的实时排序操作，筛选索引能够进一步拓展该优化思路。

针对需要排序的查询语句，创建匹配筛选条件与排序规则的筛选索引，直接省略排序流程：

sql

```
SELECT ProductNumber, ProductName
FROM Products
WHERE CategoryID IN (1, 5, 9)
ORDER BY ProductName;

CREATE INDEX SelectProducts
ON Products(ProductName, ProductNumber)
WHERE CategoryID IN (1, 5, 9);
```

筛选索引与局部索引同样存在使用限制：条件内无法使用`GETDATE()`这类动态时间函数，不能创建动态滚动时间范围筛选索引，筛选条件必须为固定常量值。

### 牢记要点

1. 仅当索引仅对数据表内小范围数据生效时，使用筛选索引才能有效节省存储空间；
2. 借助筛选索引，可仅为数据表内部分数据行设置唯一约束；
3. 筛选索引可直接省略查询语句中的排序操作，优化排序查询性能；
4. 可对比数据表分区功能，在无需额外维护索引的前提下，实现和筛选索引相近的优化效果。

## 要点 15：优先使用声明式约束，替代代码逻辑校验

数据库数据完整性的重要性不言而喻。开发过程中需要明确每个字段的合法取值范围，同时制定对应规则强制执行，这也是保障数据库稳定运行的基础。SQL 语法内置了多类约束规则，能够高效实现数据完整性管控。

SQL 约束用于为数据表字段定义数据规范，数据表执行新增、修改、删除所有数据操作时，系统都会自动校验约束规则，一旦触发规则冲突，对应数据操作会直接终止执行。

### 六大常用数据库约束

1. **NOT NULL 非空约束**：数据表字段默认允许存储空值，非空约束强制字段必须录入有效数据，禁止存入 NULL；
2. **UNIQUE 唯一约束**：限定指定字段内不能存入重复数据，适用于非主键字段做唯一性校验，唯一约束字段允许存储空值；
3. **PRIMARY KEY 主键约束**：兼具唯一性与非空性，能够唯一标识数据表内每一条数据行，一张数据表仅能定义一个主键约束，可定义多个唯一约束；
4. **FOREIGN KEY 外键约束**：当前数据表的字段，关联映射另一张数据表的主键字段，用于维护多表之间的关联关系；
5. **CHECK 检查约束**：可作用于单字段或整张数据表，单字段检查约束限定字段合法取值范围，表级检查约束可依据同一行内其他字段数据，限定当前字段取值；
6. **DEFAULT 默认值约束**：为字段预设默认填充值，新增数据未主动指定该字段值时，系统自动填入默认值。

**标准定义补充**

依据 SQL 标准定义，默认值约束不属于正式数据约束，但日常开发中常搭配非空约束使用，用于落地各类业务数据规则。

**数据库特性补充**

SQL Server 的唯一索引约束字段仅允许存入单个空值；DB2 唯一索引默认同样仅支持单个空值，添加非空筛选条件后可彻底禁止空值录入。

约束规则既可以在`CREATE TABLE`建表语句中同步定义，也可通过`ALTER TABLE`语句后期追加修改。

除依托约束实现声明式引用完整性之外，还可依靠程序化逻辑代码实现数据规则校验，常见实现方式包含客户端业务代码、存储过程、触发器三类。

在业务系统开发中，开发者固然可以编写业务代码强制校验数据库数据规则，但该实现方式存在明显弊端。数据规则与数据表结构深度绑定，理应交由数据库层统一管控，而非分散在各类应用程序中。将数据校验逻辑下沉至数据库层，能够保障所有业务端遵循同一套数据规范，统一数据修改逻辑，避免重复编写大量同质化校验代码。

借助存储过程管控数据完整性，虽然能将规则统一收拢至数据库内，但开发与维护难度更高；同时必须严格管控用户权限，仅开放存储过程执行权限、禁止用户直接操作原生数据表，额外增加了权限管控工作量。

触发器同样可以实现引用完整性约束与级联联动操作，开发者依旧可以使用常规增删改语句操作数据表，无需改动业务 SQL，但第 13 条技巧已经详细讲解过触发器存在的各类缺陷与隐患。

### 牢记要点

1. 优先使用数据库原生约束规则落地各类数据完整性管控需求；
2. 数据库查询优化器能够识别各类约束定义，依托约束规则生成执行效率更高的查询执行计划。

## 要点 16：明确项目所用 SQL 方言，适配编写对应 SQL 语句

SQL 是行业通用的数据库访问标准语言。即便 SQL 先后通过美国国家标准协会、国际标准化组织正式标准化，但不同厂商推出的数据库产品，并未完全严格遵循统一标准，各类数据库的 SQL 语法存在大量差异化设计。

日期时间语法、字符串拼接方式、空值处理逻辑、字符串大小写匹配规则等细节，不同数据库实现方式各不相同。开发者必须清楚项目所用数据库对应的 SQL 方言，才能编写出适配可用的高效 SQL 语句。

### 结果集排序规则

SQL 标准仅对空值排序做出两项基础规定：所有空值排序优先级一致；空值统一排在所有非空数据的最前方或最后方，并未划定统一排序顺序，这也导致各大数据库空值排序规则各不相同：

1. IBM DB2：空值排序优先级高于所有非空值；
2. Microsoft Access：空值排序优先级低于所有非空值；
3. Microsoft SQL Server：空值排序优先级低于所有非空值；
4. MySQL：默认空值排在非空值前方，存在未公开语法可调整排序逻辑；
5. Oracle：默认空值排序优先级最高，可通过`NULLS FIRST`、`NULLS LAST`手动调整；
6. PostgreSQL：默认空值排序优先级最高，8.3 及以上版本支持手动调整空值排序位置。

### 结果集行数限制

SQL 标准定义了三种限定查询结果行数的语法：`FETCH FIRST`、行号窗口函数、游标语法，不同数据库支持情况各不相同。

1. IBM DB2：全面支持所有标准行数限制语法；
2. Microsoft Access：不支持任何标准行数限制语法；
3. Microsoft SQL Server：支持窗口函数与游标语法；
4. MySQL：专属`LIMIT`语法 + 游标标准语法；
5. Oracle：支持窗口函数、游标语法与伪列`ROWNUM`；
6. PostgreSQL：全面支持所有标准行数限制语法。

### 布尔数据类型

SQL 标准将布尔类型设为可选数据类型，合法布尔值包含`TRUE`、`FALSE`、`NULL/UNKNOWN`，且定义`TRUE`数值优先级高于`FALSE`。

1. IBM DB2：无原生布尔数据类型；
2. Microsoft Access：提供不可为空的是 / 否专用类型；
3. Microsoft SQL Server：无原生布尔类型，常用 BIT 类型替代；
4. MySQL：布尔类型仅为 TINYINT (1) 的别名，并非标准布尔类型；
5. Oracle：无原生布尔数据类型；
6. PostgreSQL：严格遵循 SQL 布尔类型标准，支持 NULL 布尔值，不识别 UNKNOWN。

### SQL 内置函数

内置函数是各大数据库语法差异最大的板块，本文不再逐一罗列标准函数与数据库专属函数差异，开发时优先查阅对应数据库官方函数文档即可，附录中整理了常用日期时间类函数用法可供参考。

### 唯一约束规则

SQL 标准规定：启用唯一约束的字段，默认必须同时开启非空约束；仅数据库开启专属空值兼容特性后，唯一约束字段才可存储空值，且空值数量不受限制。

1. IBM DB2：遵循基础唯一约束规则，不支持空值兼容拓展特性；
2. Microsoft Access：完全遵循 SQL 唯一约束标准；
3. Microsoft SQL Server：支持空值兼容特性，但唯一约束字段仅允许存储单个空值；
4. MySQL：完整遵循包含空值兼容在内的全套唯一约束标准；
5. Oracle：支持空值兼容特性，单列唯一约束可存储任意数量空值，多列唯一约束存在特殊判定逻辑；
6. PostgreSQL：完整遵循全套唯一约束标准。

### 牢记要点

1. 符合 SQL 标准的 SQL 语句，未必能在指定数据库中正常运行；
2. 相同业务 SQL 语句，在不同数据库中运行的性能损耗与执行逻辑存在明显差异；
3. 编写 SQL 前务必查阅当前数据库官方开发文档；
4. 可参考专业数据库语法对比站点，快速查阅各类数据库语法差异化细节。

## 要点 17：合理利用索引存储计算结果

第 11 条技巧中提到，优先使用函数运算替代直接存储计算字段。而实际开发中，各类数据库均支持为函数运算生成的计算结果建立索引，大幅削弱函数运算带来的查询性能损耗。

1. DB2：大型机版本 9 及以上支持函数索引，桌面端版本 10.5 及以上开放该功能，不支持自定义函数建索引，替代方案为新建物理字段存储运算结果，绑定触发器维护字段数据后再建索引；
2. MySQL：5.7 及以上版本支持为生成列建立索引，低版本沿用 DB2 替代方案；
3. Oracle：8i 版本起支持函数索引，11g 版本新增虚拟字段功能；
4. PostgreSQL：7.2 版本起兼容表达式索引，7.4 版本全面完善该功能；
5. SQL Server：2000 版本起支持为计算字段建立索引，同时必须满足五项硬性条件：字段归属主体一致、运算逻辑具备确定性、运算不依赖浮点型数据、计算结果非大文本类型、创建字段时 ANSI_NULLS 会话参数必须开启。

创建函数索引最常用的业务场景，就是实现不区分大小写查询。SQL Server、MySQL、Access 默认查询语句大小写不敏感，其余数据库默认严格区分大小写。

区分大小写数据库中，直接使用字段等值查询无法匹配不同大小写数据，必须嵌套大小写转换函数：

sql

```
SELECT EmployeeID, EmpFirstName, EmpLastName
FROM Employees
WHERE UPPER(EmpLastName) = 'VIESCAS';
```

筛选条件中对数据表原生字段嵌套函数，会导致查询语句失去索引适配性，数据库只能执行全表扫描。为解决该问题，直接依托大小写转换函数创建函数索引即可：

sql

```
CREATE INDEX EmpLastNameUpper
ON Employees (UPPER(EmpLastName));
```

DB2、Oracle、PostgreSQL、SQL Server 的函数索引，不仅支持`UPPER`这类系统内置函数，还支持字段四则运算表达式，符合规范的自定义函数也可用于创建索引。

**SQL Server 专属规则**

SQL Server 无法直接依托函数创建索引，必须先在数据表中定义计算字段，再为计算字段建立索引。

自定义函数用于创建索引存在核心硬性限制：**函数运算逻辑必须具备确定性**。

例如依托系统当前时间计算年龄的自定义函数，运算结果会随时间动态变化，属于非确定性函数，无法用于创建索引。即便强行声明函数具备确定性并完成建索引操作，索引内存储的固定年龄数据也不会随时间自动更新，完全失去实用价值。

函数索引能够极大优化特殊条件查询性能，但开发者切忌无节制批量创建函数索引。数据表内索引数量越多，数据新增、修改、删除操作的维护开销就越大，函数索引也极易产生大量冗余无效索引。

### 牢记要点

1. 把控索引创建数量，杜绝盲目建索引；
2. 结合实际业务访问场景规划索引，仅在刚需场景下创建筛选索引、函数索引等特殊索引。

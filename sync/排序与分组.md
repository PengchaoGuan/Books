# 第六章 排序与分组

排序是一项极度消耗系统资源的操作。它会占用大量 CPU 运算时间，而最主要的问题在于，数据库必须临时缓存运算结果。毕竟排序操作必须读取完所有输入数据之后，才能输出第一条结果。排序操作无法以流水线形式执行，这一问题在处理大规模数据集时会变得尤为突出。

索引能够为被索引的数据提供有序的数据形态，这一原理在第一章中已有讲解。我们也可以理解为，索引是以预排序的方式存储数据。事实上，索引自身的排序规则，和在`ORDER BY`子句中使用对应字段排序的效果完全一致。因此我们借助索引规避`ORDER BY`子句的显式排序操作，也就不足为奇了。

颇具矛盾的一点是，在面对大规模数据集时，索引范围扫描同样会变得效率低下，后续如果还要进行回表查询更是如此，这会抵消掉免去排序操作所节省的性能开销。在这种场景下，全表扫描搭配显式排序的执行方式，速度反而可能更快。而评估各类执行方案、选出最优执行计划，正是数据库优化器的本职工作。

不过依托索引实现有序查询，不仅能省去排序的资源开销，还无需处理完全部输入数据，就能优先返回首批查询结果。也就是说，这种排序方式可以以流水线模式运行。第七章《分批结果集》将会讲解如何利用流水线式执行，编写高效的分页查询语句。这种流水线式排序的实用价值极高，作者将其称作**索引的第三大核心能力**。

本章将讲解如何借助索引实现流水线式`ORDER BY`排序执行，同时着重梳理索引与`WHERE`条件、升序降序修饰符之间的配合规则，最后再把这套优化思路应用到`GROUP BY`分组查询当中。

## 为排序字段建立索引

如果已有索引能够按照查询所需顺序返回数据行，那么带有`ORDER BY`子句的 SQL 语句，就无需再执行显式排序操作。这就意味着，同一份用于匹配`WHERE`查询条件的索引，还必须同时适配`ORDER BY`的排序规则。

举个示例，下方查询筛选出昨日销售数据，并按照销售日期、产品编号进行排序：

sql

```
SELECT sale_date, product_id, quantity
FROM sales
WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
ORDER BY sale_date, product_id;
```

数据库中原本存在基于销售日期建立的索引，可用于匹配`WHERE`筛选条件，但依旧需要额外执行显式排序，来完成排序需求。

plaintext

```
---------------------------------------------------------------
|Id | Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 | SELECT STATEMENT | | 320 | 18 |
| 1 | SORT ORDER BY | | 320 | 18 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES | 320 | 17 |
|*3 | INDEX RANGE SCAN | SALES_DATE | 320 | 3 |
---------------------------------------------------------------
```

索引范围扫描本身就会按照索引自身顺序返回数据，想要利用这一特性，只需调整索引结构，让索引字段顺序与排序字段顺序保持一致即可。

sql

```
DROP INDEX sales_date;
CREATE INDEX sales_dt_pr ON sales (sale_date, product_id);
```

plaintext

```
---------------------------------------------------------------
|Id | Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 | SELECT STATEMENT | | 320 | 300 |
| 1 | TABLE ACCESS BY INDEX ROWID| SALES | 320 | 300 |
|*2 | INDEX RANGE SCAN | SALES_DT_PR | 320 | 4 |
---------------------------------------------------------------
```

即便查询语句中依旧保留`ORDER BY`子句，执行计划里的`SORT ORDER BY`排序操作已经彻底消失，数据库直接沿用索引自带的有序性，跳过了显式排序流程。

**重点**

当索引字段排序顺序与`ORDER BY`子句排序规则一致时，数据库可以省略显式排序操作。

新的执行计划虽然精简了执行步骤，但整体执行成本却出现了明显上涨，原因是新建索引的聚集因子表现更差（详见 133 页《聚集因子自动优化机制》）。在此需要明确一点：执行成本数值，并非永远都能精准代表实际执行开销。

想要实现该排序优化，只需要保证索引扫描范围内的数据，符合`ORDER BY`的排序规则即可。因此在这个示例中，仅按产品编号排序，同样可以触发该优化：

sql

```
SELECT sale_date, product_id, quantity
FROM sales
WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
ORDER BY product_id;
```

从示意图 6.1 能够看出，在当前索引扫描区间内，产品编号是唯一有效的排序依据，索引自带顺序完全匹配查询排序需求，数据库依旧可以省去排序操作。

如果扩大索引的扫描范围，这种优化效果就会失效：

sql

```
SELECT sale_date, product_id, quantity
FROM sales
WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
ORDER BY product_id;
```

该查询不再仅筛选昨日数据，而是查询昨日至今的所有销售记录，扫描范围涵盖了多个日期的数据，整个扫描区间内的数据无法单纯依靠产品编号有序排列。对照示意图 6.1，扩大扫描范围后，区间内会再次出现数值更小的产品编号，此时数据库只能启用显式排序来完成排序需求。

plaintext

```
---------------------------------------------------------------
|Id |Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT | | 320 | 301 |
| 1 | SORT ORDER BY | | 320 | 301 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES | 320 | 300 |
|*3 | INDEX RANGE SCAN | SALES_DT_PR | 320 | 4 |
---------------------------------------------------------------
```

原本预期走流水线排序执行，结果数据库依旧启用显式排序，通常只有两个原因：第一，带显式排序的执行计划，优化器评估成本更低；第二，索引扫描区间内的数据排序规则，无法匹配`ORDER BY`的排序要求。

区分这两种情况有一个简单办法：让`ORDER BY`子句的排序字段顺序，和索引字段定义顺序完全一致，以此排除第二种适配性问题。调整后如果依旧走显式排序，说明是优化器判定该方案成本更低；如果不再执行排序操作，则证明原排序规则无法适配索引顺序。

**实用技巧**

将`ORDER BY`排序字段顺序与索引定义顺序保持一致，以此排查显式排序操作出现的根本原因。

遇到这类问题，你大概率会疑惑该如何实现流水线式排序执行。你可以直接按照索引完整字段顺序编写`ORDER BY`语句执行查询，再核对执行结果。多数情况下你会发现，是自身对索引排序逻辑存在认知偏差，索引实际排序规则原本就无法满足原有排序需求，自然无法借助索引免去排序步骤。

倘若优化器单纯因为成本评估，优先选择了显式排序方案，这一般是因为优化器会以**取出最后一条数据的整体耗时**，作为评判最优执行计划的标准。但如果数据库检测到应用端仅需要读取前几行数据，优化器便会转而优先选用依托索引的流水线排序方案，相关优化思路会在第七章详细讲解。

## 聚集因子自动优化机制

Oracle 数据库会将行物理地址`ROWID`纳入索引排序依据，以此把索引聚集因子控制在最优状态。当多条索引记录的索引键值完全相同时，数据库会依据`ROWID`来敲定这些记录的最终排列顺序。

由于`ROWID`代表数据行在数据表中的物理存储位置，这种排序方式能让索引顺序最大程度贴合数据表物理存储顺序，从而实现最优的索引聚集因子。

一旦在原有索引中新增字段，就相当于在`ROWID`这个排序依据之前，新增了一重排序规则。数据库再也无法自由按照数据表物理顺序排布索引记录，索引的聚集因子表现也就只会变差、无法变好。

即便如此，索引顺序依旧有可能大体贴合数据表存储顺序。比如同一天的销售数据，无论在数据表中还是索引中，大多都会集中存储在一起，只是彼此之间的先后顺序不再完全统一。使用`sale_date+product_id`组合索引查询时，数据库虽然需要重复读取部分数据表数据块，但读取的始终是同一批数据块。再加上高频访问数据会被缓存，实际产生的性能损耗，往往远低于执行成本数值所体现的程度。

## 适配升序、降序与空值优先 / 后置排序

数据库支持双向遍历索引结构，也就是说，只要索引扫描区间内的数据顺序，与`ORDER BY`所需顺序完全相反，同样可以实现流水线式排序。虽然`ORDER BY`中的升序、降序修饰符会限制流水线排序的生效条件，但绝大多数数据库都支持自定义索引排序方向，让索引能够适配各类正反序排序需求。

下方示例反向遍历索引，查询昨日至今的销售数据，并按照销售日期降序、产品编号降序排列：

sql

```
SELECT sale_date, product_id, quantity
FROM sales
WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
ORDER BY sale_date DESC, product_id DESC;
```

对应的执行计划能够清晰看到，数据库采用降序方式遍历索引。

plaintext

```
---------------------------------------------------------------
|Id |Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT | | 320 | 300 |
| 1 | TABLE ACCESS BY INDEX ROWID | SALES | 320 | 300 |
|*2 | INDEX RANGE SCAN DESCENDING| SALES_DT_PR | 320 | 4 |
---------------------------------------------------------------
```

执行时数据库会先通过索引树定位到最后一条符合条件的索引记录，再顺着索引叶子节点的双向链表反向向前遍历，这也是索引叶子节点采用双向链表结构设计的核心原因。

想要依靠反向遍历索引实现流水线排序，必须保证索引原生顺序与查询所需排序顺序严格相反。

**重点**

数据库支持正向、反向双向读取索引数据。

如果`ORDER BY`子句中混用升序与降序规则，就无法满足上述前提条件：

sql

```
SELECT sale_date, product_id, quantity
FROM sales
WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
ORDER BY sale_date ASC, product_id DESC;
```

该查询要求先按日期升序排布，同一日期内的数据再按产品编号降序排列。对照示意图 6.3 可以看出，想要达成这种排序效果，索引遍历过程中必须进行跳跃式读取，但索引链表不存在这类跳转路径，因此无法借助现有索引免去显式排序操作。

针对这类混合排序场景，主流数据库支持在建索引时直接指定字段排序方向，精准匹配查询排序规则：

sql

```
DROP INDEX sales_dt_pr;
CREATE INDEX sales_dt_pr
ON sales (sale_date ASC, product_id DESC);
```

**注意**

MySQL 数据库会忽略索引定义中填写的升序、降序修饰符。

调整索引排序规则后，索引顺序完全匹配查询排序需求，数据库即可再次跳过显式排序步骤。

plaintext

```
---------------------------------------------------------------
|Id | Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 | SELECT STATEMENT | | 320 | 301 |
| 1 | TABLE ACCESS BY INDEX ROWID| SALES | 320 | 301 |
|*2 | INDEX RANGE SCAN | SALES_DT_PR | 320 | 4 |
---------------------------------------------------------------
```

**重点**

当`ORDER BY`子句混用升序、降序排序规则时，必须同步按照相同的升降序规则定义索引字段顺序，才能依托索引实现流水线排序。

该调整方式不会影响索引原本用于匹配`WHERE`筛选条件的能力。

单纯想要整体反转所有字段排序顺序，无需在建索引时统一修改所有字段升降序，直接反向遍历索引即可实现，仅有索引组织表的二级索引是唯一例外。

索引组织表的二级索引会自动内嵌聚集键，且无法自定义聚集键的排序方向。如果需要让聚集键按降序排列，只能将其余所有索引字段统一设为降序，再通过反向遍历索引的方式，获取目标排序结果。

除升序、降序外，SQL 标准还定义了两种使用频率较低的排序修饰符：`NULLS FIRST`（空值排在最前）与`NULLS LAST`（空值排在最后）。针对空值排序的精细化控制，是 SQL:2003 标准新增的可选拓展语法，因此各大数据库的兼容支持程度参差不齐。

SQL 标准并未严格统一空值的默认排序位置，仅规定所有空值排序后必须集中排布，却没有明确界定空值该排在有效数据之前还是之后。严格来讲，只要排序字段允许为空值，想要实现稳定可控的排序效果，就必须手动指定空值排布规则。

从实际兼容情况来看，SQL Server 2012 与 MySQL 5.6 均未实现这套空值排序语法；Oracle 早在该语法纳入标准之前，就已经支持空值排序写法，但截至 11g 版本，依旧不支持在建索引时指定空值排布规则，这也就意味着 Oracle 无法依托索引实现带`NULLS FIRST`规则的流水线排序；仅有 PostgreSQL 从 8.3 版本开始，既支持查询语句中使用空值排序修饰符，也支持在建索引时直接定义空值排列顺序。

## 为分组查询建立索引

数据库执行`GROUP BY`分组聚合查询，主要依靠两种截然不同的算法。

第一种是哈希分组算法：先将所有输入数据存入临时哈希表完成聚合计算，等全部数据处理完毕后，再统一返回最终聚合结果。

第二种是排序分组算法：先按照分组字段对数据排序，让同一分组的数据连续排布，之后再对连续数据批量完成聚合统计。

整体而言，这两种算法都需要生成中间临时数据，默认都无法以流水线形式执行。但排序分组算法可以借助索引免去前置排序步骤，进而实现流水线式分组执行。

**备注**

MySQL 5.6 版本不支持哈希分组算法，但下文讲解的排序分组优化逻辑，在该版本中依旧适用。

沿用前文的索引结构，执行下方按产品编号分组、统计昨日销售总额的查询：

sql

```
SELECT product_id, sum(eur_value)
FROM sales
WHERE sale_date = TRUNC(sysdate) - INTERVAL '1' DAY
GROUP BY product_id;
```

由于`sale_date+product_id`组合索引扫描出的数据，本身就已经按照分组字段有序排布，排序分组算法无需再生成临时数据、执行显式排序，直接以流水线方式完成分组聚合运算。

plaintext

```
---------------------------------------------------------------
|Id |Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT | | 17 | 192 |
| 1 | SORT GROUP BY NOSORT | | 17 | 192 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES | 321 | 192 |
|*3 | INDEX RANGE SCAN | SALES_DT_PR | 321 | 3 |
---------------------------------------------------------------
```

在 Oracle 执行计划中，无需排序的流水线分组操作会标注`NOSORT`标识，其余数据库的执行计划则会直接省略所有排序相关标识。

流水线分组查询的生效前提，和流水线排序基本一致，且不受升序、降序规则影响，在建索引时定义的字段升降序，不会干扰流水线分组的正常执行，空值排布规则同理。不过部分数据库存在兼容限制，例如 PostgreSQL 想要让带空值后置规则的索引适配流水线分组，必须额外补充`ORDER BY`子句；Oracle 也无法通过反向遍历索引，实现 “分组后再排序” 的流水线组合执行。

和排序优化场景一致，扩大数据查询范围后，流水线分组同样会失效：

sql

```
SELECT product_id, sum(eur_value)
FROM sales
WHERE sale_date >= TRUNC(sysdate) - INTERVAL '1' DAY
GROUP BY product_id;
```

此时索引扫描结果无法按照分组字段连续有序排布，Oracle 会自动切换为哈希分组算法。

plaintext

```
---------------------------------------------------------------
|Id |Operation | Name | Rows | Cost |
---------------------------------------------------------------
| 0 |SELECT STATEMENT | | 24 | 356 |
| 1 | HASH GROUP BY | | 24 | 356 |
| 2 | TABLE ACCESS BY INDEX ROWID| SALES | 596 | 355 |
|*3 | INDEX RANGE SCAN | SALES_DT_PR | 596 | 4 |
---------------------------------------------------------------
```

哈希分组算法的优势在于，仅需缓存最终聚合结果即可完成运算；而排序分组算法需要缓存全部原始输入数据，对比之下哈希分组占用的内存资源更少。

和流水线排序一样，流水线分组查询最大的价值，并非单纯提升整体执行速度，而是能够以流水线形式运行，无需读完所有数据就能率先输出首批分组结果，这也是下一章进阶优化方案得以实现的核心基础。

# 第七章 部分结果集

很多时候我们并不需要一条 SQL 查询的全部结果，只需要其中前几行数据，例如只展示最新十条消息。在这类场景中，通常还需要支持用户翻阅更早的历史内容，既可以采用传统分页浏览模式，也可以使用当下更流行的无限滚动加载模式。但如果为了筛选出最新数据，不得不对全量数据进行排序，这类业务对应的 SQL 语句就极易产生严重的性能问题。因此，流水线式排序是优化这类查询极为高效的手段。

本章将讲解如何借助流水线式排序高效查询部分结果集。不同数据库实现这类查询的语法虽有差异，但底层执行逻辑高度相近，这也印证了各类数据库在核心执行逻辑上是相通的。

## 查询前 N 行数据

前 N 行查询指将查询结果限定为指定行数的查询语句，常用来筛选数据集内最新数据或者优先级最高的数据。想要让这类查询高效执行，必须依靠流水线式排序完成数据顺位排布。

仅读取查询结果前几行最简单的方式，就是取出所需行数后直接结束语句执行。但数据库优化器在生成执行计划时，无法提前预判应用程序是否只会读取部分数据。优化器选定最优执行方案前，必须确认应用最终是否会拉取全部结果集。

若是需要读取全量数据，采用全表扫描搭配显式排序的执行方式或许效率更高；可如果仅读取前十行数据，即便需要逐行读取数据，流水线式排序的执行效果也会更优。

也就是说，优化器需要提前知晓你是否会在读取完所有数据之前终止查询执行，才能精准选出最优执行计划。

**小提示**

当业务无需获取查询全部结果时，务必让数据库知晓这一需求。

长久以来 SQL 标准都没有纳入这类需求对应的语法规范，直到 SQL:2008 标准才正式引入`FETCH FIRST`语法，目前仅有 IBM DB2、PostgreSQL 以及 SQL Server 2012 及以上版本支持该标准语法。

一方面是因为该语法不属于 SQL 核心基础语法，另一方面是各大数据库早已推出各自独有的专属实现方式。

下文以查询最新十条销售记录为例，展示各类数据库常用的前 N 行查询语法，所有示例逻辑一致：从最新数据开始读取销售记录，通过对应语法读取十条数据后终止查询。

### MySQL

MySQL 与 PostgreSQL 使用`LIMIT`子句限定读取数据行数

sql

```
SELECT *
FROM sales
ORDER BY sale_date DESC
LIMIT 10;
```

### Oracle 数据库

Oracle 提供伪列`ROWNUM`自动为结果集中的数据行编排序号，若要通过该伪列做条件筛选，需要嵌套一层子查询

sql

```
SELECT *
FROM (
    SELECT *
    FROM sales
    ORDER BY sale_date DESC
)
WHERE rownum <= 10;
```

### PostgreSQL

PostgreSQL 从 8.4 版本开始支持`FETCH FIRST`标准语法，同时也兼容上文 MySQL 所用的`LIMIT`语法

sql

```
SELECT *
FROM sales
ORDER BY sale_date DESC
FETCH FIRST 10 ROWS ONLY;
```

### SQL Server

SQL Server 使用`TOP`关键字限定结果行数，2012 版本起同步支持`FETCH FIRST`标准语法

sql

```
SELECT TOP 10 *
FROM sales
ORDER BY sale_date DESC;
```

上述所有写法都具备特殊性，数据库能够直接识别出这是前 N 行限定查询。

**重点**

数据库只有在一开始就明确知晓只需部分查询结果时，才能针对性做部分结果集查询优化。

倘若优化器判定业务仅需前十行数据，在条件允许的情况下，会优先选用流水线式排序执行方案。

plaintext

```
-------------------------------------------------------------
| Operation | Name | Rows | Cost |
-------------------------------------------------------------
| SELECT STATEMENT | | 10 | 9 |
| COUNT STOPKEY | | | |
| VIEW | | 10 | 9 |
| TABLE ACCESS BY INDEX ROWID| SALES | 1004K| 9 |
| INDEX FULL SCAN DESCENDING| SALES_DT_PR | 10 | 3 |
-------------------------------------------------------------
```

在 Oracle 的执行计划中，`COUNT STOPKEY`代表查询会按预设行数提前终止执行，这也说明数据库成功识别出了前 N 行查询逻辑。

**小提示**

附录《执行计划解读》汇总整理了 MySQL、Oracle、PostgreSQL、SQL Server 四大主流数据库常见执行计划操作含义。

选对查询语法只是优化的第一步，想要实现高效提前终止查询，底层执行流程必须采用流水线模式。这就要求`ORDER BY`排序字段必须被索引覆盖，本示例中对应的就是基于销售日期、产品编号建立的`sale_dt_pr`索引。

依托该索引，数据库无需执行显式排序操作，读取到索引内的数据后便可直接推送至应用端，读取满指定行数后立即停止检索，不会读取多余数据。

**重点**

流水线式前 N 行查询无需读取并排序全量结果集。

如果没有适配流水线排序的销售日期索引，数据库只能读取整张数据表并完成全量排序，必须读取完表内最后一行数据后，才能向外输出第一条查询结果。

plaintext

```
--------------------------------------------------
| Operation | Name | Rows | Cost |
--------------------------------------------------
| SELECT STATEMENT | | 10 | 59558 |
| COUNT STOPKEY | | | |
| VIEW | | 1004K| 59558 |
| SORT ORDER BY STOPKEY| | 1004K| 59558 |
| TABLE ACCESS FULL | SALES | 1004K| 9246 |
--------------------------------------------------
```

这类未走流水线排序的执行计划，运行效率和在应用层手动终止查询相差无几。不过使用数据库原生前 N 行语法依旧存在优势：数据库无需生成完整结果集，仅需整理出前十条最新数据即可，大幅减少内存资源占用。

Oracle 执行计划中，排序操作后标注的`STOPKEY`标识，就代表启用了该层面的优化。

流水线式前 N 行查询不仅能直接提升查询响应速度，还具备更优秀的横向扩展能力。

未采用流水线执行逻辑的前 N 行查询，响应耗时会随着数据表数据量增大而不断增加；而流水线式前 N 行查询的响应耗时，仅和需要读取的数据行数相关。

简单来说，流水线式前 N 行查询的响应速度基本不受数据表整体数据量影响，仅当 B 树索引层级变深时，查询速度才会出现轻微变慢。

示意图 7.1 展示了两种执行方式在数据量不断增长场景下的性能差异：非流水线执行模式的响应耗时呈线性上涨，流水线执行模式的响应耗时则基本保持平稳。

即便流水线式前 N 行查询不受数据表总数据量影响，其响应耗时依旧会随读取行数增多而变长，读取数据量翻倍，耗时也基本同步翻倍。

这一问题在分页加载更多数据的场景中尤为突出：传统分页查询往往会从头重新遍历数据，重复读取上一页已经加载过的数据并丢弃，最终才能定位到当前页数据。下文将介绍解决该问题的具体方案。

## 分页查询结果集

借助流水线式前 N 行查询实现首页数据高效加载后，通常还需要编写查询语句拉取后续分页数据，核心难点在于如何跳过前面页面已经加载过的数据。目前主流有两种实现思路：

第一种为偏移量分页法：从数据集起始位置统一编排数据行序号，通过行号筛选过滤掉前置页面的数据；

第二种笔者称之为锚点定位分页法：记录上一页最后一条数据的字段值，直接从该位置向后读取后续数据。

首先介绍应用范围更广的偏移量分页法，它最大的优势是使用逻辑简单，各大数据库也大多为此提供了专属语法，`OFFSET`偏移量语法甚至已经被纳入 SQL 标准的`FETCH FIRST`拓展语法中。

### MySQL

MySQL 与 PostgreSQL 通过`OFFSET`子句跳过指定行数的数据，再搭配`LIMIT`限定当前页读取行数

sql

```
SELECT *
FROM sales
ORDER BY sale_date DESC
LIMIT 10 OFFSET 10;
```

### Oracle 数据库

Oracle 依靠`ROWNUM`伪列自动编排行号，但无法直接对该伪列使用大于等于条件筛选。需要通过别名重新定义行号字段，完成分层筛选

sql

```
SELECT *
FROM ( 
    SELECT tmp.*, rownum rn
    FROM ( 
        SELECT *
        FROM sales
        ORDER BY sale_date DESC
    ) tmp
    WHERE rownum <= 20
)
WHERE rn > 10;
```

该语句以内层`ROWNUM`限定最大行数，外层别名`RN`限定最小行数，完成分页筛选。

### PostgreSQL

SQL 标准的偏移量查询语法支持`OFFSET ... ROWS`写法，PostgreSQL 仅需书写`OFFSET`关键字即可，同时也兼容传统`LIMIT+OFFSET`写法

sql

```
SELECT *
FROM sales
ORDER BY sale_date DESC
OFFSET 10
FETCH NEXT 10 ROWS ONLY;
```

### SQL Server

SQL Server 专属的`TOP`语法不支持偏移量设置，2012 版本引入标准分页语法后，`OFFSET`子句成为必写项

sql

```
SELECT *
FROM sales
ORDER BY sale_date DESC
OFFSET 10 ROWS
FETCH NEXT 10 ROWS ONLY;
```

偏移量分页法除了使用简便之外，还可以直接通过设置偏移量数值随意跳转查询任意分页数据。但该方式存在明显缺陷：数据库必须从头逐行统计数据行数，直到遍历至目标分页起始位置为止，翻阅页码越靠后，需要遍历的索引区间范围就越大。

这种分页方式存在两大弊端：第一，数据表新增数据后，整体数据行排序序号会发生变动，出现分页数据错位问题；第二，翻阅历史更早的分页数据时，查询响应耗时会持续增加。

而锚点定位分页法能够同时规避以上两类问题，该方式以上一页最后一条数据的字段值作为分界条件，直接筛选出排序顺位在该数据之后的内容，通过`WHERE`条件即可实现逻辑筛选，本质就是不再重复查询已经展示过的数据。

以下为锚点定位分页法示例，为方便演示，先设定每日仅产生一条销售数据，此时销售日期可作为唯一排序标识。

由于采用日期降序排序，想要查询当前日期之前的数据，需要使用小于条件；若为升序排序，则使用大于条件筛选，最后搭配行数限定语法读取十条数据。

sql

```
SELECT *
FROM sales
WHERE sale_date < ?
ORDER BY sale_date DESC
FETCH FIRST 10 ROWS ONLY;
```

该方式不再依赖行号分页，而是通过上一页末尾数据的字段值划定查询起始边界，性能优势十分明显：数据库能够直接利用`sale_date < ?`这个条件走索引检索，真正跳过前置页面的数据。同时数据表新增数据，也不会打乱已有分页的数据展示顺序，查询结果稳定性更强。

但如果同一天内存在多条销售数据，这种简单的单字段锚点筛选就会失效。直接用上一页最后一条数据的日期作为筛选条件，会过滤掉同一天内所有销售数据，而非仅过滤已展示过的部分数据。

出现该问题的根源在于：仅靠单一日期字段编写的`ORDER BY`排序语句，无法确定数据行唯一固定的排列顺序，而稳定不变的排序顺位，是精准实现锚点分页筛选的必要前提。

倘若排序规则无法确定数据行唯一顺位，数据库返回的数据排列顺序就不具备确定性。日常查询能拿到顺序一致的结果，只是因为数据库默认执行逻辑固定，并非语法层面做出了强制限定。

在数据库并行查询机制启用后，不同执行线程完成数据检索的先后顺序存在随机性，即便执行完全相同的查询语句，每次返回的数据排列顺序都有可能出现差异。

**重点**

分页查询必须依托确定且唯一的排序规则。

即便业务需求仅要求按日期倒序排列最新数据，开发人员也必须主动完善`ORDER BY`语句，确保最终生成唯一固定的数据排列顺序。

如果用于流水线排序的组合索引本身包含多个字段，优先将索引内剩余字段补充至排序语句中，沿用原有索引实现流水线排序；若依旧无法锁定唯一排序顺位，就继续添加主键等具备唯一性的字段，同步调整对应索引结构。

下方示例在排序字段与索引中都加入主键`sale_id`，以此确定唯一数据顺位，同时结合多字段行值对比语法实现精准锚点筛选：

sql

```
CREATE INDEX sl_dtid ON sales (sale_date, sale_id);

SELECT *
FROM sales
WHERE (sale_date, sale_id) < (?, ?)
ORDER BY sale_date DESC, sale_id DESC
FETCH FIRST 10 ROWS ONLY;
```

该`WHERE`子句运用了使用频率较低的**行值表达式**语法，能够将多个字段值整合为一个整体参与条件比对。和单字段比对逻辑一致，降序排序场景下，小于号代表筛选排序顺位更靠后的数据，以此精准筛选出目标分界数据之后的所有内容。

行值表达式属于 SQL 标准语法，但主流数据库适配程度参差不齐：SQL Server 2012 完全不支持该语法；Oracle 虽在语法层面支持行值表达式，却无法对其使用区间比对运算符，执行会抛出异常；MySQL 能够正常解析行值表达式逻辑，但无法将其作为索引检索条件；仅有 PostgreSQL 完整支持行值表达式，还能依托对应组合索引完成高效检索。

对于不支持行值表达式精准比对的数据库，可以采用等效改写的方式实现锚点分页逻辑，虽然写法不够简洁、执行效率也略有折扣，但可以实现同等业务效果，以下为 Oracle 适配写法：

sql

```
SELECT *
FROM ( 
    SELECT *
    FROM sales
    WHERE sale_date <= ?
    AND NOT (sale_date = ? AND sale_id >= ?)
    ORDER BY sale_date DESC, sale_id DESC
)
WHERE rownum <= 10;
```

该条件分为两层逻辑：第一层通过`sale_date <= ?`筛选出大范围目标数据，该条件可以正常走索引检索；第二层剔除掉上一页已经展示过的重复数据。

从执行计划能够看出，数据库仅将第一层日期范围条件作为索引访问条件，第二层仅作为结果过滤条件使用。数据库会少量读取部分前置页面的数据，但会快速过滤剔除，不会造成大量无效遍历。

### SQL 行值表达式

除基础单字段标量值之外，SQL 标准还定义了行值构造器，作用是将一组有序数值组合构成单行或局部行数据。从语法形式来看，行值表达式就是括号包裹的数值列表，该语法最常应用于`INSERT`插入语句中。

在行内`WHERE`条件中使用行值表达式的用法虽少为人知，但完全符合 SQL 语法规范，SQL 标准也为行值表达式定义了全套比对运算符。

以小于比对规则为例：当两个行值表达式前置所有对应字段数值全部相等，且某一顺位字段前者数值小于后者时，判定前者整体行值小于后者。

这套比对规则恰好和锚点分页所需要的 “排序顺位先后” 逻辑完全契合。

示意图 7.4 对比了偏移量分页法与锚点定位分页法的性能差异：数据量较少时二者差距微弱，翻阅页码达到 20 页及以上后，偏移量分页的性能劣势会彻底凸显。

当然锚点定位分页法也存在短板，最突出的就是使用逻辑复杂：不仅需要精准编写多层筛选条件，还无法随意跳转指定分页；如果需要切换前后翻阅方向，还必须同步修改所有比对条件与排序规则。

而这些短板，在前端采用无限滚动加载的业务场景中都可以规避。

### 等效逻辑改写说明

同一种筛选逻辑可以编写成多种不同的 SQL 条件写法，例如上文的分页过滤逻辑也可改写为：

sql

```
WHERE 
( sale_date < ? )
OR 
( sale_date = ? AND sale_id < ? )
```

这种写法逻辑通俗易懂，但数据库无法识别出该语句的整体检索范围，只会将整段条件全部作为结果过滤条件使用，无法高效走索引检索。

即便手动补充冗余的范围条件优化检索效率，也会大幅降低 SQL 语句可读性，还存在后续迭代维护中误删冗余条件的风险，因此优先选用前文的等效筛选写法更为稳妥。

## 借助窗口函数实现分页查询

窗口函数是另一种符合 SQL 标准规范的分页实现方式，语法灵活度极高。

但不同数据库对窗口函数分页的流水线执行支持度差异较大：Oracle 与 SQL Server 能够依托窗口函数实现流水线式前 N 行查询；PostgreSQL 执行窗口函数分页查询时，无法在读取足量数据后及时终止索引扫描，执行效率偏低；MySQL 则完全不支持窗口函数语法。

以下为使用`ROW_NUMBER`行号窗口函数实现分页查询的示例：

sql

```
SELECT *
FROM ( 
    SELECT sales.*,
    ROW_NUMBER() OVER (ORDER BY sale_date DESC, sale_id DESC) rn
    FROM sales
) tmp
WHERE rn between 11 and 20
ORDER BY sale_date DESC, sale_id DESC;
```

`ROW_NUMBER`函数会按照`OVER`子句内定义的排序规则，为所有数据行依次编排序号，外层查询通过行号区间筛选出第二页数据。

Oracle 数据库能够识别这类分页终止逻辑，依托销售日期 + 销售主键的组合索引实现流水线式数据读取，执行计划中`WINDOW NOSORT STOPKEY`标识代表无需额外排序，且读取到指定行数后自动终止查询执行，整体执行效率和偏移量分页法基本持平。

不过窗口函数的核心价值并不在于实现分页查询，而是各类复杂的数据分析统计场景，有学习需求的话，建议花费时间系统研读窗口函数相关官方文档。
